Topic 01 · Terminology

Fault, Error, Failure

three words that are not synonyms, and a four-line program that shows why

This topic is mostly vocabulary, and the vocabulary earns its keep: fault, error and failure name three different things that people routinely call "a bug". The distinction is not pedantry. A test case can execute faulty code, put the program into a wrong state, and still pass — and the example below does exactly that, which is the whole argument for why finding bugs by testing is harder than it sounds.

Why this matters at all

Software in places where it being wrong is not an inconvenience
The case for all this is usually made with cases rather than arguments, and they are worth keeping in mind: glitches in pacemakers; a study reporting at least 212 deaths from device failure across five brands of implantable cardioverter-defibrillator; a sentencing calculation that released more than 3,200 US prisoners early; airbag sensor faults behind a recall of over a million cars.

And the scale of the surface: a premium car contains something like 100 million lines of code across 70 to 100 networked control units (Broy, IEEE Spectrum, 2009).
Two numbers quoted for the rate and the cost
Humphreys puts defect introduction at about 4.2 per hour of programming, and notes that hurrying makes it worse rather than better. Tricentis's Software Fail Watch put the 2016 cost of software faults at 1,100 billion USD, affecting 4.4 billion people.

These are cited figures rather than anything this page can check, and they should be read as the sort of number that makes an argument rather than settles one. What they are arguing is Boehm's curve: the cost of fixing a fault rises sharply with how late it is found, so the economics favour catching things early — which is what testing is for.

The three words

Definitions
Faultan incorrect implementation. Two kinds: commission, where something wrong was written, and omission, where something was never written at all — the harder kind, because there is no line to look at.
Erroran incorrect system state. What the fault does when it runs.
Failurea visible error in the behaviour. Also called an anomaly or an incident.

A fault sits in the code. An error is a moment during execution. A failure is something an observer could notice. They are related in that order, and each step can fail to happen.
The example
Specification: read an integer i, output 2i³. 
1.  cin >> i;
2.  i = 2 * i;
3.  i = pow(i, 3);
4.  cout << i;
Conceptual mistakeconfusing the binding power of the operators
Faultstatements 2 and 3 are in the wrong order
Errorafter line 3, i may hold the wrong value
Failuretest case: input 1, expected output 2, actual output 8

The program computes (2i)³ = 8i³ where it should compute 2i³.

Three things have to happen, and any of them can fail to
  1. The faulty code must run. A fault on a branch nobody takes produces nothing. Here the four lines are straight through, so this is free — in a real program it is most of the difficulty.
  2. Running it must make the state wrong. That is the error. With i = 0 the two programs agree, so the fault runs and the state stays correct.
  3. The wrong state must reach the output. That is the failure. An error that gets overwritten, or cancelled, or discarded before anything is printed is invisible to the test.

Set the tool to 32-bit integers and try i = 2048: the fault runs, the state genuinely goes wrong, and nothing comes out wrong. All three conditions are separate, and that input demonstrates it.

What testing is

Planned experiments, with two different purposes
  1. To reveal bugs — to turn faults into failures. Called testing to fail. "Testing can show the presence of bugs, but not their absence." (Dijkstra)
  2. To gain confidence in quality — testing to pass, which is what reliability work is about.

The word planned is doing work. A test is an experiment with a prediction attached; running the program and looking at the output is not testing.
Test case, test suite
Test casea pair: inputs (values, preconditions, the running environment, the timing of events) and expected outputs (concrete values, or symbolic properties relating input to output)
Test suitea set or list of test cases

The expected output is half the definition. A "test" with no prediction cannot fail, and therefore cannot pass either.
Validation and verification are different questions
ValidationHave we made the right product? Compliance with the intended use. Usually user-centred, usually manual, usually on the finished product.
VerificationHave we made the product right? Compliance between the artefacts of different phases. Usually artefact-driven, and open to being formalised and mechanised at every phase.

A product can be perfectly verified and still the wrong product.

Levels of testing

Three scopes, and what is used at each
Unit single units jUnit, QuickCheck, test-driven development equivalence partitioning, decision tables, classification trees
Integration subsystems together jUnit, Mockito dependency injection, mocking
System the whole product, including acceptance and user testing Selenium GUI model testing, automated GUI testing

Test management and policy are a real part of the subject and are not covered here.

Going beyond testing

Model checking
Check the state space — every execution — against formally specified properties.
+ rigorous; push-button once the model exists
− not yet scalable to very large systems, because of state-space explosion
Static analysis
Check abstract properties without running the program — division by zero, unhandled cases, and so on.
+ automatic and scalable for generic properties
+ powerful tools already exist
− involves approximation, so false positives and true negatives
− complicated for concrete, specific properties — it may take theorem proving to show the abstraction itself is correct

Takeaways

If you remember six things
  1. Fault = incorrect implementation (commission or omission); error = incorrect state; failure = visible incorrect behaviour.
  2. Three conditions in order: the fault must be reached, it must corrupt the state, and the corruption must reach the output. Any of them can fail to happen, and then the test passes.
  3. A test case is a pair — inputs and expected outputs. A test suite is a set of them.
  4. Testing to fail reveals bugs; testing to pass builds confidence. Dijkstra: presence, not absence.
  5. Validation = the right product; verification = the product right.
  6. Levels: unit, integration, system. Beyond testing: model checking (rigorous, does not scale) and static analysis (scalable, approximate).
Things that catch people out
  • Using the three words interchangeably. An exam question asking which of them a scenario describes is asking exactly whether you noticed they differ.
  • Assuming that executing faulty code means detecting it. Both extra conditions are real, and the tool above shows an input where the state goes wrong and the output does not.
  • Forgetting that faults of omission exist. There is no wrong line to find, which is why they are harder.
  • Writing a "test" with no expected output. It cannot fail, so it is not a test.
  • Swapping validation and verification. Right product, versus product right.
  • Reading Dijkstra's line as pessimism. It is a statement about what kind of evidence testing produces — which is why the other techniques exist.
