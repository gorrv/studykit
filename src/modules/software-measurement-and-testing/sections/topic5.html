Topic 05

Mocking and Refactoring

testing a unit whose collaborators you do not want, and changing code without changing what it does

Why this matters

Two practices that sound like advice and are not. A mocking library is a precise description of a behaviour — what a stub returns on the third call, what counts as an interaction, when an argument matcher is allowed — and refactoring has the most checkable definition in the whole module: a transformation that does not change behaviour.

So the tools below contain a small mocking library, written to the rules as the notes state them, and the video-store example carried through its entire chain of seven versions, with every version run against every other on more than a thousand baskets. Both turned something up, and both are below.

Mocking

The usage pattern
The three A's again, with two extra steps at the front and one at the back:
Arrangeinstantiate the mock objects; set up the state that governs their behaviour; set up the expectations on them
Actexecute the method on the unit under test, using the mocks as its resources
Assertverify the results and the expectations

That last clause is what makes mocking different. An ordinary unit test asserts on a value the unit returned; a test with mocks can assert on what the unit asked its collaborators to do, which is the only thing to assert about a method that returns nothing.
Stubbing
when(mock.method(args)) is the trigger; what follows says what to do when it fires.
thenReturn(x)return x; several values can be given for consecutive calls
thenThrow(x)throw x
thenAnswer(a)run user-defined logic rather than returning a hard-coded value — a fake rather than a stub
thenCallRealMethod()call the real method on the mock object

A method that was never stubbed returns the default value of its return type: false for a boolean, null for an object, zero for a number. Not an error — which is why a mock whose stub does not match quietly returns nothing instead of telling you.

For a method that returns void, when(...) cannot be used: it would have to call the real method to get an argument. The form is doThrow(exception).when(mock).voidMethod(args).

Verification

verify, and how many times
times(n)exactly n times; fewer or more fails
never()the same as times(0)
atLeastOnce()one or more
atLeast(n) / atMost(n)bounds rather than an exact count
only()this call, once, and nothing else on that mock at all
timeout(ms)interacted with inside a time window

verifyNoInteractions(mocks...) asks that nothing at all happened. verifyNoMoreInteractions(mocks...) asks that nothing unverified happened, so it goes after the verifications it is checking — and it catches the call you forgot rather than the call you got wrong.

Argument matchers, and the rule that catches everyone
any(), anyInt(), anyString(), anyList(), eq(x), and argThat(matcher) for a custom one. Mockito compares arguments in natural Java style with equals(); matchers are for when that is not flexible enough.

If any argument is given by a matcher, every argument must be. 
verify(mock).someOtherMethod(anyInt(), anyString(), eq("third arg"));   // fine
verify(mock).someOtherMethod(1, anyString(), "third argument");         // fails
The reason is in how matchers work rather than in the documentation: they are pushed onto a stack as they are evaluated, and the mock sees only how many arrived, not which positions they came from. Three matchers and three arguments it can line up; one matcher and three arguments it cannot.

And a stub whose arguments do not match simply does not fire — the method returns the default for its type. when(mock.getValue(1)) followed by mock.getValue(100) returns null, not an error.
Consecutive calls, and the order of calls
thenReturn(a, b, c) returns a on the first call, b on the second, c on the third — and the last value on every call after that. Useful when a loop needs different answers, or when the first call should throw and the rest should not.

inOrder(mocks...) builds a verifier whose verifications must occur in the order they are written, across all the mocks passed to it, finishing with inOrder.verifyNoMoreInteractions().

Refactoring

The definitions
a refactoring
noun		a change made to the internal structure of software to make it easier to understand and modify without changing its external behaviour
to refactor
verb		a disciplined technique for restructuring an existing body of code, altering its internal structure without changing its external behaviour

Each transformation does little; a sequence of them produces a significant restructuring. Because each one is small it is less likely to go wrong, and the system is kept fully working after each, which is what stops the restructuring from breaking it.

Refactoring is not reduction. The purpose is to improve the structure, and shorter code is a frequent side effect rather than the goal.
What it is not
− just any change — a refactoring has a clear purpose and proceeds in small, mechanical, deterministic steps
− an excuse for not thinking — the initial design should still be the best effort you can make. Before choosing the simplest solution, imagine the migration route to the alternatives; if it looks easy, go ahead, and if it looks impossible, think harder now
The methodology, and the two hats
Make every change small and methodical, following patterns that could in principle be automated. Re-test after each change by rerunning all the unit tests: if something breaks you know exactly what caused it. This needs fully automated tests, which is why the topic sits where it does.
refactoring hatupdating the design, not what the code does — so the existing tests are the check
feature-adding hatchanging what the code does — so new tests come first

Switch hats often, and always know which one you are wearing.
The rule of three
The first time you do something, you just do it. The second time you do something similar, you wince at the duplication — and do it anyway. The third time, you refactor. Three strikes and you refactor.

When: before adding a feature, to make the feature easier to add; when fixing a bug, because a bug report is a sign the code was not clear enough for you to have seen it; and at a code review, where it spreads knowledge through the team and works best in small groups.

This is the one definition you can check
"Behaviour preserving" is a claim about every input, so it can be measured. Every version above is run against every other on every basket of one or two rentals drawn from three classifications and twelve rental lengths — just under eight thousand comparisons — and not one produces a different statement.

Compare the refactoring steps in Topic 4, where the same word covered a change that altered 998 answers out of 1000. The difference is the tests: with two tests, behaviour-preserving means almost nothing; with a suite that pins the output down, it means what it says. Refactoring is only as safe as the suite you run after each step, which is why the methodology insists on running them all, every time.

Bad smells

The catalogue
Twenty names for things worth looking at. The point of the list is not that each is always wrong — it is that each has a known refactoring attached to it, so spotting one tells you what to do next.

Three of them appear in the example above: the original method is a Long Method with a Switch Statement in it, and amountFor is Feature Envy of Rental.
Simple design, in priority order
  1. The code is appropriate for the intended audience.
  2. The code passes all the tests.
  3. The code communicates everything it needs to.
  4. The code has the smallest number of classes.
  5. Each class has the smallest number of methods.

Which raises the obvious objection: should everything be one class with one method? No — the list is in priority order, and the fourth and fifth lose to the third, and to the single responsibility principle behind it.
Refactoring and performance
Some refactorings make the software slower, and that may or may not matter. Only a small fraction of a code base influences performance at all, so optimising all of it equally wastes most of the effort — and most people's intuitions about which fraction it is turn out to be wrong, which is what a profiler is for.

A well-factored program is unusually easy to tune, because the thing to tune is in one place. Make it work, make it clean, make it fast — in that order.

Takeaways

What to be able to do
  1. Write a test with a mock: create it, stub it, act, and verify the interaction.
  2. Give the when(...).thenNnnn() family and say what an unstubbed method returns.
  3. Give the verification modes, and state the matcher rule and why it exists.
  4. Say what thenReturn(a, b, c) returns on the fourth call.
  5. Define refactoring both ways round, and give the rule of three and the three occasions for it.
  6. Carry the video-store example through at least extract method, move method and replace temp with query, and say which smell each one answers.
  7. Say what the two hats are and why you must know which one you have on.
