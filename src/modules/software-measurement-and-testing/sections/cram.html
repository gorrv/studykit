Topic 01 · fault, error, failure

The three words

  • Fault — incorrect implementation. In the code, whether or not it runs.
  • …of commission (wrong thing written) or omission (nothing written) — omission is harder, there is no line to look at.
  • Error — incorrect system state, during execution.
  • Failure — visible incorrect behaviour. Also anomaly, incident.

Three conditions, in order

  • Reached — the faulty code actually executes.
  • Infected — executing it makes the state wrong. That is the error.
  • Propagated — the wrong state reaches the output. That is the failure.
  • Any one can fail to happen, and then the test passes despite the fault.

The worked example

  • Spec: output 2i³. Code: i = 2*i; then i = pow(i,3); — so (2i)³ = 8i³.
  • Fault: statements 2 and 3 in the wrong order. Error: i wrong after line 3. Failure: input 1 → 8, not 2.
  • Hidden at i = 0 over the integers — and at every multiple of 2048 in real 32-bit arithmetic, because 6i³ must vanish mod 2³².

Test case, test suite

  • Test case = a pair: inputs (values, preconditions, environment, timing) and expected outputs.
  • Expected outputs may be concrete values or symbolic properties relating input to output.
  • Test suite = a set or list of test cases.
  • No prediction, no test.

Two purposes

  • Test to fail — reveal bugs, turn faults into failures.
  • Test to pass — gain confidence in quality; the reliability literature.
  • Dijkstra: testing can show the presence of bugs, but not their absence.

Validation vs verification

  • Validation — have we made the right product? Intended use; user-centred; usually manual; on the end product.
  • Verification — have we made the product right? Between artefacts of different phases; artefact-driven; formalisable and mechanisable.

Levels

  • Unit — jUnit, QuickCheck, TDD; equivalence partitioning, decision tables, classification trees.
  • Integration — jUnit, Mockito; dependency injection, mocking.
  • System — acceptance and user testing; Selenium; GUI model testing.

Beyond testing

  • Model checking — the whole state space against formal properties. + rigorous, push-button. − state-space explosion.
  • Static analysis — abstract properties without running it. + automatic, scalable, good tools. − approximates, so false positives; hard for specific properties.

Topic 02 · functional testing

Boundary values, four variants

  • For [a, b] the interesting values are a, a+1, nominal, b−1, b; robust adds a−1 and b+1.
  • BV — one variable at a time, others nominal: 4n + 1.
  • Robust BV — 6n + 1.
  • Worst case — all combinations: 5ⁿ. Robust worst case: 7ⁿ.
  • − no sense of covering the domain, awkward for booleans, independent variables only, no white-box information.

Equivalence classes, four variants

  • Weak normal — every class of each variable. Single fault assumption. maxₓ |Sₓ|.
  • Strong normal — every combination. Multiple fault assumption. ∏ₓ |Sₓ|.
  • Weak robust — plus out of range per variable. maxₓ |Sₓ| + 2n.
  • Strong robust — ∏ₓ (|Sₓ| + 2).
  • Why max and not sum: each test case is one token covering a class of every variable at once — the m × n grid puzzle, answer max(m, n).

The mortgage example

  • Classes: age 6 (18-30 31-35 36-40 41-45 46-50 51-55), full-time 2, salary 1.
  • So weak normal max(2,6,1) = 6, strong normal 2×6×1 = 12.
  • The implementation holds four faults — two off-by-one bounds, one wrong constant, and a missing range check, which is the fault of omission.
  • Part-timers aged 51–55 are in range and in no category — the gap the specification itself leaves.

Two results worth remembering

  • The robust formulas overcount here, because full-time is a boolean with no out-of-range value: max + 2n says 12 where 10 exist, ∏(|S|+2) says 96 where 48 exist.
  • Robust worst case: 98 tests, 7 faults. Strong robust EC: 48 tests, 8 faults. No boundary value lands in 40–45, so boundaries miss that band entirely.
  • So A → B orders only the comparable techniques. Boundaries catch off-by-one; class interiors catch wrong constants.

What EC leaves open

  • No constraints on the classes — nothing stops a bad partition.
  • Dependencies between variables are ignored — age depends on full-time, and there is nowhere to say so.
  • No choice among classes — you cannot mix worst case on one variable with boundary values on another.
  • Decision tables and classification trees answer these.

Decision tables

  • Stub = the first column: conditions above, actions below. Entry = the other columns, the rules.
  • Condition entries may be true, false, other values, or don't care; action entries are do or do-not.
  • Conditions need not be independent — which is exactly what the other techniques assume.
  • Completeness: the rule counts must sum to ∏ nₐ, and each don't care counts for two (or for however many values its condition has).

Classification trees

  • Find the aspects of the specification that influence the behaviour.
  • Put them in a hierarchy — more global aspects higher.
  • Partition each aspect's domain; every partition must cover the whole domain of its parent class.
  • Then a combination table: one test case per relevant combination, so dependencies can be respected and irrelevant combinations dropped.

Which technique when

  • Physical independent variables → boundary values; robust if there is no error handling, worst case if failure is costly.
  • Logical variables → equivalence classes on the same pattern.
  • Variables not independent → decision tables or classification trees.
  • Always: the question is not which technique is strongest, but which is worth its cost.
