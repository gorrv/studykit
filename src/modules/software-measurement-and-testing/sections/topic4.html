Topic 04

Unit Testing and TDD

what a unit test is, what to put in one, and what happens when the test comes first

Why this matters

The first three topics are about choosing test cases. This one is about the test itself: what it is made of, where it lives, what makes it worth keeping, and what changes when you write it before the code it tests.

It looks like the one topic with nothing to run, and it is not. A test-driven session is a sequence of (test list, code) pairs, and everything the method claims is a claim about that sequence — each new test fails when written, passes when the next scrap of code arrives, and nothing that passed before stops passing. The worked example below is transcribed step by step and that claim is checked at each one. It is also where the interesting result comes from: there is a step where every test passes and the code is still wrong.

What a unit test is

The definition
A self-contained software module — typically a class — containing one or more test scenarios which test a unit under test in isolation. Each scenario is autonomous and tests a separate aspect of that unit.
black boxverifies that the unit behaves correctly — that it honours its contract
white boxverifies that its internal structure or workings behave correctly

Unit tests are written by developers, for developers. They do not address formal validation and verification; they prove that some code does what we intended it to do, and they complement acceptance tests rather than replacing them.
Smoke test
A set of unit tests run as a whole: turn it on and make sure no smoke comes out. A cheap way to see that the units seem to work and fit together — with no guarantee at all about the overall function, which needs functional testing.
The three A's
Arrangeinstantiate the unit under test and set up the test data
Actexecute one or more methods on the unit under test
Assertverify the results
@Test
public void testWithdraw() throws AccountException {
  AccountImpl account = new AccountImpl("1234-9999", 2000);  // ARRANGE
  account.withdraw(300);                                     // ACT
  Assert.assertEquals(1700, account.getBalance());           // ASSERT
}
The same three steps in Python, where the class inherits from unittest.TestCase and the asserts are methods on it: 
def test_withdraw(self):
    self.account.deposit(3 * self.amount)        # Arrange
    self.account.withdraw(self.amount)           # Act
    expected = 2 * self.amount                   # Assert
    self.assertEqual(expected, self.account.get_balance())
Naming and placement
the classa class is a noun, so the tests for MyUnit go in MyUnitTest; in Python a unit is a module, and its tests go in a separate module with test_ prepended
the methoda method is an action, so test the calculate method in testCalculate(), with something appended for each aspect: testWithdrawTooMuch, testWithdrawNegativeAmount
wheresame package as the unit under test, in a parallel directory tree

One scenario per test method. How much to check in one test is a judgement call, but a test covering one potential error condition tells you what broke; a test covering five tells you only that something did.
Goals for test automation: S.M.A.R.T.
Self-containedand stateless — no test may depend on another having run first
Maintainabletest-first produces five to ten times more test code than production code, so its maintenance cost is the larger of the two
Act as documentationthe tests are the definitive reference for what the system is supposed to do
Repeatable and robustpasses alone and in a suite, today and tomorrow
To the pointso that a failure points at one thing — good "defect triangulation"

The fixture

setUp and tearDown
@Beforeruns before every test method — @BeforeEach in JUnit 5, setUp(self) in Python
@Afterruns after every test method — @AfterEach, tearDown(self)

Before every test, not once for the class. That is what makes the first letter of S.M.A.R.T. true, and the tool below measures what it is worth.

Exceptions, and tests that are not run

Three ways to test that something throws
annotation@Test(expected = NastyException.class) in JUnit 4; assertThrows in JUnit 5; @unittest.expectedFailure or assertRaises in Python
try/catchcall it, then fail("Expected a NastyException!") on the next line, and catch the expected exception with an empty body — more typing, but it lets you assert on the state afterwards
lambdaself.assertRaises(ValueError, lambda: account.withdraw(2 * amount)), or hand the framework the function and its arguments and let it do the calling

Unchecked exceptions thrown during a test — null, divide by zero — are caught by the framework and reported as errors, so the test fails. A test method must declare any checked exception the unit may throw; declaring throws Exception is acceptable when there are several.
@Ignore
@Ignore("trying to fix the bug") parks a test without deleting it — and the @Test annotation has to stay, or it is not a parked test but a lost one. A parked test is a known unknown; it costs nothing to keep and everything to forget.

What to test

Not everything
Exhaustive testing means covering every possible aspect of the function. It takes forever and a day and often is not possible at all. The answer is pragmatic testing: test everything that could possibly break, and do not test things that are too simple to break — getters, setters, plain data holders.

The two areas that reliably repay attention are error conditions and boundary conditions.
Right-BICEP — six things to ask
Rightare the results right?
Bare all the boundary conditions CORRECT?
Ican you check inverse relationships? x² against sqrt, insert against read back
Ccan you cross-check results using other means — a second, slower way of getting the same answer?
Ecan you force error conditions to happen? If it cannot be forced, it cannot be tested
Pare performance characteristics within bounds?
CORRECT — seven kinds of boundary
Conformancedoes the value conform to an expected format? 1 000 SEK
Orderingis the set of values ordered, or unordered, as appropriate?
Rangeis the value within reasonable minimum and maximum values? 0–100%
Referencedoes the code reference anything external that is not under its own control?
Existencedoes the value exist — non-null, non-zero, present in a set, file present?
Cardinalityare there exactly enough values? exactly two parents
Timeabsolute and relative — in the right order, at the right time, in time?

Test-driven development

The cycle
  1. Think about what you want to do, and about how to test it.
  2. Write a small test — which is where the API gets designed, because you are its first user.
  3. Watch it fail. The red bar. A compiler error counts.
  4. Write just enough production code to pass it and every earlier test. The green bar.
  5. Refactor to remove duplication and increase expressiveness, then run them all again and see the bar stay green.
  6. Repeat until no test you can think of drives new production code.

Design a little – test a little – code a little, and round again. Work from a test list brainstormed at the start of a task of four to eight hours; do not get hung up on completeness, since you can always add more later.
Step 3 is the one people drop
Watching the test fail is what shows that the test tests anything. A test that has never been red might be asserting nothing at all — and you would never find out, because it is green either way. Two columns that are easy to confuse: whether the tests passed, and whether the code was right.
Green is a statement about the tests
At the Buzz step the five tests written so far all pass, and the code answers Fizz for 15. Nothing is broken in the method — it does exactly what has been asked of it. The largest number any of those five tests mentions is 5, and the smallest number the code gets wrong is 15.

This is the same shape as the fault in the structural topic, arrived at from the other side: there, a test set satisfied every coverage criterion and missed the fault; here, a test list drives code that passes everything on it and is incomplete. Coverage and the green bar are both measurements of the test set, not of the program. The repair in both cases is a better test — and the advantage of the test list is that you were going to write one anyway.

🛠️ Was that really a refactoring?

Practice tool

Two versions, compared on every input

A refactoring changes the structure without changing the behaviour, which is a checkable claim. Two of the nine steps are labelled refactorings; one of them is one.
"Behaviour preserving" means preserving the tested behaviour
Extracting isDivisibleBy changes nothing: the two versions agree on every input. Replacing number == 1 ? "1" : "2" with String.valueOf(number) changes the answer for 998 of the first 1000 inputs — and is still a refactoring in the sense that matters, because the bar stayed green and the behaviour anyone had specified was preserved.

That is not a quibble; it is the mechanism. Early in a session the tests pin down so little that almost any change is behaviour-preserving, which is exactly why the steps can be so crude. The tests are the specification, and the specification grows as you go.

What it changes

The effects the notes claim
+ the tests are already automated, so they are immediately useful as integration and regression tests
+ less time in the debugger, and no long tedious testing phase at the end of the project
+ intentional design of interfaces — the code does not exist yet, so you are free to choose the interface that is most usable
+ non-speculative interfaces — they provide what is needed right now and no more
+ the tests document the intended usage
+ high cohesion and low coupling, because dependencies are what make a unit hard to test
And the weak points
− test code that leans hard on the production API can make that API harder to change — the tests become a second set of callers
− buggy tests: failures caused by the test rather than the code
− and the honest one — it stops being worth it when maintaining the tests costs more than they return
Testability is designed in
Testability has two parts. Visibility: the tester can see and understand what happens inside the system. Control: the tester can force interesting things to happen. Neither arrives by itself, and writing the tests first is a reliable way of getting both — a unit you cannot instantiate without half the system is a unit you will not write a test for, and you find that out on the first day instead of the last.

Takeaways

What to be able to do
  1. Write a unit test in the three A's, named and placed by the convention, in either Java or Python.
  2. Say what setUp runs before, and why "before every test" rather than "once" is the whole of self-containment.
  3. Give Right-BICEP and CORRECT, and apply them to a method you are shown.
  4. Give the TDD cycle in order, and say what step 3 is for.
  5. Explain why a green bar is not a correctness claim, with the Buzz step as the example.
  6. Say what makes a change a refactoring, and in what sense that is relative to the tests you have.
