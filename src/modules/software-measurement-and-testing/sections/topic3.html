Topic 03

Structural Testing

flow graphs, DD-paths, prime paths, and a number that says how hard a program is to test

Why this matters

Functional testing never looks at the program. That is its strength — test cases can be written before a line of code exists — and its weakness: it has no way of knowing which parts of the code its test cases actually reach. Structural testing turns the program into a graph and measures a test set by how much of that graph it touches.

The tools below contain a parser, a flow-graph builder and an interpreter for a small imperative language, so the graphs on this page are built from programs rather than drawn, and the paths are recorded by running them. The punchline of the topic is a program whose test set satisfies every criterion here and still misses the only input it gets wrong; that program is run against its specification across all 65 536 inputs further down.

Flow graphs

The definition
Nodesprogram statements
Edgesp → q exactly when q may execute immediately after p

Four shapes build every program:
sequenceprog₀ ; prog₁ — one edge from the end of the first to the start of the second
conditionalif c then prog₀ else prog₁ fi — one node with two outgoing edges, and the two branches meeting again
whilewhile c do prog — the test comes first, and the body comes back to it
repeatrepeat prog until c — the body comes first, and the test goes back to it

Test adequacy criteria

The ladder, weakest first
A test set covers, in the flow graph,
1all nodes — statement coverage
2all edges — DD-path coverage
3all prime paths — single-loop coverage
4all edges + all combinations of data-flow dependent edges — dependent pairs coverage
5all edges + all combinations of condition edges — multiple-condition coverage
6all paths — full path coverage
Finite feasibility
A criterion is only usable if some finite test set satisfies it. All paths fails that at once: a single loop has infinitely many. Worse, the others fail it too, for a different reason — a node the program can never reach can never be covered, so statement coverage is unsatisfiable for any program with dead code in it.

The repair is to ask only for the reachable nodes, edges and paths. And that does not work either, because deciding reachability is undecidable in general. So every criterion below the top of the ladder is a practical approximation, and the infeasible parts of a real program have to be argued about by hand.

Chains and DD-paths

Chain
A chain n₀, …, nᵢ is a list of nodes where each one leads to the next and indeg(nⱼ) = outdeg(nⱼ) = 1 throughout — a run of statements with no way in except the front and no way out except the back. It is maximal when it cannot be extended at either end.
DD-path
A DD-path is a set of nodes that is either
  1. {n} where indeg(n) ≠ 1 or outdeg(n) ≠ 1 — so start and terminal nodes, branches and merges stand alone; or
  2. {n₀, …, nᵢ} a maximal chain.

Property. Each node belongs to precisely one DD-path. That is what makes the next definition well formed, and the test suite checks it on every graph on this page.
The DD-path graph
Nodes are DD-paths; there is an edge from one to another when some node of the first leads to some node of the second. A test set is adequate when every node and every edge of the DD-path graph is covered by some test case.
equivalent toedge coverage of the flow graph — but with fewer things to check, because a chain collapses to one node
subsumesnode coverage
"Equivalent, with fewer checks" is worth testing
It is also worth being precise about. A self-loop has both ends in the same DD-path, and collapsing it away makes DD-path coverage strictly weaker than edge coverage — a test set can cover everything in the DD-path graph without ever taking the loop. The engine keeps those edges, and the two criteria then agree on every one of a few thousand randomly generated graphs.

One more condition hides in the word equivalent: the test cases have to be complete runs. A path that stops in the middle of a chain can cover every DD-path and still leave an edge inside that chain untaken. Real test cases run to the end, so the equivalence holds — but it is a fact about executions, not about arbitrary paths.

Simple paths and prime paths

The two definitions
simple pathvisits each node at most once, except that the first and last node may be the same — so one complete trip round a loop counts
prime patha simple path that is not a proper sub-path of any other simple path

Informally a prime path is either a complete route from start to end, or one complete and simple iteration of a loop. Prime path coverage asks for a test case covering each one as a sub-path, which comes to all complete simple paths and up to two iterations of each loop.

One input in sixty-five thousand
The program disagrees with its specification on exactly one input, 49, and a test set that covers every statement and every edge can miss it. The reason is worth stating exactly: 49 is the only input that executes both bodies in the same run. Statement and edge coverage are satisfied by two tests that each take one of them, and nothing in either criterion asks for the combination.

Prime path coverage does ask. One of the four prime paths of that program is 0→1→2→3→4 — both conditions true — and the only input that covers it is 49. Here the stronger criterion is exactly strong enough, which is not a thing to expect in general.
What to do about it
  1. Use a stronger criterion — prime paths, dependent pairs, multiple condition coverage.
  2. Expect to pay for it, in test cases, and sometimes to find no more faults for the money.
  3. Write the program differently. A choice — a switch, or if … else if … else — instead of two conditions in a row makes the three cases mutually exclusive, which is what the specification said in the first place. Select that program in the first tool: it has the same cyclomatic number and it agrees with the specification on all 65 536 inputs.
DD-path testing, weighed
+ DD-paths rather than statements: fewer things to measure
+ a practical measure of adequacy
+ implemented in many tools
− infeasible paths still have to be dealt with
− important paths are left untested
− no test case generation technique — it measures a test set, it does not produce one
− the root of it: the specification and the data dependencies are ignored

The cyclomatic number

The idea, and the formula
Take one path from start to exit, then count the alternatives by flipping one condition at a time. Also called McCabe complexity, the nullity, the first Betti number, or the dimension of the cycle space.

For a graph with one connected component, one starting node and one terminal node:
V(G)#edges − #nodes + 2
planar graphs#regions the graph cuts the plane into

It is size independent. Adding a statement in a straight line adds one node and one edge, and the two cancel: a three-statement program and a four-statement program both score 1.

The formula, and the independent cycles it is counting

The second figure joins the exit back to the entry and measures the dimension of the cycle space by elimination — a different calculation that must give the same answer.
Laid end to end
For the running graph, V(G) = 5. Two copies in sequence give 9 = 5 + 5 − 1, not 10, because the exit of the first is the entry of the second and the two share a node. n copies give 4n + 1.

The general rule that follows: composing graphs in sequence adds their cyclomatic numbers and subtracts one each time, so complexity accumulates almost linearly down a program — which is why a long procedure scores badly however simple each part of it is.
What the number is used for
1–10a simple program, without much risk
11–20more complex, moderate risk
21–50complex, high risk program
>50untestable program (very high risk)

Watch for V(G) > 10. It is implemented in several tools, and it was invented as a measure of test-set adequacy rather than of complexity — the number of independent paths you would have to test.

Takeaways

What to be able to do
  1. Draw the flow graph of a program with sequence, conditionals, while and repeat-until.
  2. Partition its nodes into DD-paths from the simplified definition, and draw the DD-path graph.
  3. Give the six adequacy criteria in order and say which are finitely feasible, and why "all reachable" does not rescue them.
  4. List the simple paths of a small graph and pick out the prime ones.
  5. Compute V(G) both ways, and know that it is size independent and that sequential composition gives V₁ + V₂ − 1.
  6. Explain how a test set can satisfy every criterion up to DD-path coverage and still miss a fault — with the 49 example.
