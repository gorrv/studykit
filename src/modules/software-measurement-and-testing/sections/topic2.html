Topic 02 · Functional Testing

Choosing Which Inputs to Try

boundary values, equivalence classes, decision tables and classification trees

A program is a map from a domain of inputs to a range of outputs, and there are far too many inputs to try them all. Functional testing is the business of choosing some — from the specification alone, without looking inside the code. Every technique here is a different answer to "which ones", and each comes with a formula for how many test cases it costs.

The whole topic hangs on one example, and the useful thing about it is that the example is a real program with real faults in it. So rather than take the techniques on trust, the tools below generate each suite, run it, and count what it catches.

Boundary value testing

The idea
A test case for each combination of extreme values — normal and out of bound. For a variable ranging over [a, b] the interesting values are a, a+1, something nominal, b−1, b; robust variants add a−1 and b+1.
BVvary one variable at a time, others at nominal — 4n + 1 test cases
Robust BVthe same, plus just outside — 6n + 1
Worst caseevery combination of the extreme values — 5ⁿ
Robust worst caseevery combination, including outside — 7ⁿ
What is wrong with it
+ test cases are straightforward to generate
− no sense of covering the input domain
− awkward for logical variables — what is the boundary of a boolean?
− only handles independent input domains
− uses no white-box information

The first of those is measurable, and the second tool below measures it: on this example the number of faults boundary value testing finds depends entirely on which values you happened to call nominal.

Equivalence class testing

The idea
Partition the domain of each input variable (and the range of each output) into equivalence classes — sets of values the program ought to treat alike — and then cover the classes. Also called the equivalence partition or category partition method.

The variants differ in how thoroughly they cover:
Weak normalcover every class of each variable. Single fault assumption. maxₓ |Sₓ| test cases
Strong normalcover every combination of classes. Multiple fault assumption. ∏ₓ |Sₓ|
Weak robustweak normal, plus out-of-range values for each variable. maxₓ |Sₓ| + 2n
Strong robustevery combination including out of range. ∏ₓ (|Sₓ| + 2)
A puzzle that explains the first formula
What is the fewest tokens you can place on an m × n grid so that every row and every column holds at least one?

max(m, n) — put token i at (min(i, m), min(i, n)). Weak normal EC is exactly this puzzle: each test case is a token covering one class of every variable at once, so covering all the classes of all the variables costs the largest single count, not the sum.

The mortgage example

The specification
Three inputs: full-time (boolean), age in [18, 55], salary in [0, 10000]. Output the total mortgage, which is salary × factor:
full-time = true false
Young18–35 → 7518–30 → 70
Middle36–45 → 5531–40 → 50
Old46–55 → 3041–50 → 35

Note the gap, because it matters later: a part-timer aged 51 to 55 is inside the permitted age range and in none of the categories. The notes treat that as an error — "too late".
The equivalence classes
agedifficult, because the two columns break differently: [18-30] [31-35] [36-40] [41-45] [46-50] [51-55] — six classes
salary[0-10000] — one class
full-timetrue, false — two, and "as strange as boundary value"

So weak normal EC needs max(2, 6, 1) = 6 test cases, and strong normal needs 2 × 6 × 1 = 12.
And the implementation, which does not match it
if (full-time)
  return (18 ≤ age < 35) ? 75*salary : (31 ≤ age < 40) ? 55*salary : 30*salary
else
  return (18 ≤ age < 30) ? 75*salary : (31 ≤ age < 40) ? 50*salary : 35*salary

More test cases does not mean more faults
The numbers above contain a result worth pausing on. Robust worst case runs 98 test cases and finds 7 faults. Strong robust EC runs 48 and finds 8. Twice the effort, one fault fewer.

The fault it misses is the full-time middle band, ages 40 to 45. Boundary value testing picks ages 17, 18, 19, 36, 54, 55 and 56 — none of which lands between 40 and 45. Equivalence classes pick the middle of each class, so they walk straight into it.

That is the complementarity behind the worst-case technique being described as "BV + EC": boundaries catch off-by-one mistakes, class interiors catch wrong constants and misplaced bands, and neither subsumes the other. The A → B hierarchy orders the techniques that are comparable; these two are not.
A → B means every test case of A is a test case of B
The techniques form a hierarchy, so faults found by A are found by B as well. Weak normal sits at the bottom; robust worst case at the top, with a hundred-odd test cases for three variables. The question is never which is strongest — it is which is worth its cost.
The three problems equivalence classes leave open
  1. No constraints on the classes. Nothing stops you partitioning badly.
  2. Dependencies between variables are ignored. Age classes here depend on full-time, and the technique has nowhere to say so.
  3. No choice among classes. You cannot apply worst case to one variable and boundary values to another.

Decision tables and classification trees are the answers to these.

Decision tables

The idea
Summarise the logic of the program, rather in the manner of a Karnaugh map: find a few conditions on the input that determine the behaviour, and give the action for each combination. The conditions need not be independent, which is exactly the assumption every earlier technique had to make. Also called cause-effect graph testing or tableau testing.
Stubthe left-hand column: conditions first (most dominating at the top, multi-valued and special cases last), then actions, then exceptions
Entrythe other columns, called rules. Condition entries are true, false, other values, or don't care; action entries mark which actions fire
The completeness check
For independent conditions there must be 2|{cₐ}| rules — or ∏ₐ nₐ when conditions take nₐ values. Each don't care counts for two rules, which is how a handful of columns can cover the whole space.

If the count comes up short, there are input combinations whose behaviour nobody has specified. Those are precisely where faults of omission come from.

Which technique when
The notes close this section with a decision table about decision tables. Reading it off: with physical variables that are independent, use boundary values — robust if exceptions matter, worst case if you cannot assume a single fault. With logical variables, use equivalence classes on the same pattern. And whenever the variables are not independent, the answer is a decision table, whatever else is true.

Classification trees

The steps
  1. Determine the aspects of the specification that influence the logic.
  2. Establish a hierarchy between them — the more global conditions first.
  3. Partition the input domain for each aspect.
  4. Each partition must cover the whole domain of its parent node.

Then a combination table: one test case per relevant combination of inputs. The word relevant is where the judgement goes, and it is what the technique buys you over strong EC's blind product.
The mortgage example as a tree
  1. Salary: −1, [0..10000], >10000
  2. Full time: true, false
  3. Age: too young, young, middle, old, too old — dependent on full-time

That last line is the thing equivalence class testing could not express. The hierarchy lets the age partition differ depending on the branch above it, which is the actual structure of the specification.

Shapes. The hierarchy is the point: "which kind of triangle" only exists under "large" and "triangle".

Conclusions

What the notes conclude
  • Equivalence testing is the basis. Strong variants are often practically infeasible, and robust techniques are very effective for weakly typed languages, where nothing else stops an out-of-range value.
  • Decision tables and classification trees help by summarising the logic and by documenting which methods and test cases are the effective ones.

No perfect technique exists. Consider the domain and how much coverage of the requirements is justified; a classification tree or decision table usually gives the most useful structured overview.

Takeaways

If you remember seven things
  1. Weak normal EC costs maxₓ |Sₓ|, by the token puzzle: one test case covers one class of every variable at once.
  2. Strong normal costs ∏ₓ |Sₓ|; weak robust adds 2n; strong robust is ∏(|Sₓ| + 2).
  3. Weak = single fault assumption, strong = multiple. Robust = out-of-range values included.
  4. BV is 4n+1, robust BV 6n+1, worst case 5ⁿ, robust worst case 7ⁿ.
  5. A → B means A's test cases are a subset of B's, so B finds at least what A finds.
  6. Decision tables drop the independence assumption. Completeness needs 2|conditions| rules, each don't care counting for two.
  7. Classification trees add hierarchy, so one aspect's partition can depend on another's — which is what the mortgage age classes need.
Things that catch people out
  • Adding the class counts for weak normal EC. It is the maximum, not the sum.
  • Applying the robust formulas to a boolean. There is no value just outside {true, false}, so the formula overcounts — the tool shows 96 against 48 for this example.
  • Treating boundary value testing as thorough. On this example it finds anywhere from zero to three faults depending only on the nominal values chosen.
  • Forgetting that don't care counts for two rules when checking completeness.
  • Assuming equivalence classes can express dependency between variables. They cannot; that is what the hierarchy of a classification tree is for.
  • Reading "strong" as "better". It is exponentially more expensive, and the notes call the strong variants often practically infeasible.
