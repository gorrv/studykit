Topic 02 · Pointers and Ownership

But I Miss Typing new

pointers, delete, and the three functions you get for free

Topic 1 said C++ objects can be values. This topic puts new back, and with it the question Java never asks: who frees this? Nothing collects your garbage, so ownership stops being an implementation detail and becomes part of what a class means.

Pointers

The syntax, against Java
// Java
Coordinate a = new Coordinate(4, 3);
System.out.println(a.getX());

// C++
Coordinate * a = new Coordinate(4, 3);
cout << a->getX() << endl;
Coordinate * is a pointer to a Coordinate. -> reaches through it, and is shorthand for (*a).getX(). A Java variable is always something like this pointer — which is why the Java line needs no star, and why everything below has no Java equivalent.
The three operators
string cc is a string
string * bb is a pointer to a string
*bthe string b points at — * dereferences
&ca pointer to c — its address in memory
b->size()the same as (*b).size()

Count stars: * takes one off, & puts one on.
Pointers bring back the two things Topic 1 removed
They can be null. string * s = nullptr; s->size(); compiles and then crashes — the C++ equivalent of a NullPointerException, without the exception. A reference could not have done this.

Comparing them compares addresses. new string("Dave") == new string("Dave") is false, exactly as in Java, because there are two objects at two addresses. Topic 1 said C++ fixes Java’s == trap; this is the case where it does not, because now you are back to comparing handles. *a == *b compares the strings.

new, and the delete that has to follow it

Every new needs a delete
void myFunction() {
  string * s = new string("Hello");
  cout << *s << endl;
  delete s;
}
In Java, an object with nothing pointing at it is collected. In C++ it simply stays, unreachable and unfreed, for as long as the program runs. That is a memory leak: the program’s footprint grows until it exits.
The early return, which is how leaks actually happen
void myFunction(const string & a) {
  string * b = new string("Hello");
  if (a == *b) {
    cout << "was Hello\n";
    return;                  // ← b is never deleted
  }
  cout << "was not Hello\n";
  delete b;
}
Nobody forgets the delete at the end of the function. They forget the one on the path that returns early — and every extra return, break or thrown exception adds a path that has to free everything again. This is the argument for not allocating by hand at all where a vector or a local object will do.
Arrays, and the other delete
int * a = new int[10];
a[i] = i;                  // the same as *(a + i)
delete [] a;               // note the brackets
delete and delete [] are different operators, and using the wrong one is undefined behaviour rather than an error you will be told about. A raw array also has no idea how long it is, which is why printArray(int *, int) has to be handed the length separately and will happily read past the end if you lie to it.

Use vector. It knows its own size, and when it falls out of scope it frees its contents for you — so there is no delete to forget.
operator[] comes in two versions, and const picks one
int & operator[](int idx);                    // on a modifiable vector
const int & operator[](int idx) const;       // on a const one
Returning a reference is what makes numbers[i] += 1; work, where Java needs numbers.set(i, numbers.get(i) + 1). The const version returns a const reference and is the one chosen when the vector is reached through a const vector<int> & — which is why int addNumbers(const vector<int> & toAdd) uses it. Provide only the non-const version and that function stops compiling.

The anatomy of a class

The four the compiler writes for you
default constructorC() only if you write no constructor at all
copy constructorC(const C & other) copies each member
assignment operatorC & operator=(const C & other) assigns each member
destructor~C() destroys each member — and does nothing about pointers

Write any constructor and the free default one disappears; ask for it back with C() {} or, better, C() = default;.
Why the copy constructor takes a const reference
const, because copying something should not change it. Reference, for a sharper reason: if it took its argument by value, then calling it would first have to copy the argument — which would call the copy constructor — which would first have to copy its argument. The signature has to be a reference or it cannot exist.
operator=, and why it returns a reference
SomeClass & operator=(const SomeClass & other) {
  x = other.x;
  y = other.y;
  return *this;
}
b = a; is b.operator=(a);. And c = b = a; is c.operator=(b.operator=(a)); — so whatever the inner call returns is what c is assigned from. Return the object itself and you have made a copy for nothing; return a reference to it and the chain works.

this is a pointer to the current object, so *this is the object — the same dereferencing operator as everywhere else.

Pointers in classes: the Rule of Three

The compiler’s versions of those functions copy each member. When a member is a string *, copying it copies the address — and two objects end up sharing one string that each of them believes it owns.

The class the week is built around
class IHazStringPtr {
private:
  string * str;
public:
  IHazStringPtr() : str(new string()) {}
  void addCharacter(const char c) { str->push_back(c); }
  void printIt() const { cout << *str << endl; }
};
Two separate objects print a and b. But IHazStringPtr b = a; uses the compiler’s copy constructor, which does str(other.str) — and then both print ab, because there was only ever one string.

Leaks, double frees, and which of the three you wrote

Every block of memory is drawn with the objects that point at it. All 36 combinations of these switches are checked against g++ -fsanitize=address in this module’s test suite, so the leaks reported here are the ones that really happen.
A deep copy
// attempt 2 — handles a null pointer
IHazStringPtr(const IHazStringPtr & other) {
  if (other.str == nullptr) { str = nullptr; }
  else { str = new string(*(other.str)); }
}

// attempt 3 — the same, in the initialiser list
IHazStringPtr(const IHazStringPtr & other)
  : str(other.str == nullptr ? nullptr
                             : new string(*(other.str))) { }
new string(*(other.str)) is the whole idea: dereference their pointer to get their string, and construct a new string from it. The third version does it in the initialiser list for the reason Topic 1 gave — the member is built once rather than built and then overwritten.
The assignment operator has one more job
IHazStringPtr & operator=(const IHazStringPtr & other) {
  if (str) delete str;             // ← the object already owned something
  if (other.str) { str = new string(*(other.str)); }
  else { str = nullptr; }
  return *this;
}
A copy constructor builds an object that did not exist a moment ago, so there is nothing to release. An assignment overwrites one that did, and whatever it was holding becomes unreachable the instant you overwrite the pointer. Without that first line the class leaks a string on every assignment.
And that version is still wrong, in a way that is easy to miss
Try a = a; in the tool above with deep, deletes the old selected.

if (str) delete str; frees the string. Then new string(*(other.str)) reads other.str — and other is a, so that pointer is the one just freed. The object reads its own released memory. Compiled with -fsanitize=address this is a hard crash, reported as a use-after-free inside operator=.

The fix is one line at the top:
if (this == &other) return *this;

Self-assignment looks like something nobody writes, and directly it is. It arrives through aliases — v[i] = v[j] where i and j happen to be equal, or two references that turn out to name the same object. Guard for it once and stop thinking about it.
The destructor, and the Rule of Three
~IHazStringPtr() { delete str; }
Runs when the object goes out of scope. Without it, every IHazStringPtr ever created leaks its string — a loop of 10 000 calls leaks 10 000 strings.

The Rule of Three. If a class needs any one of the copy constructor, the assignment operator or the destructor, it almost certainly needs all three, because all three exist for the same reason: the class owns something the compiler does not know how to copy or release. Writing one or two of them is the dangerous state — you have proved the compiler’s versions are wrong for this class, and then left some of them in place.

Takeaways

What to be able to do without thinking
Count stars. * removes one, & adds one, both sides must match.

Pair every new with a delete, on every path out of the function — and delete [] for new [].

Say what the compiler’s copy constructor does to a class holding a pointer, and what that means when both objects are destroyed.

Write the three. Deep copy constructor; assignment operator that deletes the old, deep copies, guards self-assignment and returns *this; destructor that deletes.

Explain why operator= returns a reference — c = b = a — and why the copy constructor’s parameter must be one.
Traps
  • Comparing pointers when you meant to compare what they point at.
  • Forgetting the delete on an early-return path.
  • delete where delete [] was needed.
  • Writing a deep copy constructor and leaving the assignment operator shallow.
  • An assignment operator that deep copies but never frees what it overwrote.
  • Forgetting the self-assignment guard once you do free it.
  • Returning by value from operator=, breaking c = b = a.
  • Assuming a destructor is unnecessary because nothing looks like it is leaking.
The one-sentence version
A pointer says where something is but nothing about who is responsible for it, so the moment a class holds one you have to answer that question yourself — and the three functions the compiler writes for you all answer it wrongly.
