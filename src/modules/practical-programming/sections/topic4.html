Topic 04 · Ownership and Moving

Who Deletes It?

unique_ptr, lvalues and rvalues, move semantics

Topic 2 left you with a rule: every new needs a delete, and getting that right by hand across every early return, exception and branch is a job nobody does perfectly. This topic is the way out. One class holds the pointer and deletes it when it goes out of scope, and the type system is used to guarantee that exactly one thing owns it at a time.

Making that guarantee hold turns out to need a piece of the language that looks unrelated: the difference between a variable and a temporary. Most of this topic is really about that difference, because it is what lets the compiler tell this object is about to be thrown away from this object is still in use — and once it can tell, it can move things instead of copying them.

A pointer that cleans up after itself

The whole idea, in a class
template<typename T>
class unique_ptr {
private:
  T * d;
public:
  unique_ptr(T * dIn) : d(dIn)     {}
  unique_ptr()        : d(nullptr) {}
  ~unique_ptr() { delete d; }

  unique_ptr(const unique_ptr & other)             = delete;
  unique_ptr & operator=(const unique_ptr & other) = delete;

  T & operator*()  const { return *d; }
  T * operator->() const { return d; }
};
Three ideas, and that is the entire class.

1. The destructor deletes. Put one on the stack and the delete happens when it goes out of scope — including when you return early, and including when an exception is thrown past you.
2. Copying is banned. = delete removes a function. If copying were allowed, two objects would hold the same pointer and both destructors would run.
3. It behaves like a pointer. operator* and operator-> are overloaded, so code that used a raw pointer mostly does not notice.
Using it
{
  unique_ptr<Coordinate> c(new Coordinate(3,4));
  cout << *c << endl;
}   // the Coordinate is deleted here
No delete anywhere, and no way to forget one. This is the pattern the rest of modern C++ is built on: a resource is owned by an object, and the object’s lifetime is the resource’s lifetime.
Banning copies breaks something useful
unique_ptr<Coordinate> makeOne() {
  return unique_ptr<Coordinate>(new Coordinate(3,4));
}

int main() {
  unique_ptr<Coordinate> a;
  a = makeOne();      // ???
}
With the class above, this does not compile — the assignment operator is the deleted one. But it obviously should work: the thing on the right is a temporary that is about to be destroyed anyway, so nobody would be left holding a second copy of the pointer.

The real std::unique_ptr accepts it. What it has that the class above does not is an overload for temporaries — and to write one, you need a way to say “this parameter is only ever a temporary”.

Variables and temporaries

The distinction
An lvalue names something that is still there afterwards — a variable, an array element, whatever a reference refers to, anything you could take the address of.
An rvalue is a value that exists only inside the expression it appears in: the result of an arithmetic operation, a literal, whatever a function returns by value.

The names come from where they may appear: 
int a = 3;        // a is an lvalue, 3 is an rvalue
int b = a + 7;    // a + 7 is an rvalue

3 = a;            // error: an rvalue cannot be assigned to
a * 2 = 3;        // error: same reason
The rule that matters is not about assignment, though. It is about references.
What a reference may name
int byValue() { int a = 3, b = 4; return a + b; }

int   y = byValue();   // fine: copy the value out of the temporary
int & y = byValue();   // error
The second line asks for a reference to a temporary that ceases to exist at the semicolon. If it were allowed, y += 7 on the next line would be writing to memory that no longer belongs to anything. So a plain & reference binds only to lvalues.

With a function that returns a reference, the same call is an lvalue and the same line is fine: 
class OneInt {
  int x;
public:
  int & getX() { return x; }
};

OneInt foo;
int & y = foo.getX();   // fine: names foo.x, which still exists
++y;                    // foo.x is now 1
Where this bites in ordinary code
void increment(double & d) { d += 1; }

int main() {
  int x = 7;
  increment(x);   // error
}
Nothing here mentions temporaries, and yet: converting the int to a double produces one, and double & will not bind to it. Which is a mercy — if it did bind, the function would faithfully increment a temporary that is discarded on the next line, and x would never change.

const references are the exception. A const double & binds to that temporary quite happily, and the temporary’s lifetime is extended to match the reference. It is safe precisely because you cannot write through it, so there is no change to lose. This is why so many parameters are const T &: it is the one form that takes everything.
The same trap with an iterator
iterator insert(iterator & position, const T & value);

LinkedList<int> foo;
foo.insert(foo.begin(), 42);   // error
begin() returns an iterator by value, so the argument is a temporary and the non-const reference will not bind. Take the iterator by value or by const reference and the call is fine. Iterators are small; by value is the normal choice, which is why the standard containers do it that way.

Rvalue references

A reference that only takes temporaries
T && is a reference that binds to rvalues and refuses lvalues — the exact opposite of T &. On its own that sounds useless. Its point is what it tells you: whatever you have been handed is about to be destroyed, so you may take it apart. 
unique_ptr & operator=(unique_ptr && other) {
  delete d;               // throw away what we had
  d = other.d;            // take theirs
  other.d = nullptr;      // leave them holding nothing
  return *this;
}
Now a = makeOne(); compiles. The temporary is an rvalue, so this overload is chosen rather than the deleted copy assignment, and the pointer is handed over instead of duplicated. There is still exactly one owner at every moment — which was the point of banning copies in the first place.
The move constructor is the same idea
unique_ptr(unique_ptr && other) : d(other.d) {
  other.d = nullptr;
}
Take the pointer, null out the source. A moved-from object must be left in a state where its destructor is safe to run — here, holding nullptr, which delete is happy with.
Why everyone else gets faster too
vector<int> massiveVector() {
  vector<int> toReturn(1000000);
  return toReturn;
}

vector<int> a;
a = massiveVector();
Without an rvalue-reference overload, the assignment takes a const reference and has to copy: allocate a million ints, copy a million ints, then destroy the original. With one, it takes the pointer to the existing array and nulls the source — a couple of assignments, regardless of size.

Nothing at the call site changed. The overload gets picked automatically because the argument is a temporary, which is why this arrived in C++11 and made existing code faster without anyone editing it.
std::move does not move anything
vector<int> numbers(1000000);
vector<int> a(std::move(numbers));

cout << numbers.size() << endl;   // 0
cout << a.size() << endl;         // 1000000
It is a cast, and nothing else. It takes an lvalue and hands back the same object described as an rvalue, so that overload resolution picks the stealing version. The moving is done by the constructor that gets chosen, not by std::move.

What it costs you is the promise implied by writing it: numbers still exists and is still a valid vector, but you have said you no longer care what is in it. Reading it afterwards is legal and almost always a bug.

The rest of the class

Converting to bool
explicit operator bool() const { return d != nullptr; }
A conversion operator: it says what happens when an object of this type is used where a bool is wanted. So if (p) asks whether the pointer holds anything, exactly as it would for a raw pointer. 
if (foo) { cout << *foo << endl; }
else     { cout << "foo is null\n"; }
The explicit matters. Without it, the conversion applies anywhere a number would do, and p + 1 quietly compiles as true + 1, giving 2. Marked explicit, the conversion is used only where a condition is expected — which is the only place it makes sense.
get, reset, release
callwhat it doeswho owns it afterwards
p.get() hands back the raw pointer still the unique_ptr — do not delete what you get
p.reset(q) deletes what it held, then takes q the unique_ptr, now owning q
p.release() hands back the raw pointer and forgets it. Deletes nothing. you. If you drop it, it leaks
reset and release are the pair people mix up. One frees, the other hands over. release is how you pass ownership out to something that is not a unique_ptr; used by accident it is a straightforward leak.

Getting the compiler to help

Four flags worth knowing
g++ -std=c++11 -Wall -Werror -g -D_GLIBCXX_DEBUG -o exec source.cc
-Wall — ask for the warnings that are off by default. The name means “all” but does not mean all; -Wextra asks for more.
-Werror — turn warnings into errors, so they cannot be scrolled past. Standard on most large projects, and the reason is discipline rather than pedantry: a warning nobody fixes is noise that hides the next one.
-g — keep the information a debugger needs to name your functions and lines.
-D_GLIBCXX_DEBUG — turn on the standard library’s own checking. Indexing a vector past its end, or dereferencing end(), becomes a clear message at the moment it happens instead of a mysterious crash later. It makes the code substantially slower, so it is a development setting, not a shipping one.
The warning everyone meets first
vector<int> numbers(5);
for (int i = 0; i < numbers.size(); ++i) { ... }
size() returns an unsigned type, i is signed, and comparing them is a warning — with -Werror, a build failure. It is not fussing over nothing: if the signed value is negative it converts to an enormous unsigned one and the comparison comes out backwards.

Cast it, for (int i = 0; i < (int) numbers.size(); ++i), or use the matching type, or avoid the question with a range-for.
Too many flags to type
exec: source.cc
	g++ -std=c++11 -Wall -Werror -g -D_GLIBCXX_DEBUG -o exec source.cc
A Makefile gives a target, the files it depends on, and the command to rebuild it. If source.cc is newer than exec, the command runs; otherwise it does not.

The line under the target must begin with a tab. Spaces produce an error that does not mention whitespace, and it is the first thing to check when a Makefile refuses to work.

Takeaways

If you remember five things
  1. An lvalue names something that survives the line; an rvalue does not. & binds only to the first, && only to the second, and const & binds to both — which is why it is everywhere.
  2. An rvalue reference parameter means the argument is expendable, so the function may take its contents rather than copy them. That is all move semantics is.
  3. std::move is a cast. It performs no move. It makes an lvalue look like an rvalue so that the stealing overload is chosen.
  4. unique_ptr deletes what it owns when it goes out of scope, and cannot be copied — only moved. One owner, always.
  5. reset deletes, release hands over. Mixing them up leaks or double-frees.
Things that catch people out
  • Expecting int & r = f(); to work because int r = f(); does.
  • Passing an int to a function taking double & and wondering why it will not compile — the conversion makes a temporary.
  • Reading a variable after std::move. It compiles, and it is empty.
  • Writing operator bool() without explicit, so the object silently takes part in arithmetic.
  • Using release() when you meant reset(), which leaks; or deleting what get() returned, which double-frees.
  • A function returning a non-void type with no return on some path. It compiles by default and is undefined at runtime — one of many reasons for -Wall -Werror.
