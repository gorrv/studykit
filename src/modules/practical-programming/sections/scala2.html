Scala 02 · Functions and Matching

Say What, Not How

higher-order functions, Option, for-comprehensions, pattern matching

Scala 01 took the loops away. This topic is what you use instead. Every loop you were going to write is one of about six shapes — transform each element, keep some of them, find the first one, count them, check them all, combine them — and each shape has a name and takes a function.

Two things fall out of that. Functions become values you can pass around, and the answer "there wasn't one" becomes a value too, with a type that says so.

Functions that take functions

The shapes
def even(x: Int): Boolean = x % 2 == 0

List(1, 2, 3, 4, 5).filter(even)   // List(2, 4)
List(1, 2, 3, 4, 5).count(even)    // 2
List(1, 2, 3, 4, 5).find(even)     // Some(2)
List(1, 2, 3, 4, 5).exists(even)   // true
List(1, 2, 3, 4, 5).forall(even)   // false
List(1, 2, 3, 4, 5).map(n => n * n)  // List(1, 4, 9, 16, 25)
even is passed as an argument, without being called. A function is a value like any other: it has a type — here Int => Boolean — and can be stored, passed and returned.

Note what find gives back. Not the element, and not −1 or null when there isn't one: an Option[Int], which is either Some(2) or None. The type tells you the search might fail before you have written a line.
Writing the function inline
def less4(x: Int) = x < 4    // named
(x: Int) => x < 4             // the same function, anonymous
x => x < 4                    // the type is inferred from the context
_ < 4                         // and the name is not needed either
The underscore stands for the argument, in order. One _ means one parameter; two _s mean two parameters, so _ * _ is (a, b) => a * b and not x => x * x. When you want the same argument twice, write the lambda out.

For-comprehensions

Not a loop
for (n <- List(1, 2, 3, 4, 5)) yield n * n
// List(1, 4, 9, 16, 25)
This looks like a for loop and is not one. It is syntax for map, rewritten by the compiler before anything runs: 
List(1, 2, 3, 4, 5).map(n => n * n)
With a condition, the if becomes a filter. With two generators, the outer one becomes a flatMap. The yield is what makes it produce a result — without it you get Unit and whatever the body did to the outside world.

Option

A value that might not be there, in the type
List(7, 2, 3, 4, 5, 6).find(_ < 4)   // Some(2)
List(5, 6, 7, 8, 9).find(_ < 4)      // None
An Option[Int] is either Some(n) or None. That is the whole type — two cases, and the compiler knows about both.

Compare the alternatives. A sentinel like −1 is a real Int, so nothing stops you adding it to something. A null has the same type as a real value, so the compiler cannot see the difference and the mistake arrives later, somewhere else, as a NullPointerException. An Option[Int] is a different type from Int, so the one place you must think about emptiness is the place that knows what to do about it.
Where this bites first: parsing
"1234".toInt          // 1234
"12x".toInt           // throws NumberFormatException
"  12".toInt          // throws — no trimming
"2147483648".toInt    // throws — does not fit in an Int

"12x".toIntOption     // None
"1234".toIntOption    // Some(1234)
toInt is Integer.parseInt, and its failure is an exception that the signature does not mention. toIntOption puts the failure in the type instead, so it cannot be forgotten.
Four ways to get at what is inside
callwhat it does
o.getOrElse(d)the value, or d when empty
o.map(f)applies f only when there is something; still an Option
o match { … }handles both cases, visibly
o.getthe value, or a NoSuchElementException
The last one throws away everything the type bought you. It exists, and reaching for it is almost always a sign that the wrong one of the other three was skipped.

Map, the data structure

Not the method
val ascii = ('a' to 'z').map(c => (c, c.toInt))
val ascii_map = ascii.toMap

ascii_map.get('a')        // Some(97)
ascii_map('a')            // 97
ascii_map.get('A')        // None
ascii_map('A')            // throws NoSuchElementException
map the method transforms every element; Map the type is a key-value store. The example above uses both in two lines, which is unfortunate and worth being clear about.

get returns an Option, not the value — a missing key is exactly the case Option is for. Applying the map directly, ascii_map('a'), gives the value and throws when the key is absent. Two different calls for two different situations: use get when the key might not be there, and say what to do about it.

Pattern matching

More than a switch
def fizz_buzz(n: Int): String =
  (n % 3, n % 5) match {
    case (0, 0) => "fizz buzz"
    case (0, _) => "fizz"
    case (_, 0) => "buzz"
    case _      => n.toString
  }
The thing being matched is a pair, and the patterns take it apart. A switch compares one value against constants; this matches the shape of a structure and binds the pieces at the same time.

Cases are tried in order and the first match wins. For n = 15 all four patterns above would match, and only the first gets to. That is why the specific cases go first, and why case _ at the top makes everything below it dead code.
What you can match on
case 3                 // a literal
case (a, b)            // a tuple, binding both halves
case Nil               // the empty list
case h :: t            // a non-empty list, binding head and tail
case List(a, b)        // a list of exactly two
case Some(v)           // an Option that has something, binding it
case None              // one that does not
case x if x > 10       // a guard
case _                 // anything
A lowercase name in a pattern binds — it does not compare against a variable of that name. This catches everyone once: case n => … matches anything and shadows the n you meant to compare with.

Recursion

Matching and recursion fit together
def my_flatten(xs: List[Option[Int]]): List[Int] =
  xs match {
    case Nil             => Nil
    case None :: rest    => my_flatten(rest)
    case Some(v) :: rest => v :: my_flatten(rest)
  }
Three cases, three lines, no index and no accumulator. The list is either empty — and then the answer is obvious — or it has a head and a tail, and the head is either something or nothing. Every case of the input has a case in the code, which is what makes it hard to get wrong.
Right, and still the wrong shape
def fib(n: Int): Int = {
  if (n == 0 || n == 1) 1
  else fib(n - 1) + fib(n - 2)
}
A direct transcription of the definition, and correct. It is also exponential — the two calls recompute the same values over and over. The tool below counts the calls rather than estimating them.

Note the indexing too: this gives 1 for both 0 and 1, so it is shifted by one from the sequence that starts 0, 1, 1, 2, 3.

Takeaways

If you remember five things
  1. Functions are values. filter, map, find, count, exists, forall take one, and between them replace nearly every loop.
  2. A for-comprehension is syntax for map — with if becoming filter and a second generator becoming flatMap. Without yield it produces nothing.
  3. Option puts "there might be nothing" in the type, where the compiler can see it. find and Map.get both return one.
  4. Cases are tried in order; the first match wins. Specific first, case _ last.
  5. A lowercase name in a pattern binds rather than compares.
Things that catch people out
  • Expecting find to return the element. It returns an Option.
  • Expecting Map.get to return the value. Same.
  • _ * _ when you meant x => x * x.
  • Forgetting yield, and getting Unit.
  • Putting case _ before the cases that do the work.
  • Reaching for .get on an Option to make the types line up.
