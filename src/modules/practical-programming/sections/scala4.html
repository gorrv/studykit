The Order Is the Answer

reverse Polish notation, stack machines, and what backtracking costs

Two things that look unrelated and are the same idea twice. Turning an expression into reverse Polish notation makes the brackets unnecessary, because the order already says what they said — and once the order says it, the translation to machine instructions is a substitution. Then the same question about regular expressions: if the pattern can be turned into the right shape in advance, matching stops needing to guess.

Reverse Polish notation

The same expression, without brackets
(3 + 1) * (2 + 9)
⇒  3 1 + 2 9 + *
Every operator comes after the two things it operates on. There are no brackets and no precedence rules, and there is nothing to disambiguate: the order is the only information and it is enough.

Reading it is a stack. A number goes on; an operator takes two off and puts one back. When the input runs out there is exactly one value left, and that is the answer — and if there is not exactly one, the expression was malformed.
Getting there: the shunting-yard
Read the infix expression left to right. Numbers go straight to the output. An operator waits on a stack until something of at least its own precedence needs to come off, then both go out in the right order. Brackets push and pop.

That is the whole conversion, and it is where the precedence and the brackets are spent: the output has neither, because the order now carries what they meant.
And then it is already machine code
(3 + 1) * (2 + 9)      ldc 3
                        ldc 1
⇒  3 1 + 2 9 + *        iadd
                        ldc 2
                        ldc 9
                        iadd
                        imul
A number becomes ldc — load constant — and an operator becomes the instruction that pops two and pushes one. That is a one-to-one substitution, which is the point: all the work was done by the conversion.

The JVM is a stack machine, so this is close to what a real compiler emits for arithmetic. There is no cleverness left in the last step because the notation already removed the need for it.

What backtracking costs

A pattern, and a string with no b in it
(a*)*b        matched against     aaaaaaaaaaaaaaaaaaaa
The answer is no — there is no b, so nothing can match. The question is how long it takes to say so.

Most regular expression engines work by trying: let the star take some characters, try to match the rest, and if that fails, come back and take a different number. Here the outer star can divide a run of n a's between its repetitions in exponentially many ways, and every one of them has to fail before the engine will admit there is no b.
This is not a Scala problem, and it is not hypothetical
Java, Python, JavaScript, Ruby and most others use backtracking engines and all behave this way on this pattern. The tool below measures your own browser's engine doing it, in this tab, right now.

A pattern like this reachable from user input is a way to take a server down with a twenty-character string. It has a name — ReDoS — and it is common enough to have a CVE category.
The alternative: rewrite the pattern as you read
Instead of trying alternatives, ask a different question at each character: given this pattern, what pattern would be left after consuming an a? That is the derivative of the pattern, and it is computed rather than searched.

Walk the input once, rewriting as you go, and at the end ask whether the pattern that is left can match the empty string. There is no backtracking because nothing was ever guessed — one pass, one step per character, for any pattern.

The catch is that the rewritten pattern grows unless you simplify it, and the simplification rules are what make this practical: ∅r = ∅, εr = r, ∅ | r = r, and collapsing two identical alternatives.

Why this is the same idea as the RPN half
In both cases the fix is to do the thinking in advance. The shunting-yard spends the brackets and precedence once, so the machine that runs the result can be stupid. The derivative spends the pattern's ambiguity once per character, so the matcher never has to guess and come back.

The next topic is what you get if you push that all the way: work out every state the pattern could be in before seeing any input at all, and matching becomes a table lookup per character.

Takeaways

If you remember five things
  1. RPN needs no brackets because the order carries the same information. Evaluate it with a stack: numbers push, operators pop two and push one.
  2. The shunting-yard converts infix to RPN — numbers straight out, operators wait on a stack until something at least as tight comes off.
  3. RPN to stack-machine code is a substitution, which is why the conversion was worth doing.
  4. A backtracking matcher can take exponential time on a pattern with nested ambiguity, such as (a*)*b, even to answer no.
  5. Derivatives answer the same question in one pass, at the cost of rewriting and simplifying the pattern as you go.
Things that catch people out
  • Writing the RPN operands in the wrong order for - and /, which unlike + and * do not forgive it.
  • Expecting the stack to end with one value when the expression was malformed.
  • Assuming a slow regex means a big input. Twenty characters is enough.
  • Assuming the star is the problem. (a*)b is linear; the nesting is what costs.
  • Forgetting to simplify when computing derivatives, and trading an exponential search for an exponential pattern.
