Topic 03 · Templates and the STL

Write It Once, For Any Type

templates, containers, iterators, function objects and maps

Weeks 1 and 2 were about one object at a time. This week is about the machinery for holding many of them, and about writing code that does not care what type it holds. Java reaches for generics and Object; C++ generates a separate copy of your code for each type, which is why it costs nothing at runtime and why the error messages are so long.

Templates

From two classes to one
template<typename T>
class template_array {
private:
  T * elements;
  int arraySize;
public:
  template_array(const int s) : elements(new T[s]), arraySize(s) {}
  ~template_array() { delete [] elements; }
  T & operator[](const int idx) { return elements[idx]; }
  int size() const { return arraySize; }
};
Everywhere int appeared, put T. The template argument is part of the type:
template_array<int> a(10); and template_array<double> b(5); are two unrelated types, and the compiler generates the class separately for each.
Two of the standard ones
std::pair<A, B> holds two values, first and second — the usual way to return two things at once.
std::tuple<A, B, C, …> holds any number.
The slide reads a tuple the wrong way
Slide 8 prints ans.get<0>(). A tuple has no member called get, and that line does not compile. The accessor is a free function template:

std::get<0>(ans)

The index has to be a compile-time constant, because the type of what comes back depends on it — get<0> and get<2> have different return types, so it could never be an ordinary runtime argument. That is also why there is no ans[i].

The Standard Template Library

What is in it
The C++ standard splits into the core — syntax and language features — and the standard library, of which the STL is the container and algorithm part. It is optional, in the sense that you reach it through #include, and you should essentially always use it.

Looping, auto, and iterators

The range-for, and the three ways to take the element
for (int & item : p)          // modify the container's elements
for (const int & item : p)    // read them, no copy
for (int item : p)            // a copy of each — changes go nowhere
for (auto & item : p)        // whatever the element is, by reference
auto works out the element type for you, and picks up const when the container is const. That is not just less typing: it is the version that keeps compiling when the container’s element type changes.
Iterators
vector<int>::iterator itr = a.begin();
cout << *itr << endl;    // dereference, as with a pointer
++itr;                    // move to the next element
:: names a type defined inside a class, the way Java writes BorderLayout.NORTH. An iterator is a pointer in disguise — for a vector it genuinely wraps a T *, with operator* and operator++ written to do the obvious things.

end() points past the last element. For a vector of size 10 the elements are 0 to 9 and end() is position 10. It exists to be compared against; dereferencing it is undefined behaviour. 
for (auto itr = a.begin(), e = a.end(); itr != e; ++itr)
Note != rather than <: not every iterator supports ordering, but they all support comparison for equality.
There is no magic in the range-for
for (int & element : a) is the loop above, written out by the compiler. Anything with a begin() and an end() can be used with it — standard containers, and any class of your own that provides them.

Iterators, insert, erase and find

Each row is the container after one operation, with the iterators drawn where they point. The things worth being certain about are what insert and erase return.
insert, erase and find
insert puts the new element before the iterator and returns an iterator to what it inserted.
erase removes what the iterator points at and returns an iterator to what is now in that position — what used to be next. That return value is what makes itr = c.erase(itr); the correct way to remove inside a loop; incrementing after an erase uses an iterator that no longer means anything.
find returns end() when there is no match. Compare against end() before dereferencing.

Vector iterators support begin() + 2, because the elements are contiguous and that is arithmetic. List iterators do not — a list is nodes joined by pointers, so you have to walk it.

Template functions and function objects

A function that takes any type
template<typename T>
const T & max(const T & a, const T & b) {
  if (a < b) { return b; } else { return a; }
}
Call it as max<int>(a, b), or just max(a, b) and let type deduction work T out from the arguments. Note the requirement hiding in the body: whatever T is, it must support <.
Only one operator< per type — so pass the comparison in
class LTByRange {
public:
  bool operator()(const Car & a, const Car & b) const {
    return (a.getRange() < b.getRange());
  }
};
A class with operator() is a function object, and comp(a, b) is comp.operator()(a, b). It can be passed like a value and called like a function — so a template can take the comparison as a parameter: 
template<typename T, typename Comp>
const T & max(const T & a, const T & b, Comp comp) {
  if (comp(a, b)) { return b; } else { return a; }
}

Car highestRange = max(a, b, LTByRange());
Both T and Comp are deduced. A function object can also carry state, which a plain function pointer cannot — that is the reason the STL is built around them.

std::map

How it works
A map is an associative container built as a binary search tree indexed by key. Each node’s left subtree holds smaller keys and its right subtree larger ones, so the map needs to be able to say when one key is less than another. By default it uses <, through a function object: 
template<typename T>
class less {
public:
  bool operator()(const T & lhs, const T & rhs) const { return (lhs < rhs); }
};

template<typename K, typename V, typename Comp = less<K> >
class map { protected: Comp comp; ... };
Supply your own as the third argument when < is not what you want: map<SomeClass, int, SomeClassLT> myMap;
Looping over a map — the slide’s version does not compile
Slide 61 writes: 
for (pair<int,string> & elem : kNumbers)   // ✗
A map element is a pair<const int, string>. The key is const because the tree is ordered by it — changing a key in place would leave the map sorted wrongly, with no way to notice. So there is no pair<int, string> for that reference to bind to.

Any of these work: 
for (auto & elem : kNumbers)                          // ✓ and the usual choice
for (const pair<const int, string> & elem : kNumbers) // ✓ the full type
for (pair<int,string> elem : kNumbers)                // ✓ but copies each element
This is exactly the case auto exists for, and the slides recommend it nine slides earlier.
Getting things in and out
kNumbers.insert(pair<int,string>(1194384, "Andrew"));  // build a pair, then copy it in
kNumbers.emplace(1194384, "Andrew");                     // forward the arguments, build in place
insert takes a finished pair and the map copies it into a node. emplace takes the pieces and hands them straight to the node’s constructor, so no temporary pair is built and copied. That is perfect forwarding, and vector::emplace_back(4, -2) is the same idea against push_back(Coordinate(4, -2)).
Adding a key that is already there does nothing
Not “overwrites” — nothing. Both insert and emplace return a pair<iterator, bool>:
first — an iterator to the element with that key, new or existing
second — true if it was actually inserted 
auto result = kNumbers.emplace(1194384, "Andrew Coles");
cout << result.second << endl;              // 0 if the key was already there
result.first->second = "Andrew Coles";       // force the value anyway

kNumbers[1194384] = "Andrew Coles";          // ...or just this
operator[] does overwrite, and creates the entry when it is missing — which is also why m[k] is not available on a const map.

Takeaways

What to be able to do without thinking
Turn a concrete class into a template. Replace the type with T, add template<typename T>, remember the argument is part of the type.

Say what T is deduced to be, and why two different argument types make deduction fail rather than convert.

Write an iterator loop with begin(), != end() and ++, and say what end() is.

Know what insert and erase return, and why erase’s return value is what lets you remove inside a loop.

Write a function object — a class with operator() — and pass it to a template as a comparator.

Loop over a map correctly, and say why the element type has a const key.
Traps
  • tuple.get<0>() — it is std::get<0>(tuple).
  • pair<int,string> & when looping a map. The key is const.
  • Expecting deduction to promote int and double to a common type.
  • Dereferencing end(), or using find’s result without checking it first.
  • ++itr after erase(itr). Use the returned iterator.
  • begin() + 2 on a list.
  • Expecting insert or emplace to overwrite an existing key.
  • Forgetting that a container’s operator< requirement means your class needs one before it can be a set element or a map key.
The one-sentence version
A template is a recipe the compiler follows once per type you use it with, and the STL is that idea applied to every container and algorithm you would otherwise write badly yourself — with iterators as the common language that lets any algorithm work on any container.
