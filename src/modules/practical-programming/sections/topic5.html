Topic 05 · Inheritance

Base Classes, and What It Costs

virtual functions, object layout, slicing, and the four casts

Inheritance in C++ looks like inheritance in Java for about ten lines, and then stops. The differences all come from one decision: a C++ object is a lump of memory, not a reference to one. Once you know what that lump looks like, everything else in this topic — why a function call can pick the wrong body, why copying an object can silently lose half of it, why there are four different casts — follows from it.

Deriving a class

The syntax, next to the Java you know
class Bikes : public Coordinate {
protected:
  int howMany;
public:
  Bikes(const int xIn, const int yIn, const int howManyIn)
    : Coordinate(xIn, yIn),      // instead of super(xIn, yIn);
      howMany(howManyIn)
  {}

  void printDetails() {
    Coordinate::printDetails();  // instead of super.printDetails();
    cout << ": " << howMany << " bikes";
  }
};
: public Coordinate instead of extends. The base is constructed in the initialiser list, not in the body — by the time the body runs the base is already built. And the base version of a function is reached by naming it, Coordinate::printDetails(), since there is no super.
public, protected, private members
private members are the base class’s own business and a derived class cannot touch them. protected means the derived class can. Use protected sparingly: it is part of your interface to every subclass anyone ever writes, and just as hard to change later as a public member.

The object in memory

One member after another, base first
An object is its members laid out in order, and a derived object is the base object followed by the new members. So sizeof(Coordinate) is 8 — two ints — and sizeof(Bikes) is 12.

This is why a Bikes * converts to a Coordinate * for nothing: the first eight bytes of a Bikes are a valid Coordinate. The conversion changes the type, not the address.

Which function runs

This is the surprise
void someFunction(Coordinate & c) {
  c.printDetails();
  cout << endl;
}

int main() {
  Bikes strand(20,10,100);
  strand.printDetails();   // 20,10: 100 bikes
  cout << endl;
  someFunction(strand);    // 20,10
}
The same object, the same function name, two different answers. Inside someFunction, c is declared Coordinate &, so the compiler resolves the call to Coordinate::printDetails and fixes that address at compile time. It never looks at what the object really is.

In Java every method is virtual and this cannot happen. In C++ it is the default, because it is faster and because you only pay for what you ask for.
Asking for the Java behaviour
class Coordinate {
public:
  virtual void printDetails() { ... }
  virtual ~Coordinate() {}
};

class Bikes : public Coordinate {
public:
  void printDetails() override { ... }
};
virtual on the base class function means: decide at run time, from what the object really is. Once the base declares it virtual, every override is virtual too, whether or not it says so.

override is optional and worth writing anyway. It asks the compiler to check that you really are overriding something — so a typo in the name, or a parameter type that does not quite match, becomes an error instead of a second, unrelated function that never gets called.
If you inherit, make the destructor virtual
Coordinate * c = new Bikes(3,4,100);
delete c;   // which destructor?
The same rule applies to destructors, and here getting it wrong leaks. With a non-virtual destructor, delete c runs ~Coordinate only — the Bikes part is never destroyed, so anything it owned is lost.

The rule of thumb: if a class has any virtual function, give it a virtual destructor. If it has one it is meant to be inherited from, and if it is meant to be inherited from someone will eventually delete a derived object through a base pointer.
Abstract classes
virtual void printDetails() = 0;
= 0 makes the function pure virtual: declared, not defined. A class with one cannot be instantiated, and neither can a derived class that has not implemented it. There is no abstract keyword — the = 0 is the whole mechanism, and an interface is simply a class where every function is pure virtual.

Static and dynamic dispatch

One object, one call, four ways of naming it. The interesting cases are the ones where the declared type and the real type differ.

Objects, not references

What does this do?
Coordinate c = Bikes(3,4,100);
In Java the equivalent line stores a reference and the object stays a Bikes. Here c is a Coordinate — eight bytes of it — and the Bikes is copied into that space. Only the Coordinate part fits, so only the Coordinate part is copied. The howMany is gone.

It compiles without a murmur, and afterwards c is a genuine Coordinate: even with virtual, the base version of every function is what runs. This is slicing, and it is why polymorphic code passes Base & or Base * and never Base.
Holding a mixture of derived types
vector<Coordinate> v;                    // sliced: each element is a Coordinate
vector<Coordinate *> v;                  // works, but who deletes them?
vector<unique_ptr<Coordinate> > v;       // works, and cleans up
A vector<Coordinate> is that many Coordinate objects end to end, so there is nowhere for a Bikes to live. Pointers solve that — every element is eight bytes and the objects live elsewhere — at the cost of putting you back in charge of deleting them. A vector of unique_ptr gives you both: derived objects, and destruction handled when the vector goes. 
vector<unique_ptr<Coordinate> > c;
c.emplace_back(new Bikes(3,4,100));
push_back wants a unique_ptr and you have a raw pointer; the conversion is explicit, so it is refused. emplace_back constructs the element in place from the arguments you give it, which is exactly what is needed here.

How virtual functions work

A hidden first member
Each class with virtual functions gets a vtable: a small array holding the address of each virtual function for that class. Coordinate’s table points at Coordinate::printDetails; Bikes’ table points at Bikes::printDetails.

Every object of such a class carries a hidden extra member — a pointer to its class’s table — placed first, before your own members. A virtual call reads the address from the table and jumps there, so the answer depends on the object rather than the declaration.

That is the whole mechanism, and it explains the numbers: an object with virtual functions is eight bytes bigger, and a virtual call is one indirection slower than a direct one.
You only pay for what you use
This is the design principle the language keeps returning to. Virtual dispatch is not free, so it is not the default; a class with no virtual functions has no vtable pointer and its objects are exactly as big as their members. The trade is that you have to know to ask.

The four casts

Why four rather than one
C-style (Bikes *) p does whichever of these will work, without saying which, and cannot be searched for. The four named casts each do one thing, and the compiler can refuse the ones that make no sense.
castchecksif it cannot
static_cast at compile time, that the types are related does not compile
dynamic_cast at run time, what the object really is nullptr, or throws for references
const_cast that const is the only difference does not compile
reinterpret_cast nothing whatsoever it never refuses
dynamic_cast is instanceof and the cast together
void someFunction(Coordinate * c) {
  Bikes * b = dynamic_cast<Bikes*>(c);
  if (b) {
    cout << b->howMany << endl;
  } else {
    cout << "not a Bikes" << endl;
  }
}
At run time it compares the object’s vtable pointer with the one Bikes objects have. Two consequences worth remembering: it needs a vtable, so a class with no virtual functions cannot be the source of one — that is a compile error, not a failed cast; and for references it throws std::bad_cast, since a reference has no null to return.
static_cast down does not check anything
Bikes * b = static_cast<Bikes*>(c);   // compiles whatever c points at
The compile-time check is only that Bikes is derived from Coordinate. Whether c points at one is your problem, and if it does not, reading b->howMany reads whatever memory happens to follow. Use it when you already know; use dynamic_cast when the point is to find out.

Pick the cast

Eight situations. Some of them have a right answer that is not a cast at all.

Inheriting from more than one class

Allowed, and it moves the address
class Bikes : public Coordinate, public StreetAddress {
  ...
  Bikes(int xIn, int yIn, const string & pc, int n, int howManyIn)
    : Coordinate(xIn, yIn), StreetAddress(pc, n), howMany(howManyIn)
  {}
};
The base subobjects are laid out in the order they are listed, then the new members. Only the first base can start at offset zero, so: 
Bikes * b = new Bikes(...);
Coordinate * c = b;      // same address
StreetAddress * a = b;   // b plus the size of the Coordinate part
The compiler adjusts the pointer silently, and adjusts it back when you cast the other way. The offset depends on the exact layout — add a virtual function to the first base and every later offset moves by eight — which is a reason to let the compiler do this arithmetic and never do it yourself.
The two questions it raises
Both bases have a function with the same name. Naming it is ambiguous and the compiler stops. Say which you meant: b.Coordinate::describe().

D inherits from B and C, which both inherit from A. By default a D contains two A subobjects, so d.v is ambiguous and d.B::v and d.C::v are different variables. Writing class B : virtual public A makes the A shared, so there is one — at the cost of a more complicated layout, since the shared base can no longer sit at a fixed offset.

This is the complication Java avoided by allowing only one base class, and giving interfaces no data to duplicate.

Takeaways

If you remember five things
  1. Without virtual, the declared type decides which body runs. The object’s real type is never consulted. This is the opposite of Java and the source of most surprises.
  2. A vtable pointer is a hidden first member, added to every object of a class with virtual functions. Eight bytes per object, one indirection per call.
  3. Copying a derived object into a base variable slices it. No warning. Pass references or pointers.
  4. If a class has virtual functions, give it a virtual destructor, or deleting through a base pointer will not destroy the derived part.
  5. dynamic_cast asks, static_cast assumes. The first costs a run-time check and needs a vtable; the second costs nothing and is undefined if you are wrong.
Things that catch people out
  • Forgetting virtual and concluding that C++ dispatch is broken.
  • vector<Base> when the elements are derived — every one is sliced.
  • Deleting through a base pointer with a non-virtual destructor.
  • Using the result of dynamic_cast without checking it for null.
  • dynamic_cast on a class with no virtual functions — a compile error about the source not being polymorphic.
  • Assuming a base pointer and a derived pointer to the same object print the same address. With multiple inheritance, not always.
  • Constructing a base in the constructor body rather than the initialiser list — by then it has already been built, with whatever constructor took no arguments, and if there is not one the code will not compile.
