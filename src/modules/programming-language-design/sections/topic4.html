Topic 04 · Imperative Languages — Structural Operational Semantics

Induction, Small-Step & Big-Step

the answer to the abstract machine's disadvantage

Topic 03 ended with a complaint: the abstract machine works, but "many transitions are doing just phrase analysis; only a few really perform computations." This topic gives the alternative — an operational semantics where the execution of programs is defined by induction.

Aims & structure
  1. Understand the use of induction to specify transition systems and prove properties of programs.
  2. Give alternative definitions of SIMP's operational semantics using induction.

Three parts: revision of induction → small-step semantics (a reduction relation) → big-step semantics (an evaluation relation).

Part 1 · The principle of mathematical induction

The principle
For any property P(n) of natural numbers (n ∈ ℕ = {0, 1, 2, …}), to prove ∀n ∈ ℕ. P(n) it is sufficient to show:
  • Base case: P(0)
  • Induction step: ∀n ∈ ℕ. P(n) ⇒ P(n + 1)

The worked example: for all natural numbers n,  Σi=1..n (2i − 1) = n².

Base case
0 = 0²
Induction step
Assume  Σi=1..n (2i − 1) = n²
Σi=1..n+1 (2i − 1)  =  Σi=1..n (2i − 1) + 2(n + 1) − 1  =  n² + 2n + 1  =  (n + 1)²

Structural induction

Induction generalises from numbers to structures. First, lists. We denote an empty list by nil, and a non-empty list by cons(h, l) where h is the head element and l is the tail.

Structural induction on lists
To prove that a property P holds for every list, it is sufficient to prove:
  • Base case: P(nil)
  • Induction step: P(l) ⇒ P(cons(h, l)) for all h, l
Structural induction on finite labelled trees — the general form
More generally, for finite labelled trees, to prove a property P it is sufficient to show:
  • Base case: P(l) for all leaf nodes l
  • Induction step: for each tree constructor c (with n ≥ 1 arguments):
    ∀t₁, …, tₙ. P(t₁) ∧ … ∧ P(tₙ) ⇒ P(c(t₁, …, tₙ))
Why this is exactly the shape of a SIMP grammar
Look back at Topic 03: the leaves of a SIMP tree are ℤ ∪ {True, False} ∪ L ∪ {skip}, and the non-leaves are operators and commands. So the abstract syntax hands you the base cases and the induction steps — one base case per leaf kind, one induction step per constructor. The grammar is the induction principle. That is the deepest idea of the topic and it's why abstract syntax was set up as trees in Topic 01.

Example: proving a property of SIMP integer expressions

To prove that a property P holds for all integer expressions in SIMP:

1 · Base case
Prove P(n) for all n ∈ ℤ
Prove P(!l) for all locations l
2 · Induction step
For all integer expressions E, E′ and operators op:
Prove that P(E) and P(E′) implies P(E op E′)
Remark: why structural induction is legitimate
The principle of structural induction can be justified by the principle of mathematical induction. This is because we work with finite trees, so we can understand structural induction as induction on the size of the tree.

Formally: let P′(n) be the property "for all expressions E of size at most n, P(E) holds". Then ∀E. P(E) is equivalent to ∀n. P′(n) — and the latter is ordinary mathematical induction.

Application: expressions with defined locations always have a value

There is a real theorem about SIMP behind this machinery. Informally:

The property, in words
The semantics of SIMP guarantees that for any integer expression E appearing in a program working on a memory m, if E uses locations that are defined in m then the value of E is defined.

In other words: for any configuration ⟨E · c, r, m⟩ where c is any arbitrary control stack and r is also arbitrary, there is a configuration ⟨c, n · r, m⟩ such that ⟨E · c, r, m⟩ →* ⟨c, n · r, m⟩.

Formally, we prove ∀E. P(E) where P is:

∀m. locations(E) ∈ dom(m) ⇒ ∃n. ∀c. ∀r. ⟨E · c, r, m⟩ →* ⟨c, n · r, m⟩

This is proved by induction on the structure of E:

Base case
If E is a number n or !l, then the transitions for constants and locations prove P(E).
Induction step
Assume P(E₁) and P(E₂) hold; we have to prove P(E₁ op E₂).
⟨(E₁ op E₂) · c, r, m⟩  →  ⟨E₁ · E₂ · op · c, r, m⟩
    →* ⟨E₂ · op · c, n₁ · r, m⟩   for some n₁, by P(E₁)
    →* ⟨op · c, n₂ · n₁ · r, m⟩   for some n₂, by P(E₂)
    →* ⟨c, n · r, m⟩   where n = n₁ op n₂
Notice what the "∀c. ∀r." is doing
This is precisely the Topic 03 observation that expression evaluation leaves the rest of the stacks alone, now stated as a formal property and used as an induction hypothesis. Because P(E₁) holds for any control stack, we can instantiate it with the stack E₂ · op · c — which is exactly what the second line of the induction step does. Without the universal quantifiers the proof wouldn't go through.

Inductive definitions: axioms and rules

Induction isn't only a proof method — we can also use it to define subsets of a given set T. Inductive definitions are written using axioms (the base case) and rules (the induction step).

Definition
An axiom is an element of T.
A rule is a pair (H, c) where
  • H is a non-empty subset of T, called the hypotheses of the rule
  • c is an element of T, called the conclusion of the rule

The subset I of T inductively defined by a collection of axioms A and rules R consists of those t ∈ T such that:

  • t ∈ A, or
  • there are t₁, …, tₙ ∈ I and a rule (H, c) such that H = {t₁, …, tₙ} and t = c.

To show that an element t of T is in I, it is sufficient to show that t is an axiom, or that there is a proof — a tree whose leaves are axioms and where for each non-leaf node tᵢ there is a rule ({tᵢ₁, …, tᵢₘ}, tᵢ). This kind of proof is usually written with horizontal lines:

⋮
⋮
t₁
…
⋮
tₙ
t

Rule induction

Once a set is defined by axioms and rules, we get a matching induction principle for free.

Principle of rule induction
Let I be a set defined by induction with axioms and rules (A, R). To show that P(i) holds for all i ∈ I, it is sufficient to prove:
  • Base case: ∀a ∈ A. P(a)
  • Induction step: ∀({h₁, …, hₙ}, c) ∈ R.  P(h₁) ∧ … ∧ P(hₙ) ⇒ P(c)

Example: each integer expression in SIMP has a unique value under the evaluation relation ⇓.

Basis
Trivial, since numbers have unique values.
Induction step
For non-atomic expressions, we remark that the value of an arithmetic expression is uniquely determined by the values of its arguments, which are unique by the induction hypotheses.
Special principle of rule induction
In some cases we are only interested in proving a property for a subset J of the inductive set I defined by (A, R). To prove that Q(x) holds for all elements of J, it is sufficient to show:
  • Basis: ∀a ∈ (A ∩ J). Q(a)
  • Induction step: for all (H, c) ∈ R such that c ∈ J:  (∀h ∈ H ∩ J. Q(h)) ⇒ Q(c)

Note the two intersections with J: you only have to handle the axioms that are in J, and for rules you only get to assume the property for those hypotheses that are in J. It's the ordinary principle, restricted.

Three induction principles — keep them straight
  • Mathematical induction — over ℕ. Base P(0), step P(n) ⇒ P(n+1).
  • Structural induction — over the syntax (lists, trees, SIMP expressions). One base case per leaf, one step per constructor.
  • Rule induction — over a set defined by axioms and rules (like the relation ⇓ or →). One base case per axiom, one step per rule.

A question saying "prove by induction on the structure of E" wants the second; "prove by rule induction" or "prove for all derivations" wants the third.

The bridge to the rest of the topic
There are two styles of structural operational semantics:
  • Small-step semantics: defined using a reduction relation.
  • Big-step semantics: defined using an evaluation relation.

Part 2 · Small-step semantics: configurations

We define a transition system with configurations

⟨P, s⟩

where P is a SIMP program and s is a store (memory) represented by a partial function from locations to integers.

Compare with the abstract machine — the configuration got smaller
Topic 03 used a triple ⟨control, results, memory⟩ with two explicit stacks. Here a configuration is just a pair: the program itself, and the store. There are no stacks — the remaining work is represented by the program text that is left. Each transition rewrites the program into a slightly-more-evaluated program.

Notation: s[l ↦ n] denotes the function s′ that coincides with s except that it associates to l the value n:

s[l ↦ n](l) = n
s[l ↦ n](l′) = s(l′)    if l ≠ l′
The transition relation, and what counts as a result
The transition relation → on configurations is inductively defined by the axioms and rules below.
  • The expression E has the value n in the memory state s if ⟨E, s⟩ →* ⟨n, s′⟩.
  • The command C has a successful execution in the memory state s if ⟨C, s⟩ →* ⟨skip, s′⟩. We say that C in s produces s′.

Note the shift: in Topic 03 success meant empty stacks; here it means the program has been rewritten into the value itself — into a numeral, a boolean, or skip.

The pattern — and where evaluation order is hiding
Each operator gets an axiom (both operands are already values → compute) plus congruence rules (an operand isn't a value yet → reduce it in place).

The L rule has a general E₁ on the left; the R rule requires n₁ — an already-evaluated left operand. That single detail forces left-to-right evaluation: you may only start on E₂ once E₁ has become a value. This is the formal answer to the f(i++, --i) problem from Topic 03 — the rules leave nothing unspecified.

Worked example: !z + 1

Let s be a state such that s(z) = 0 and let E = !z + 1. The expression E evaluates to 1 in s, since

⟨!z + 1, s⟩ → ⟨0 + 1, s⟩ → ⟨1, s⟩

Each of those two arrows needs a proof:

⟨!z, s⟩ → ⟨0, s⟩

⟨!z + 1, s⟩ → ⟨0 + 1, s⟩
Second step

⟨0 + 1, s⟩ → ⟨1, s⟩

The while rule is the star of this topic
⟨while B do C, s⟩ → ⟨if B then (C ; while B do C) else skip, s⟩

It is an axiom — no premise, no test evaluated, the store unchanged. The loop simply unfolds itself once into an if, and everything else follows from the rules we already have. Compare Topic 03, where while needed three separate rules and had to save B and C on the results stack. Here, one rewriting does the job, because the program text itself is the machine's memory of what remains.

Worked example: the swap program

Let P be z := !x; x := !y; y := !z and s a state such that s(z) = 0, s(x) = 1, s(y) = 2.

0⟨P, s⟩
1→⟨z := 1; (x := !y; y := !z), s⟩
2→⟨skip; (x := !y; y := !z), s[z ↦ 1]⟩
3→⟨x := !y; y := !z, s[z ↦ 1]⟩
4→⟨x := 2; y := !z, s[z ↦ 1]⟩
5→⟨skip; y := !z, s[z ↦ 1, x ↦ 2]⟩
6→⟨y := !z, s[z ↦ 1, x ↦ 2]⟩
7→⟨y := 1, s[z ↦ 1, x ↦ 2]⟩
8→⟨skip, s[z ↦ 1, x ↦ 2, y ↦ 1]⟩
Read the rhythm of that trace
Every assignment takes two steps — one to evaluate the right-hand side (:=R, via var), one to actually store it (:=) — and then a third (skip) to discard the leftover skip;. Eight transitions for three assignments. Compare Topic 03's abstract machine, which took considerably more, most of them pure syntax shuffling.

Terminal and blocked configurations

The remark — know this list
There is no axiom or rule for programs of the form:
  • ⟨n, s⟩ where n is an integer
  • ⟨b, s⟩ where b is a boolean
  • ⟨!l, s⟩ where l ∉ dom(s)
  • ⟨skip, s⟩

These are terminal configurations. In the case of ⟨!l, s⟩ where l ∉ dom(s) we say that the program is blocked.

Terminal ≠ successful
A blocked configuration is terminal in the Topic 01 sense — no c′ with c → c′ — but it is not a result. The first three cases are values and skip is successful termination; the blocked case is a failure that just happens to look the same from the outside. This is the same distinction the Topic 03 tool made between "final" and "stuck".

Comparison with the abstract machine

1 · Better

Each transition here is doing a part of the computation that leads to the result, whereas some of the transitions of the machine were only manipulating syntax.

2 · Worse

To show that a sequence of reductions is valid we need a proof. Each single arrow may require a whole derivation tree.

The example given: ⟨if !l > 0 then (C′; C) else skip, s⟩ → ⟨if 4 > 0 then (C′; C) else skip, s⟩ can be proved if s(l) = 4:

l ∈ dom(s), s(l) = 4
var
⟨!l, s⟩ → ⟨4, s⟩
bopL
⟨!l > 0, s⟩ → ⟨4 > 0, s⟩
if
⟨if !l > 0 then (C′; C) else skip, s⟩ → ⟨if 4 > 0 then (C′; C) else skip, s⟩
Summary of part 2
We have defined a transition system for SIMP where the transition relation is defined by induction. Transition steps represent steps of computation; the result of a program P in a memory state s can be found by performing transition steps starting from ⟨P, s⟩ until a terminal configuration is obtained — not all configurations reach a terminal configuration.

Part 3 · Determinism and evaluation sequences

Remark: determinism
The previous system is deterministic: given a configuration ⟨P, s⟩ there is a unique sequence of transitions from ⟨P, s⟩ with maximal length. This is called the evaluation sequence for ⟨P, s⟩.

The evaluation sequence for ⟨P, s⟩ may be finite or infinite.

Evaluation sequences are classified into three categories:

Terminating

The sequence eventually reaches a terminal non-blocked configuration — that is, ⟨n, s⟩ with n an integer, ⟨b, s⟩ with b a boolean, or ⟨skip, s⟩.

⟨if 4 = 0 then skip else skip, s⟩

Blocked (Stuck)

The sequence eventually reaches a blocked configuration — that is, ⟨!l, s⟩ where l ∉ dom(s).

⟨if !x = 0 then skip else skip, s⟩ when dom(s) does not contain x

Divergent

The sequence is infinite.

⟨while True do skip, s⟩

Big-step semantics

The goal, and the notation
Define a binary relation between configurations which associates a configuration with its corresponding terminal one (if it exists). That is, define by induction the relation ⟨P, s⟩ →* ⟨P′, s′⟩ such that ⟨P′, s′⟩ is terminal. The usual notation is ⟨P, s⟩ ⇓ ⟨P′, s′⟩:
⟨P, s⟩ ⇓ ⟨P′, s′⟩   if   ⟨P, s⟩ →* ⟨P′, s′⟩  where ⟨P′, s′⟩ is terminal

Small-step tells you how a program computes, one arrow at a time. Big-step tells you what it computes, in a single judgement — and hides the intermediate states inside the derivation tree.

Watch the stores thread through: s → s′ → s″
In every two-premise rule the output store of the first premise is the input store of the second. That threading is how big-step encodes sequencing and evaluation order without any notion of "steps". It's also why the rules are stated with three different store names rather than one — even for expressions, which in SIMP can't actually change the store.

whileT is the rule to understand — it has itself as a premise
The third premise of whileT is ⟨while B do C, s″⟩ ⇓ ⟨skip, s‴⟩ — the very same loop, in the store produced by one pass of the body. So a loop that runs four times has a derivation tree nested four deep, with the whileF case at the bottom terminating the recursion.

Consequence worth stating in an exam: a divergent program simply has no derivation. There is no finite proof tree for while True do skip, so the relation ⇓ never relates it to anything. Big-step semantics cannot distinguish non-termination from being stuck — both are just "no derivation exists". Small-step can: one gives an infinite sequence, the other reaches a blocked configuration. That is the sharpest difference between the two styles.

Adding variable declarations to SIMP

The idea
We can add local declarations to SIMP by using a local state in which the scope of a newly created location corresponds precisely with the block where the location is created and initialised — that is, static scope. For this we need a stack-based implementation of the state.

This is Topic 02's static scoping, now given a formal rule.

Syntax. We extend the syntax of SIMP with blocks:

C ::= begin loc x := E; C end

Semantics. We add the following rule to the big-step semantics:

⟨E, s⟩ ⇓ ⟨n, s′⟩
⟨C{x ↦ l}, s′[l ↦ n]⟩ ⇓ ⟨skip, s″[l ↦ n′]⟩
⟨begin loc x := E; C end, s⟩ ⇓ ⟨skip, s″⟩

where

  • l ∉ dom(s′) ∪ dom(s″) ∪ locations(C) — that is, l is a fresh name;
  • C{x ↦ l} is the program C where all the occurrences of x are replaced by l — to avoid confusion with other variables of the same name in other parts of the program.
Read the conclusion's store very carefully
The second premise ends in s″[l ↦ n′] but the conclusion is just s″. The fresh location l — with whatever final value n′ it ended up holding — is discarded when the block exits. That deletion is the whole meaning of "local": the block's variable does not exist outside the block, which is exactly static scope, expressed as a side-condition on a store.

And the freshness condition plus the renaming C{x ↦ l} is how the rule prevents a local x from clashing with an x elsewhere in the program — the formal counterpart of Topic 02's Pascal example where P1's x shadows main's.

Example: swap using a local variable

begin loc z := !x; x := !y; y := !z end

To show that the program P is correct:

First we prove
⟨x := !y; y := !l,  s[l ↦ s(x)]⟩ ⇓ ⟨skip,  s[x ↦ s(y), y ↦ s(x), l ↦ s(x)]⟩
as in the previous examples.
Let s′ = s[x ↦ s(y), y ↦ s(x)]  and  s″ = s[x ↦ s(y), y ↦ s(x), l ↦ s(x)], then:
⟨!x, s⟩ ⇓ ⟨s(x), s⟩
⟨x := !y; y := !l, s[l ↦ s(x)]⟩ ⇓ ⟨skip, s″⟩
⟨P, s⟩ ⇓ ⟨skip, s′⟩

Notice the final store is s′, not s″ — l has vanished, exactly as the rule prescribes.

Exam-style takeaways

Key things to nail for Topic 04
  1. Mathematical induction — base P(0), step ∀n. P(n) ⇒ P(n+1). Be able to run the Σ(2i − 1) = n² proof.
  2. Structural induction on lists — base P(nil), step P(l) ⇒ P(cons(h, l)).
  3. Structural induction on trees — base P(l) for all leaves; step, for each constructor c with n ≥ 1 arguments, ∀t₁…tₙ. P(t₁) ∧ … ∧ P(tₙ) ⇒ P(c(t₁,…,tₙ)).
  4. Instantiate it for SIMP expressions — base: P(n) for all n ∈ ℤ and P(!l) for all l; step: P(E) ∧ P(E′) ⇒ P(E op E′).
  5. Why structural induction is valid — it reduces to mathematical induction on the size of the (finite) tree; ∀E. P(E) ≡ ∀n. P′(n) where P′(n) = "for all E of size ≤ n, P(E)".
  6. The application theorem — if an integer expression uses only locations defined in m, its value is defined. Be able to write the induction step showing ⟨(E₁ op E₂)·c, r, m⟩ →* ⟨c, n·r, m⟩ using P(E₁) then P(E₂).
  7. Inductive definitions — an axiom is an element of T; a rule is a pair (H, c) with H a non-empty set of hypotheses and c the conclusion. I consists of t that are axioms, or conclusions of a rule whose hypotheses are all in I.
  8. Proofs are trees — leaves are axioms, each non-leaf matches a rule. Be able to draw one.
  9. The two example definitions — the naturals (axiom 0, rule n ⊢ n+1); and the evaluation relation (E, m) ⇓ n with its two axioms and one rule.
  10. Rule induction — base ∀a ∈ A. P(a); step ∀({h₁…hₙ}, c) ∈ R. P(h₁) ∧ … ∧ P(hₙ) ⇒ P(c). Example: uniqueness of values under ⇓.
  11. Special principle of rule induction — restrict to a subset J: basis over A ∩ J, and for rules with c ∈ J assume the property only for h ∈ H ∩ J.
  12. Small-step configurations — ⟨P, s⟩ with P a SIMP program and s a partial function from locations to integers; s[l ↦ n] notation.
  13. What counts as a result — E has value n if ⟨E, s⟩ →* ⟨n, s′⟩; C has a successful execution if ⟨C, s⟩ →* ⟨skip, s′⟩ (C in s produces s′).
  14. Reproduce the small-step rules — var, op, bop, and, not as axioms; opL/opR, bopL/bopR, notArg, andL/andR as congruence rules; :=R, :=, seq, skip, if, ifT, ifF, while for commands.
  15. Why the R rules require n₁ — a value on the left; this forces left-to-right evaluation.
  16. The while rule — ⟨while B do C, s⟩ → ⟨if B then (C; while B do C) else skip, s⟩. An axiom, one unfolding, no premise.
  17. Do a small-step trace — the swap example in 8 transitions, and !z + 1 with a derivation tree for each arrow.
  18. Terminal configurations — ⟨n, s⟩, ⟨b, s⟩, ⟨skip, s⟩, and ⟨!l, s⟩ with l ∉ dom(s); the last is called blocked.
  19. Comparison with the abstract machine — (1) each transition here does part of the computation, whereas some machine transitions only manipulated syntax; (2) but showing a reduction is valid requires a proof. Know the if !l > 0 … derivation.
  20. Determinism — given ⟨P, s⟩ there is a unique maximal-length transition sequence: the evaluation sequence, which may be finite or infinite.
  21. The three categories — terminating (reaches a terminal non-blocked configuration), blocked/stuck (reaches ⟨!l, s⟩ with l ∉ dom(s)), divergent (infinite). Know the three examples.
  22. Big-step definition — ⟨P, s⟩ ⇓ ⟨P′, s′⟩ if ⟨P, s⟩ →* ⟨P′, s′⟩ with ⟨P′, s′⟩ terminal.
  23. Reproduce the big-step rules — const, var, and, not, op, bop; skip, :=, seq, ifT, ifF, whileF, whileT. Note how stores thread s → s′ → s″.
  24. whileT has itself as a third premise — so a loop's derivation nests once per iteration, bottoming out in whileF. A divergent program has no derivation at all.
  25. Build a big-step derivation — the swap example, in the two stages shown.
  26. Variable declarations — syntax C ::= begin loc x := E; C end; the rule with its two side conditions (l fresh, C{x ↦ l} renaming); and the fact that l is dropped from the store in the conclusion, which is what makes scoping static.
