Topic 08 · Logic programming

Unification & SLD-Resolution

the machinery underneath every Prolog query

Topic 07 described Prolog's behaviour informally — "look for a clause with the same predicate in the head, replace the goal by its body, replacing variables as required". This topic gives both halves precisely: unification is how the replacing of variables is computed, and SLD-resolution is how the goals evolve.

Unification: unifiers and the mgu

A short history
  • A unification algorithm was first sketched by Jacques Herbrand in his thesis in the 1930s.
  • In 1965, Alan Robinson introduced the Principle of Resolution and gave a unification algorithm.
  • Around 1974, Robert Kowalski, Alain Colmerauer and Philippe Roussel defined and implemented Prolog based on these ideas.
  • The version presented here is based on the work of Martelli and Montanari, 1982.
The three definitions
  • A unification problem U is a set of equations between terms containing variables:  {s₁ = t₁, …, sₙ = tₙ}
  • A solution to U, also called a unifier, is a substitution σ such that when applied to every term in U, for each equation sᵢ = tᵢ the terms sᵢσ and tᵢσ are syntactically identical.
  • The most general unifier (mgu) of U is a unifier σ such that any other unifier ρ is an instance of σ.

Why "most general" — the worked comparison

Take U = {f(X) = f(Y)} with σ = {X ↦ Y} and ρ = {X ↦ a, Y ↦ a}. Both make the terms syntactically identical:

under σf(X)σ = f(Y) = f(Y)σ under ρf(X)ρ = f(a) = f(Y)ρ

Hence they are both unifiers. However σ is more general than ρ, because ρ is an instance of σ — applying γ = {Y ↦ a} after σ gives ρ — but ρ is not an instance of σ (we cannot get σ back from ρ). So σ is the most general unifier: no other unifier is more general.

Why the mgu is the one we want

The intuition — a very likely exam discussion point
Substitutions are applied to entire clauses to allow them to resolve. Substitutions that "commit" variables to specific terms (e.g. constants and function terms) prevent future substitutions being able to act as unifiers.

We can unify the atoms p(X) and p(Y) in the clauses p(X) ∨ ¬q(X) and ¬p(Y) either by replacing X by Y (or Y by X), or by replacing both X and Y by, say, the constant a.

The first two would let us then unify the resolvent ¬q(X) with the clause q(b); the last would not. Replacing X and Y by a early commits the variable to the constant, generating ¬q(a), which cannot then resolve with any atom involving anything other than a.

So we want to leave the variables "free", unless we need to bind them for the unification to succeed.

The unification algorithm

  • It finds the mgu for a unification problem if a solution exists, or otherwise fails, indicating that there are no solutions.
  • To find the mgu the algorithm simplifies the set of equations using a set of transformation rules.
  • At each step, either a new set of equations is produced or a failure case arises.
  • The algorithm terminates and outputs the mgu when no rule may be applied.
The six rules — learn these cold
(1)  f(s₁,…,sₙ) = f(t₁,…,tₙ), E  →  s₁ = t₁, …, sₙ = tₙ, E
(2)  f(s₁,…,sₙ) = g(t₁,…,tm), E  →  failure
(3)  X = X, E  →  E
(4)  t = X, E  →  X = t, E   if t is not a variable
(5)  X = t, E  →  X = t, E{X ↦ t}   if X not in t and X in E
(6)  X = t, E  →  failure   if X occurs in t and X ≠ t

Cases (1) and (2) apply also to constants (arity 0): in the first case the equation is eliminated, in the second failure arises.

Rule (6) is the occur-check
For example, X = f(X) is a failure case. This test is time consuming, and for this reason in some systems it is not implemented.

Without it, unifying X with f(X) builds a cyclic term and most Prologs will loop or print something infinite. It comes back at the end of this topic in the variable-renaming discussion.

Three more things worth knowing about the algorithm
  • The rules are applied in a non-deterministic way until no rule can be applied or a failure arises.
  • In the case of success, by changing each = in the final set of equations to ↦ we obtain the mgu.
  • We are working with sets of equations, so their order in the problem is unimportant.

The Principle of Resolution

How a goal is proved
  • In order to prove a goal :- G₁, …, Gₙ with respect to a set P of program clauses, resolution seeks to show that P ∪ {¬G₁ ∨ … ∨ ¬Gₙ} leads to a contradiction.
  • A contradiction is obtained when a literal and its negation are stated at the same time — both A and ¬A (recall A ∧ ¬A is unsatisfiable).
  • If a contradiction does not arise directly, a new goal is derived by unifying the current goal with a program clause.
  • The derived goals are called resolvents.
Note the logic: this is proof by contradiction
You don't prove the goal directly — you negate it, add it to the program, and derive a contradiction. That is why a query is a clause of only negative literals: :- G₁,…,Gₙ literally is ¬G₁ ∨ … ∨ ¬Gₙ. Topic 07's definition of a goal was setting this up.

What S, L and D stand for

Selective

At each resolution step a fixed computation rule is applied to select which atom from the goal will be next resolved upon.

Linear

At each resolution step the most recently derived resolvent is used as the next goal.

Definite

All the program clauses are definite clauses.

Two properties of SLD-resolution
  1. Refutation-complete: given a program and a goal, if a contradiction can be derived, then SLD-resolution will eventually generate it.
  2. Independence of the selection rule: if there exists a solution to a goal, SLD-resolution will find it, regardless of the selection rule employed for choosing which atom is next resolved upon.

Computing resolvents

The recipe
  • Given a goal clause :- G₁, …, Gk, we select an atom Gᵢ of the form p(s₁,…,sₙ).
  • We select a program clause p(t₁,…,tₙ) :- B₁,…,Bm such that p(t₁,…,tₙ) and p(s₁,…,sₙ) are unifiable using the mgu σ.
  • We obtain the resolvent :- B₁σ, …, Bmσ, G₁σ, …, Gi−1σ, … Gi+1σ, …, Gkσ, from which Gᵢσ has been eliminated.
  • Continue until an empty resolvent is found — a contradiction.
  • When an empty resolvent is generated, the composition of the substitutions applied at each resolution step, restricted to the variables of the query, is the solution.
Prolog's two commitments — and what they cost
  • Prolog always selects the left-most literal in the goal.
  • Prolog uses the clauses in the program in the order they are written, top to bottom.
  • SLD-resolution is complete, but Prolog's implementation of SLD-resolution is not complete, because of its search strategy in the SLD-tree.
  • Prolog uses depth-first search, which is efficient but not complete, because it may get stuck in a branch that expands infinitely.

Read those together: the calculus is complete, the implementation is not. That gap is entirely due to depth-first search, and it is why clause order matters so much in practice.

Worked example: :- likes(Z, prolog).

1based(prolog, logic).
2based(haskell, maths).
3likes(max, logic).
4likes(claire, maths).
5likes(X, P) :- based(P, Y), likes(X, Y).
1:- likes(Z, prolog).
2:- based(prolog, Y), likes(Z, Y).using the last clause and the mgu {X ↦ Z, P ↦ prolog}
3:- likes(Z, logic).using the first clause and the mgu {Y ↦ logic}
4□  empty resolventunify with the fact likes(max, logic) using {Z ↦ max}

The composition of substitutions generated is {X ↦ max, P ↦ prolog, Y ↦ logic, Z ↦ max}, and the solution to the initial query is {Z ↦ max} — restricted to the variables of the query.

SLD-resolution trees

Each resolution step is drawn as a goal, an arrow labelled with the mgu, and the resolvent. Since several clauses may be usable, a goal may have several children — giving an SLD-resolution tree.

Three kinds of branch
  • Every branch that leads to an empty resolvent (denoted □) yields a solution.
  • If a goal unifies with no program clause, the branch is a failure.
  • Thus an SLD-resolution tree may have success branches, failure branches, but also infinite branches.

Back-tracking

How Prolog explores the tree
  • When a branch ends, Prolog can back-track over the tree to search alternative branches.
  • The previous resolution step is taken back and the next possible resolvent is generated.
  • Failure branches back-track automatically, and solution branches can be back-tracked from on request.
  • Back-tracking can be stopped by using the cut predicate, written !, which means do not back-track beyond this point.

The standard example — :- append(X, [1, 2], U). produces infinitely many solutions by back-tracking:

(1) {X ↦ [], U ↦ [1, 2]} (2) {X ↦ [X1], U ↦ [X1, 1, 2]} (3) {X ↦ [X1, X2], U ↦ [X1, X2, 1, 2]} (4) ...

Non-termination: clause order matters

The rule
Since Prolog searches the tree using the program clauses in the order in which they are written, and in a depth-first manner, it is important to put base clauses before recursive ones.
append([X|L],Y,[X|Z]) :- append(L,Y,Z). append([],L,L).

This program produces no solutions and will result in an error, because Prolog will attempt to construct an infinite branch by using the recursive clause at each resolution step.

Note exactly what changed — and what didn't
The two programs are logically identical: a set of clauses has no order. Only Prolog's search strategy distinguishes them. This is the sharpest possible illustration of "SLD-resolution is complete, but Prolog's implementation is not": the solution is still there in the tree, depth-first search just never reaches it.

Constructing an SLD-resolution tree

The full checklist
  • Each node represents the goal being operated on, which may contain several literals.
  • The selection function picks the next literal to resolve — in Prolog, always the left-most literal (underlined in the examples).
  • When resolving, Prolog uses the clauses in order of appearance, top to bottom.
  • Each node has as many children as there are clauses that can be unified with the selected literal. Failed unifications are not depicted.
  • The order of resolution with program clauses is depicted left-to-right.
  • Each child is connected to its parent by an arrow labelled with the mgu used.
  • If no clause can be unified, the branch fails (no children) — indicated with "failure".
  • If a goal node is empty, it is represented by □ and ends a success branch.
  • Some goals need no program clauses — typically built-in predicates. E.g. Y is 3+1 succeeds if Y can be unified with 4, so it succeeds if Y is free or already bound to 4, and fails otherwise.

A note on variable renaming

Consider this program clause and goal:

% in the program myappend([X|Y],Z,[X|W]) :- myappend(Y,Z,W). % goal :- myappend(Y,[2],W).
Without renaming, the unification fails
To resolve, we must solve  U = {[X|Y] = Y,  Z = [2],  [X|W] = W}.

Formally [X|Y] is shorthand for '[|]'(X,Y), whose functor is '[|]'. By rule (6) of the unification algorithm — the occur-check — U cannot be solved, because Y occurs in [X|Y] (and likewise W in [X|W]).

Why renaming is legitimate, and how to do it
The choice of variables used in a Prolog program is irrelevant, because formally they are universally quantified. We are free to rename them as long as we do the renaming uniformly within the clause and do not use symbols that already appear elsewhere in it (lest we cause unwanted bindings).

For example, renaming X by Z in myappend([X|Y],Z,[X|W]) would clearly change the intended meaning, because in the original clause X and Z allow bindings to different terms.

It is common to rename systematically with a suffix:

myappend([X1|Y1],Z,[X1|W1]) :- myappend(Y1,Z,W1).

which allows myappend(Y,[2],W) and myappend([X1|Y1],Z,[X1|W1]) to be resolved using

σ = {Y ↦ [X1 | Y1],  Z ↦ [2],  W ↦ [X1 | W1]}

In this case we do not have to rename X and Z for the unification to be possible, but renaming is safe if done uniformly. And: remember to carry the corresponding bindings back to the variables in the original goal!

This is what the tool's _1, _2 suffixes are doing
Every time the SLD-tree builder below uses a clause, it renames that clause's variables apart first. That's not an implementation convenience — it is required for correctness, as this example shows. Exam-style takeaways

Key things to nail for Topic 08
  1. Unification problem = a set of equations between terms; a unifier σ makes sᵢσ and tᵢσ syntactically identical; the mgu is a unifier of which every other unifier is an instance.
  2. The f(X) = f(Y) comparison — why {X↦Y} is more general than {X↦a, Y↦a}: ρ is an instance of σ (compose with {Y↦a}) but not conversely.
  3. Why generality matters — committing a variable to a constant early prevents later resolutions; leave variables free unless binding is needed.
  4. Write out all six rules. (1) same functor → equate arguments; (2) different functor → failure; (3) X = X → delete; (4) t = X with t not a variable → swap; (5) X = t with X ∉ t and X in E → substitute in E; (6) X occurs in t and X ≠ t → failure.
  5. Rules (1) and (2) apply to constants too — arity 0: eliminate, or fail.
  6. Rule (6) is the occur-check — X = f(X) fails; the test is time consuming, so some systems omit it.
  7. Reading off the answer — change each = to ↦ in the final set. The problem is a set, so order is unimportant.
  8. Run the algorithm by hand — all three worked examples, especially the 10-step exercise.
  9. The Principle of Resolution — prove :- G₁,…,Gₙ by showing P ∪ {¬G₁ ∨ … ∨ ¬Gₙ} leads to a contradiction; derived goals are resolvents.
  10. S, L, D — Selective (a fixed computation rule picks the atom), Linear (the most recently derived resolvent is the next goal), Definite (all program clauses are definite).
  11. Two properties — refutation-complete; independence of the selection rule.
  12. Computing a resolvent — select Gᵢ, find a clause whose head unifies with mgu σ, replace Gᵢ by the clause body, applying σ throughout. The composition of substitutions restricted to the query's variables is the answer.
  13. Prolog's strategy — left-most literal, clauses top to bottom, depth-first. SLD-resolution is complete but Prolog's implementation is not, because depth-first search can get stuck in an infinite branch.
  14. Draw SLD-trees — nodes are goals, edges are labelled with mgus, children in program order left-to-right, failed unifications not shown, □ ends a success branch, dead ends marked failure. Trees may have success, failure and infinite branches.
  15. Reproduce the trees above — likes(Z,prolog), likes(Z,painting), the four goals on the s/r/q/p program, and length([2,3],X).
  16. Built-ins in a tree — Y is 3+1 needs no program clause; it succeeds if Y is free or already bound to 4.
  17. Back-tracking — failure branches back-track automatically, success branches on request; the cut ! means do not back-track beyond this point.
  18. Clause order — put base clauses before recursive ones; the reversed append yields an infinite branch and no solutions, even though the program is logically the same.
  19. Variable renaming — needed because {[X|Y] = Y, …} fails the occur-check. Renaming is legitimate because clause variables are universally quantified; it must be done uniformly within the clause and must not reuse symbols already in it. Carry the bindings back to the original goal's variables.
