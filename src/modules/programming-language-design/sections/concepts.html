Acronyms & names — expand these on sight

If you learn one acronym properly, make it SLD
Selective · Linear · Definite. And know the two properties that go with it:
  • Refutation-complete — given a program and a goal, if a contradiction can be derived, SLD-resolution will eventually generate it.
  • Independence of the selection rule — if a solution exists, SLD-resolution will find it regardless of the selection rule used to choose the next atom.

The three components of a language

ComponentDefinition (as given)Answers
SyntaxDefines the form of programs: how expressions, commands and declarations are built and put together to form a program.Which strings (or trees) are programs?
SemanticsGives the meaning of programs: how they behave when they are executed.What does this program do?
ImplementationA software system that can read a program and execute it on a machine, plus a set of tools (editors, debuggers, etc).How does the meaning actually happen on hardware?

Concrete vs abstract syntax

Concrete syntax

  • Defines strings of characters.
  • Written in BNF over terminals.
  • Can be ambiguous — one string, two parse trees, two different values.
  • What a parser has to cope with.

Abstract syntax

  • Defines trees, not strings.
  • e.g. e ::= n | op(e, e)
  • No ambiguity — the two readings are simply two different trees.
  • The form the rest of the course works with.
Ambiguity — the definition and the fix
A grammar is ambiguous when a single string has more than one parse tree. It matters because different trees can give different values — 1 − 2 − 3 is −4 or 2 depending on which derivation you take.

The course's fix is not to patch the concrete grammar but to move up a level to abstract syntax.

Compilation vs interpretation vs hybrid

MethodWhat it doesTrade
CompilationThe compiler translates the source language into machine language that can be executed directly on the computer.Fast execution.
InterpretationA program (the interpreter) reads and executes the source directly, without producing machine code first.Slower execution, easier debugging and portability.
HybridSource is compiled to an intermediate form which is then interpreted (or JIT-compiled).A middle ground — portability of interpretation with much of the speed of compilation.
The four phases of compilation — memorise the list and the order
  1. Lexical Analysis — characters → tokens
  2. Syntax Analysis (Parsing) — tokens → syntax tree
  3. Type and Semantics Analysis — static checks on the tree
  4. Machine Code Generation — emit machine code

The three components are hiding in that pipeline: phases 1–2 implement the syntax (concrete in, abstract out), phase 3 the static semantics, phase 4 the implementation.

The three styles of semantics

StyleMeaning is given…Good for
Denotationalin an abstract, mathematical way, using a mathematical model of the language; describes the effect of each construct.reasoning & proving properties of programs
Axiomaticusing axioms and deduction rules in a specific logic — a precondition and a postcondition around each construct.reasoning & proving properties of programs
Operational ★in terms of computation steps — the behaviour of each construct.implementing the language; this is the one the course develops
The examinable framing
They are complementary, not rivals — "each has its advantages". If asked to compare, say what each is for: denotational and axiomatic for proving things about programs, operational for saying how they run.

Configurations: terminal vs blocked vs value
A configuration is terminal when there is no c′ with c → c′. The ones with no rule are:
⟨n, s⟩  — an integer
⟨b, s⟩  — a boolean
⟨skip, s⟩  — successful termination
⟨!l, s⟩ where l ∉ dom(s)  — blocked

Terminal ≠ successful. The first three are values or successful termination; the fourth is a failure that merely looks the same from outside. Blocked is different again from divergent (never terminating).

Determinism, in one line
A transition system is deterministic if every configuration has at most one successor — for each c there is at most one c′ with c → c′. That is what makes "the" evaluation sequence well defined.

The three inductions

KindYou induct over…Base case / step
Mathematical inductionthe natural numbersprove P(0); assume P(n), prove P(n+1)
Structural inductionthe structure of a term or tree (e.g. an expression, a list, a user-defined type)prove it for the atomic constructors; assume it for the sub-terms, prove it for the compound constructor
Rule inductionthe derivations of an inductively defined relation — its axioms and rulesprove it for each axiom; assume it for the premises of each rule, prove it for the conclusion
How to pick the right one in an exam
Look at what the statement quantifies over. "For all n…" → mathematical. "For all expressions/commands/lists…" → structural. "Whenever ⟨P,s⟩ → ⟨P′,s′⟩ …" or "for everything in this inductively defined set" → rule induction, because you are inducting over how the judgement was derived.

Variables: the four properties

PropertyWhat it is
NameUsually a string of characters with constraints — maximal length, allowed characters.
TypeIndicates the range of values allowed and the operations available. Some languages are untyped; others statically typed (Java, Haskell, ML, Scala) or dynamically typed (Python, Ruby).
Address — the l-valueThe memory address the variable is associated with. The association is not simple: the same name may be associated with different addresses in different parts of the program.
Value — the r-valueThe contents of the memory location it is associated with.
l-value vs r-value — the whole point of the names
From the two sides of x = y:
  • l-value = the address. What appears on the left: we need to know where to put something.
  • r-value = the value. What appears on the right: we need to know what is stored there.

So x = y means: take the r-value of y and store it at the l-value of x. In SIMP this is why you write l := !l − 1 — the ! is exactly "take the r-value".

Lifetime: the four classes of variable

Definition
Lifetime = the time during which the variable is allocated a specific memory location — between allocation and deallocation.
ClassAllocated…✓ Advantage✗ Disadvantage
Static Bound to a memory location before program execution begins, and until it ends. Efficiency — all addressing resolved at compile time; no allocation/deallocation at run time. Storage cannot be reused, and recursive programs need dynamic variables.
Stack dynamic Allocated when the declaration is processed at run time; deallocated when the block exits. Supports recursion — each activation gets its own copy. Run-time overhead for allocation/deallocation; the value does not survive the block.
Explicit heap-dynamic Allocated and deallocated by explicit instructions written by the programmer (e.g. new / delete, malloc / free), at run time. Full programmer control over lifetime; needed for dynamic data structures. Error-prone — leaks and dangling pointers are the programmer's fault.
Implicit heap-dynamic Allocated automatically, when a value is assigned to the variable — no declaration or explicit instruction. Maximum flexibility; very high-level code. Costly at run time, and loses compile-time error detection because the type isn't fixed in advance.
Explicit vs implicit heap-dynamic — the one they love to ask
Both live on the heap and both are created at run time. The difference is who does the allocating:
  • Explicit — the programmer writes an instruction that allocates and one that deallocates.
  • Implicit — it just happens, on assignment. The variable is bound to storage (and often to a type) only when something is assigned to it.

Memory hook: explicit = you say when. Implicit = the assignment says when.

Scope: static vs dynamic — and scope vs lifetime

Definitions
  • Scope = the range of instructions in which the variable is visible (can be used).
  • Local variables are those declared in the block of program being executed.
  • Variables that are visible but not local are called global.

Static scope

  • Can be determined before execution (at compile time).
  • The rule: look for the declaration in the same block; if not there, in the parent block; and so on outwards.
  • If no declaration is found, the compiler reports an error.
  • Follows the program text.

Dynamic scope

  • Determined at run time.
  • The declaration is looked for in the chain of calls — the most recent still-active declaration wins.
  • Follows the execution history, not the text.
  • The same name in the same place can refer to different variables on different runs.
Don't confuse scope with lifetime
Two different questions about the same variable:
  • Lifetime is about time — when does this variable have memory allocated?
  • Scope is about place in the program text — where can this name be used?

A variable can be alive but invisible (a caller's local while a callee runs) — which is exactly the situation dynamic scoping exploits.

Control statements

Loops — two independent classifications, and the exam likes both
By when the test happensBy what controls it
Pre-test — the test for loop completion is done before the body executes. (while, for) Counter-controlled — a counter variable with an initial value, an increment and a limit.
Post-test — the test occurs after the body is executed. (do…while, repeat…until) Logically-controlled — repetition is governed by a boolean condition rather than a count.

The consequence to state: a post-test loop always runs its body at least once; a pre-test loop can run it zero times.

And the trap: do…while continues while the condition is true, repeat…until stops when it becomes true — same expression, opposite meaning.

The dangling else
In if C₁ then if C₂ then S₁ else S₂, the else could attach to either if. This is an ambiguity in the concrete syntax. The usual resolution: the else binds to the nearest unmatched if.

Functional: the two properties of evaluation

PropertyStatement
Unicity of normal formsIn (pure) functional languages the value of an expression is uniquely determined by its components, and is independent of the order of reduction.
Non-terminationNot all reduction sequences lead to a value — some do not terminate.
How the two interact — the sentence that gets marks
With fortytwo x = 42 and infinity = infinity + 1:

for fortytwo infinity, some reduction sequences do not terminate, but those which terminate give the value 42.

So unicity says: if you reach a normal form, it is the normal form. It does not promise you will reach one.

Call-by-name vs call-by-value vs lazy

StrategyDefinitionConsequence
Call-by-name
normal order		 Reduce first the application using the definition of the function, and then the argument. Finds a value whenever one exists. May evaluate the same argument more than once.
Call-by-value
applicative order		 Evaluate first the argument and then the application using the definition of the function. Each argument evaluated once, but may diverge where call-by-name succeeds — e.g. fortytwo infinity.
Lazy Call-by-name plus sharing: the argument is not evaluated until needed, and once evaluated the result is shared. Same termination behaviour as call-by-name, without the duplicated work. This is what Haskell does.
The one-line comparison
CBV can fail where CBN succeeds; lazy = CBN with the repeated work removed. If asked why lazy exists, the answer is sharing, not termination — it terminates exactly as often as call-by-name does.

Currying, partial application, composition

The central fact
Functions in Haskell take no more than one argument. Applying a function to n > 1 arguments yields another function with n − 1 arguments. This is what allows partial application.
plus :: Int → Int → Int
plus 3 :: Int → Int   — partially applied
(plus 3) 2 = 5

Two conventions doing the work: → is right-associative (Int→(Int→Int)) while application is left-associative ((plus 3) 2).

Tuples vs currying — the distinction they ask for
Multiple arguments can be passed as one tuple, but this does not allow partial application: a tuple argument is one argument, so there is no intermediate stage to stop at.

Static vs dynamic typing

Definitions
Types help ensure a program behaves in a precise, pre-determined way. Values are divided into classes called types, and each type is associated with a set of operations. Types may be given explicitly by the programmer or inferred automatically by the type system.

Checking that types are used correctly is called typing, and may be checked:

Static typingDynamic typing
Before executionDuring execution
C, C++, Java, HaskellPython, JavaScript, PHP
Static typing — the claims to quote
Every valid expression must have a type. Expressions that cannot be "typed" are considered erroneous and are rejected by the compiler without evaluation.

Advantages:

  • Types help detecting errors at an early stage.
  • Types help in the design of software, since they are a simple form of specification.

A program that passes the type controls is not guaranteed to be correct, but it is free of type errors at runtime. — learn this sentence verbatim; it is the honest statement of what types do and don't buy you.

Monomorphic vs polymorphic, and the two polymorphisms

Definition
Type systems can be:
  • monomorphic — every expression has at most one type;
  • polymorphic — some expressions have more than one type.

The standard example is functional composition, where a, b, c are type variables:

(.) :: (b → c) → (a → b) → (a → c)
Parametric polymorphismOverloading (ad-hoc polymorphism)
WhatOne definition that works uniformly for any type, written with type variables.Several functions, with different types, share the same name.
Examplelength :: [a] → Int+ for both integers and reals
Why neededWrite it once, use it at every type.A polymorphic (+) :: a → a → a is too general — it would allow 'a' + 'b', which makes no sense.
Where type classes come in
Type classes are Haskell's mechanism for overloading: they constrain a type variable to those types that support the operation, e.g. (+) :: Num a ⇒ a → a → a. That reads "for any type a that is a Num" — general enough to reuse, restricted enough to reject characters.
Type inference, in one sentence
The type system works out the most general type of an expression without the programmer writing it down. "Most general" is the key word: it commits to nothing it doesn't have to, leaving type variables wherever the code doesn't force a particular type.

SFUN: fnval vs fnname

fnval (call-by-value)fnname (call-by-name)
The ruleThe argument must be evaluated to a value first, then substituted.The argument is substituted unevaluated, then the body is evaluated.
Failure modeIf the argument has no value, there is no derivation at all — even if the body never uses it.Succeeds where CBV fails, because an unused argument is simply discarded.
CostEach argument evaluated once.An argument used twice is evaluated twice — visible as repeated sub-derivations in the proof tree.
The canonical example
fortytwo(infinity) — no derivation under fnval, value 42 under fnname. And max(3, square(2)) gives 12 under both, but call-by-name's derivation is larger because it evaluates square(2) twice. That duplication is exactly what sharing removes in a lazy implementation.

Logic programming: the vocabulary ladder

TermDefinition
TermA constant, a variable, or a function symbol applied to terms.
Atomic formula (atom)A predicate symbol applied to terms — e.g. p(s₁,…,sₙ).
LiteralAn atomic formula (positive) or its negation (negative).
Horn clauseA disjunction of literals of which at most one may be positive.
Definite clauseA Horn clause with exactly one positive literal. (The notes warn this terminology is not uniform — some books call all Horn clauses definite.)
FactA definite clause comprising a single positive literal A.
RuleA definite clause with some negative literals: A ∨ ¬B₁ ∨ … ∨ ¬Bₙ  — written A :- B₁, …, Bₙ.
GoalA clause with only negative literals — written :- G₁, …, Gₙ.
ProgramA set of definite clauses (facts and rules).
The three cases of a Horn clause — say them in this order
  1. a single positive literal and some negative literals → a rule;
  2. a single positive literal and no negative literals → a fact;
  3. only negative literals → a goal.

Cases 1 and 2 are the definite clauses. That is why a program is made of facts and rules, and a query is the odd one out.

Substitution, unifier, mgu

TermDefinition
SubstitutionA partial mapping from variables to terms, with a finite domain. Written σ = {X₁ ↦ t₁, …, Xₙ ↦ tₙ}.
Unification problemA set of equations between terms containing variables: {s₁ = t₁, …, sₙ = tₙ}.
Unifier (a solution)A substitution σ such that applying it to every term makes each pair syntactically identical.
mguThe most general unifier — every other unifier is an instance of it. It commits to as little as possible.
Two details worth a mark each
  • We always replace variables with terms, never the other way round — because only variables can be replaced, and not all terms are variables.
  • Application is simultaneous. A substitution is applied to all variables in one pass, not one after another.

And the occur check: X = f(X) has no solution — a variable cannot be unified with a term properly containing it.

Resolution and SLD

The Principle of Resolution
To prove a goal :- G₁, …, Gₙ against a set P of program clauses, resolution seeks to show that
P ∪ {¬G₁ ∨ … ∨ ¬Gₙ}  leads to a contradiction.
A contradiction arises when a literal and its negation are stated at the same time (A ∧ ¬A is unsatisfiable). If no contradiction arises directly, a new goal is derived by unifying the current goal with a program clause. The derived goals are called resolvents.

Note the logic: this is proof by contradiction. You don't prove the goal directly — you negate it and derive a contradiction.

Backtracking, and why clause order matters
Prolog searches the SLD-tree depth-first, left-to-right, and backtracks when a branch fails. Because the search is depth-first, the order of the clauses in the program can decide whether the query terminates at all — a solution further right in the tree is never reached if an infinite branch sits to its left. Independence of the selection rule is about which atom is chosen, not about clause order.
Variable renaming — why X becomes X_14
Program clauses are renamed apart (given fresh variables) at every use, so that a variable in the clause is never accidentally identified with a variable of the same name in the goal. Without it, unification can fail — or worse, succeed wrongly — through pure name collision.

Prolog's two limitations

LimitationWhyWhat Prolog does instead
Negation Programs are made of definite clauses, which contain exactly one positive literal. So you cannot state negative facts (¬p(b)) nor put a negative literal in a clause head. Negation as failure — failure to prove A is taken as proof that ¬A follows. Written \+. A negative literal is then allowed in the body of a clause (and in a goal).
Disjunction A definite clause has one positive literal, so you cannot write a disjunctive head A ∨ B. Express the alternatives as separate clauses with the same head.
Negation as failure is not logical negation
It is a weaker notion. It assumes everything not derivable is false (a closed-world assumption). :- \+ p(a). fails precisely because :- p(a). succeeds — so what you are really testing is "can I prove it?", not "is it false?".
