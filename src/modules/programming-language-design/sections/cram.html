W1 · The three components

  • Syntax = form of programs (how expressions/commands/declarations are built).
  • Semantics = meaning of programs (how they behave when executed).
  • Implementation = software system that reads & executes a program, + tools.
  • Layers: machine → OS → language implementation → user programs.

W1 · Paradigms

  • Imperative — computation steps, mirrors the architecture. Fortran, C, Python, Java.
  • Functional — mathematical functions; what, not how. Lisp, Haskell, CaML, Scheme.
  • Logic — describes the problem, not the algorithm. Prolog.
  • Object-oriented — orthogonal; addable to any of the above. Java, OCaML, Scala, Python, Ruby, F#.
  • Mismatched design method & language ⇒ programming effort increases.

W1 · Implementation techniques

  • Compilation → machine language. Fast execution.
  • Phases: lexical analysis → syntax analysis (parsing) → type & semantics analysis → machine code generation.
  • Interpretation → no translation; a virtual machine for the language. Easy to implement, easy debugging, better errors; slow. LISP, shell scripts.
  • Hybrid → compile to an intermediate language, then interpret. Portability. Java bytecode; functional → abstract machine code. ghci vs ghc.
  • Fetch–execute: init PC; repeat { fetch at PC · increment PC · decode & execute }.

W1 · Syntax

  • Given by: an alphabet + a set of rules.
  • Grammar = alphabet V = VT ∪ VNT + rules + initial symbol. Written in BNF.
  • Concrete syntax — which chains of characters are well-formed programs.
  • Abstract syntax — the syntax trees, to which a semantics is associated.
  • Ambiguity: 1-2-3 has two derivations → 1−(2−3)=2 vs (1−2)−3=−4.
  • Fix: e ::= n | op(e,e) defines trees — unambiguous. We always work with abstract syntax.

W1 · Semantics

  • Static (typing) — catch syntactically-correct-but-broken programs before execution, e.g. 1 + 'a'.
  • Dynamic — the meaning of programs.
  • Formal semantics matters for: implementation (machine-independent abstraction), programmers (reason & prove), designers (detect ambiguity, suggest constructs — cf. λ-calculus).
  • Denotational — abstract mathematical model; describes the effect.
  • Axiomatic — axioms + deduction rules; pre/postconditions.
  • Operational ★ — computation steps via transition systems. Studied in this course.
  • Operational → implementation & compiler-optimisation correctness. Denotational/axiomatic → proving program properties.

W1 · Transition systems

  • Specified by: a set Config of configurations + a relation → ⊆ Config × Config.
  • c →* c′ = reflexive transitive closure: a chain c → c₁ → … → cₙ = c′ with n ≥ 0.
  • Terminal (T): for all c ∈ T there is no c′ with c → c′.
  • A run = a sequence of transitions from i ∈ I to t ∈ T.
  • Deterministic iff ∀c,c₁,c₂: c → c₁ ∧ c → c₂ ⇒ c₁ = c₂.
  • Abstract machine = a transition system specifying an interpreter. Great for implementation, hard for users.
  • Structural OS (SOS) = inductive definition of execution; each command described in terms of its components.

W2 · Variables

  • Imperative languages = abstractions of the Von Neumann architecture; variables represent memory cells.
  • 4 properties: name · type (values allowed and operations available) · address = l-value · value = r-value.
  • Name→address is not simple: one name ↦ many addresses; many names ↦ one address (Pascal variant records, Fortran EQUIVALENCE).
  • Static/dynamic typing: Java, Haskell, ML, Scala / Python, Ruby.

W2 · Lifetime & scope

  • Lifetime = time between allocation and deallocation. 4 classes:
  • Static — bound before execution until end. ✓ efficiency (compile-time addressing) ✗ no reuse, no recursion.
  • Stack dynamic — allocated when the declaration is processed at run time (locals of recursive procedures).
  • Explicit heap-dynamic — nameless cells via pointers (C++ new/delete); Java objects, no explicit destroy → GC (first in Lisp).
  • Implicit heap-dynamic — bound only when assigned (Perl/JS strings, arrays). ✓ flexibility ✗ hard error detection.
  • Scope = range where the variable is visible. Local = declared in the executing block; global = visible but not local.
  • Static scope — compile time; same block → parent block → …; not found = compiler error.
  • Dynamic scope — depends on the calling sequence. ✗ no static type-checking ✗ very hard to understand. Perl lets you choose; Scheme is static.

W2 · Flow of control

  • 3 kinds: selection · looping · branching. if-then-else + while suffice for any sequential algorithm; go-to is superfluous.
  • Dangling else — Java matches else with the most recent unpaired then. Algol 60 disambiguates with begin/end; Java needs braces for the outer reading.
  • Multiple selectors — switch; some languages exit at the end of a branch, others need explicit break/return.
  • Pre-test (test before body) vs post-test (after) — post-test runs the body at least once.
  • Counter-controlled vs logically-controlled.
  • for(e1;e2;e3) — e1 initialises; e2 evaluated before each body; e3 after each body.
  • while pre-test, runs while True · do post-test, runs until False · Pascal repeat runs until True (the opposite of do).
  • Assignment: = ≠ mathematical equivalence (:= sometimes); i++ returns i, ++i returns i+1.
  • Blocks (keywords/separators, may hold declarations → local under static scope) · subprograms = named blocks invoked explicitly · formal (declaration) vs actual (invocation) parameters.

W3 · SIMP syntax

  • Why formal: f(i++,--i) — both operators precise, but C never specified the order of evaluation of parameters → different compilers, different code.
  • Abstract machine = transition system specifying an interpreter. The first approach to formal description.
  • P ::= C | E | B
  • C ::= skip | l := E | C ; C | if B then C else C | while B do C
  • E ::= !l | n | E op E · op ::= + − ∗ /
  • B ::= True | False | E bop E | ¬B | B ∧ B · bop ::= > < =
  • !l = the value stored in l (r-value); bare l = the address (l-value).
  • Grammars define trees: leaves ∈ ℤ ∪ {True,False} ∪ L ∪ {skip}; non-leaves = operators & commands.

W3 · The machine

  • 3 parts: control stack c · results (auxiliary) stack r · memory/store m, a partial function address → integer; dom(m) = where defined.
  • m[l ↦ n](l) = n and m[l ↦ n](l′) = m(l′) if l ≠ l′.
  • Configuration = ⟨Control, Results, Memory⟩. Initial ⟨C · nil, nil, m⟩ · Final ⟨nil, nil, m⟩.
  • Command semantics: ⟨C·nil, nil, m⟩ →* ⟨nil, nil, m′⟩ ⇒ C terminates successfully producing m′.
  • Expression semantics: ⟨E·c, r, m⟩ →* ⟨c, v·r, m′⟩ ⇒ the value of E in m is v.
  • Every operator has 2 rules: decomposition (push sub-phrases + token) then application (consume operands, push one value).
  • ⚠ Argument order: results stack is n₂·n₁·r — compute n₁ op n₂.
  • Assignment: l pushed unevaluated onto r; := then sees n·l·r and yields m[l↦n].
  • If: both branches parked on r; if discards all three and moves the chosen branch to c.
  • While: ⟨while·c, True·B·C·r, m⟩ → ⟨C · (while B do C) · c, r, m⟩ — the loop rebuilds itself behind the body.
  • ✓ Advantage: step-by-step, useful for implementing the language. ✗ Disadvantage: not intuitive — many transitions are just phrase analysis, few really compute.
  • Fix → structural approach (Plotkin): transitions for a compound statement defined via those of its sub-statements — i.e. inductive.

W4 · Induction

  • Mathematical: base P(0); step ∀n. P(n) ⇒ P(n+1).
  • Structural (lists): P(nil); P(l) ⇒ P(cons(h,l)).
  • Structural (trees): P(leaf) for all leaves; for each constructor c, P(t₁)∧…∧P(tₙ) ⇒ P(c(t₁,…,tₙ)).
  • For SIMP E: base P(n), P(!l); step P(E)∧P(E′) ⇒ P(E op E′).
  • Justified by maths induction on tree size (trees are finite).
  • Inductive definition: axiom = element of T; rule = (H, c), H non-empty hypotheses, c conclusion. Membership shown by a proof tree whose leaves are axioms.
  • Rule induction: base ∀a∈A. P(a); step ∀({h₁…hₙ},c)∈R. P(h₁)∧…∧P(hₙ) ⇒ P(c).
  • Special rule induction (subset J): basis over A∩J; for rules with c∈J assume only for h∈H∩J.

W4 · Small-step

  • Configuration = ⟨P, s⟩ — a pair, no stacks. Remaining work = the leftover program text.
  • E has value n if ⟨E,s⟩ →* ⟨n,s′⟩ · C succeeds if ⟨C,s⟩ →* ⟨skip,s′⟩.
  • Axioms: var, op, bop, and, not. Congruence: opL/opR, bopL/bopR, notArg, andL/andR.
  • R rules require n₁ — a value on the left ⇒ forces left-to-right evaluation.
  • Commands: :=R, := , seq, skip, if, ifT, ifF, while.
  • while is an axiom: ⟨while B do C,s⟩ → ⟨if B then (C; while B do C) else skip, s⟩.
  • Terminal: ⟨n,s⟩ ⟨b,s⟩ ⟨skip,s⟩ and ⟨!l,s⟩ with l ∉ dom(s) — the last is blocked.
  • vs abstract machine: ✓ every transition does real computation; ✗ each arrow needs a proof.
  • Deterministic ⇒ a unique maximal evaluation sequence, finite or infinite.
  • 3 categories: terminating · blocked/stuck · divergent.

W4 · Big-step

  • ⟨P,s⟩ ⇓ ⟨P′,s′⟩ if ⟨P,s⟩ →* ⟨P′,s′⟩ and ⟨P′,s′⟩ is terminal.
  • Expressions: const, var, and, not, op, bop. Stores thread s → s′ → s″.
  • Commands: skip, := , seq, ifT, ifF, whileF, whileT.
  • whileT has three premises, the third being the same loop again ⇒ tree nests once per iteration, bottoming out at whileF.
  • ⚠ Divergent programs have NO derivation — big-step can't distinguish divergent from blocked; small-step can.
  • Blocks: C ::= begin loc x := E; C end. Rule needs l fresh (∉ dom(s′) ∪ dom(s″) ∪ locations(C)) and the renaming C{x ↦ l}.
  • The conclusion drops l from the store — that discard is what makes scoping static.

W6 · Functional basics

  • Programs consist entirely of functions; functions defined in terms of other functions; focus on what, not how.
  • Strongly typed (no core dumps) + built-in memory management. ✓ shorter, easier to understand/design/verify/maintain. ✗ usually slower, arguably less flexible.
  • Evaluation = reduction: a simplification process yielding the value / normal form. Notation e → e′. The meaning of an expression is its value.
  • Unicity of normal forms — value determined by the components, independent of the order of reduction.
  • Non-termination — not all reduction sequences lead to a value. fortytwo infinity: some sequences diverge, those that terminate give 42.
  • Call-by-name (normal order): application first, then argument. Always finds the value if one exists.
  • Call-by-value (applicative order): argument first. More efficient in general, but may fail.
  • lazy = call-by-name + sharing — Haskell's strategy; defers evaluation until results are needed.
  • f : A → B, domain A, codomain B; (f x) :: B.

W6 · Definitions & currying

  • 3 styles: plain equation · guarded (conditional) equations · pattern matching.
  • Pattern order matters — arguments compared against definitions in the order provided, until a match or the patterns are exhausted.
  • Conditional semantics: evaluate the condition, then only the chosen branch. This is why recursion terminates.
  • error — predefined, takes a string, terminates the evaluator immediately and displays it.
  • Application: precedence over other operations · associates left (square square 3 = (square square) 3) · outer brackets omitted.
  • where / let … in — local definitions, available only on the RHS. Evaluate e′ → replace a by r → evaluate e{a↦r}.
  • Operators are functions: infix by default, prefix in brackets (+) 3 4; (+) is the curryfied +; quote to make prefix functions infix: 10 `div` 2. + - * / left associative.
  • Composition: (·) :: (b→c) → (a→b) → (a→c), (f·g) x = f (g x). Itself a function. Only matching types compose — g runs first.
  • Currying: functions take no more than one argument; applying to n>1 yields a function of n−1 ⇒ partial application. plus 3 :: Int → Int.
  • Tuples don't curry — one argument, no intermediate stage. Convert with curry :: ((a,b)→c)→(a→b→c) and uncurry.
  • Lists: !! indexes from 0 · : is cons · zipWith f l1 l2 pointwise.

W8 · Types & polymorphism

  • Values divided into types, each associated with a set of operations; given explicitly or inferred.
  • Static (C, C++, Java, Haskell) vs dynamic (Python, JavaScript, PHP).
  • Untypeable expressions are rejected without evaluation. ✓ early errors ✓ types as specification. Passing type checks ≠ correct, but ⇒ no type errors at runtime.
  • Haskell types: basic · constructed (tuples, lists, strings) · function. The arrow associates right.
  • Monomorphic = at most one type per expression; polymorphic = some have more than one.
  • T ::= V | C(T₁,…,Tₙ); a polymorphic type represents the set of its instances.
  • error :: String → a — must be polymorphic, since all branches of a definition share a type.
  • Overloading = ad-hoc polymorphism: same name, different types. (+) :: a→a→a is too general ('a'+'b'). Fixes: different names · enrich types with ∧ · type classes Num a ⇒ a→a→a.
  • Inference: most general type; combination gives constraints; unsolvable ⇒ untypeable. square :: Num c ⇒ c → c. square square 3 fails because Int = (Int→Int) has no solution.

W8 · Lists & user-defined types

  • [] :: [a] · (:) :: a→[a]→[a] · head :: [a]→a · tail :: [a]→[a]. Strings are lists of characters.
  • data Nat = Zero | Succ Nat · data Seq a = Empty | Cons a (Seq a).
  • Data constructors build terms; type constructors define new polymorphic types (Seq).
  • data Tree a = Leaf a | Branch (Tree a) (Tree a); height via pattern matching + local max.
  • Structural induction: one case per constructor. For Nat it is mathematical induction: (P(0) ∧ ∀n.(P(n)⇒P(n+1))) ⇔ ∀n.P(n).
  • Prove add n Zero = n and sumNat n = n(n+1)/2.

W8 · SFUN semantics & typing

  • SFUN = small, first-order functional language over ints and Booleans. Configurations are just terms — no store.
  • Program = set of recursive equations; vars(dᵢ) ⊆ parameters; one equation per function name. Closed term = no variables.
  • Big-step ⇓P rules: (n) (b) (op) (bop) (and) (not) (ift) (iff) and the application rule.
  • fnval — n+1 premises, substitutes values: arguments evaluated first.
  • fnname — one premise, substitutes unevaluated terms. Only this rule changes.
  • fortytwo(infinity): no derivation under CBV, ⇓ 42 under CBN. square(2+1): 2+1 evaluated once under CBV, twice under CBN.
  • Determinism (both strategies): t ⇓ v₁ ∧ t ⇓ v₂ ⇒ v₁ = v₂, by rule induction; only one rule applies to any term.
  • Types: β ::= int | bool; τ ::= (β₁,…,βₙ)→β; n = 0 written β. No arrows inside — first-order, so no currying.
  • Γ ⊢ε t : τ — Γ: variables → base types; ε: function names → types respecting arity. ⟨f⟩ = 0 makes the application rule an axiom; both if branches need the same τ.
  • P typeable iff for each equation there are Γᵢ, τᵢ typing both sides. infinity is typeable but never terminates.

W9 · Logic programming basics

  • Logic expresses knowledge / describes the problem; inference computes the solution.
  • ✓ knowledge-based · declarative · precise simple semantics · one formalism for spec/program/proof · the same program used many ways ← only this last one is specific to LP.
  • No input/output variables — reverse answers X in either position, or with none at all.
  • ✗ efficient arithmetic and I/O cost the declarative semantics; ✗ restricted to a fragment of classical FOL.
  • Prolog: Colmerauer & Roussel, early 1970s · NLP and AI · syntax = clausal fragment of FOL · semantics = SLD-resolution with automatic backtracking · impure.
  • Term = a variable, or f(t₁,…,tₙ) with f of arity n (constants have arity 0).
  • Atomic formula p(t₁,…,tₙ); literal = A or ¬A. Only terms can be arguments of predicates.

W9 · Clauses & substitutions

  • Horn clause = disjunction of literals, at most one positive. Definite clause = exactly one positive.
  • Fact single positive · Rule positive + negatives · Goal only negatives, :- B₁,…,Bₙ.
  • A ∨ ¬B₁ ∨ … ≡ (B₁∧…∧Bₙ)→A, read backwards as A :- B₁,…,Bₙ.
  • Programs = sets of definite clauses. Facts before rules. X-1 can't be passed directly — bind it with is.
  • All clauses are universally quantified on all their variables.
  • Substitution = partial map variables → terms, finite domain; σ = {X₁↦t₁,…}; dom(σ). Only variables get replaced.
  • Applied simultaneously — {X↦Y, Y↦a} must not become X↦a. Variables not in t are unaffected.
  • Order matters twice: clauses in program order; the selection function picks the leftmost literal. Answers are a by-product of resolution.

W9 · Built-ins, lists, limitations

  • Built-ins: operators · is · call/1 fail/0 !/0 · ',' · =.. · write, nl. Notation p/n.
  • Lists: [] · [X|L] cons · [X,Y,Z]. [] matches only the empty list, [H|T] only non-empty. member/2 length/2 sort/2.
  • append([],L,L). append([X|L],Y,[X|Z]) :- append(L,Y,Z). — forwards, failing, and infinitely many solutions.
  • No negative facts, no negative heads — definite clauses have exactly one positive literal.
  • Resolution rule: from A∨B and ¬A∨C infer B∨C. Unrestricted, clauses resolve in multiple ways and the next pair must be chosen arbitrarily.
  • Restricting to definite clauses makes resolution Selective (unique & deterministic) and Linear (resolvent is empty or a new goal) — with Definite, that's SLD.
  • Negation as failure \\+ — failure to prove A is taken as proof of ¬A (closed-world assumption).
  • Disjunction A∨B can't be represented: adding both facts gives the stronger A∧B; rewriting with \\+ doesn't behave like true disjunction.

W10 · Unification

  • Problem U = set of equations between terms. Unifier σ makes sᵢσ and tᵢσ syntactically identical. mgu = a unifier of which every other unifier is an instance.
  • {X↦Y} is more general than {X↦a, Y↦a}: compose with {Y↦a} to get ρ, but not conversely.
  • Why generality matters: committing a variable to a constant early blocks later resolutions — leave variables free unless binding is needed.
  • (1) f(s̄)=f(t̄) → s₁=t₁,…,sₙ=tₙ  (2) f≠g → failure  (3) X=X → delete
  • (4) t=X (t not a var) → X=t  (5) X=t, X∉t, X in E → substitute X↦t in E  (6) X occurs in t, X≠t → failure (occur-check)
  • (1) and (2) apply to constants too (arity 0). Occur-check is costly, so some systems omit it.
  • Success: change each = to ↦. U is a set — order is unimportant.

W10 · SLD-resolution

  • Principle: prove :- G₁,…,Gₙ by showing P ∪ {¬G₁∨…∨¬Gₙ} leads to a contradiction. Derived goals = resolvents.
  • Selective (a fixed computation rule picks the atom) · Linear (the most recent resolvent is the next goal) · Definite (all program clauses definite).
  • ✓ refutation-complete · ✓ independence of the selection rule.
  • Resolvent: select Gᵢ, unify with a clause head via mgu σ, replace Gᵢ by the body, apply σ throughout. Answer = composition of the σ's, restricted to the query's variables.
  • Prolog: left-most literal, clauses top-to-bottom, depth-first. SLD-resolution is complete but Prolog's implementation is not — it can get stuck in an infinite branch.
  • Tree: nodes = goals, edges labelled with mgus, children left-to-right in program order, failed unifications not drawn, □ = success, dead end = failure. Branches may be success, failure or infinite.
  • Back-tracking: failure branches automatically, success branches on request; cut ! = do not back-track beyond this point.
  • Clause order: base clauses before recursive ones — the reversed append gives an infinite left-most branch and no solutions.
  • Variable renaming is required: {[X|Y]=Y,…} fails the occur-check. Legitimate because clause variables are universally quantified; rename uniformly, avoid symbols already in the clause, carry bindings back to the goal.

Cross-cutting threads

  • The three components reappear as the compiler's phases: parsing = syntax, type analysis = static semantics, code gen = dynamic semantics.
  • Trees, not strings — abstract syntax exists so that SOS rules can be defined "in terms of its components".
  • An interpreter is a machine in software — the same idea returns as the abstract machine.
  • Non-determinism is a bug for imperative execution but a feature for logic programming search (Prolog, later).
  • The dangling else is W1's ambiguity problem inside a real language — same string, two parse trees. Abstract syntax dissolves it.
  • Blocks do double duty: they scope declarations and disambiguate nested selectors.
  • W2 describes constructs informally; SIMP gives them a formal operational semantics using W1's transition systems.
  • l-value / r-value (W2) becomes syntax in W3: l := !l − 1. The assignment rule is the distinction made mechanical.
  • W1's terminal configuration (no outgoing →) is W3's ⟨nil, nil, m⟩; a stuck configuration (undefined location, division by zero) is non-final with no successor.
  • Determinism (W1) is what makes the machine an interpreter: exactly one rule matches each configuration.
  • Abstract syntax = the induction principle. W1 made programs trees; W4 uses exactly those leaves and constructors as the base cases and induction steps.
  • Three semantics for one language: abstract machine (W3) · small-step · big-step (W4). All agree on the final store; they differ in granularity and in what they can express about failure.
  • W2's static scope becomes W4's block rule: a fresh location, a renaming, and a discard on exit.
  • Evaluation order, unspecified in C, is pinned down three times over: op-decomp order (W3), the n₁ in the R rules (W4 small-step), and store threading s→s′→s″ (W4 big-step).
  • e → e′ is the same arrow throughout. Functional evaluation (W6) is a small-step semantics with no store — a configuration is just an expression, because nothing can be assigned to.
  • Evaluation order, one more time: C left it open (W3), SIMP's rules pinned it down (W3–W4), and W6 makes it a choice — the strategy — with real consequences for termination.
  • Scope recurs: Pascal blocks (W2) → SIMP's begin loc rule (W4) → where / let … in (W6). Always: a local name, a delimited region, gone afterwards.
  • SIMP vs SFUN — both get a big-step semantics in the same style, but SIMP's configurations are ⟨P, s⟩ and SFUN's are just terms. Removing the store is exactly what "no side effects" means formally.
  • "No derivation exists" means the same thing in W4 and W8: divergence and stuckness are both just the absence of a finite proof tree.
  • Induction, three times: mathematical (W4) → structural over abstract syntax (W4) → structural over a data declaration (W8). Always one case per constructor.
  • Goals are configurations. Prolog's "informal procedural mechanism" is a transition system in W1's sense — one step replaces the selected literal by a clause body under a substitution.
  • Substitution runs through the whole course: SIMP's m[l ↦ n], SFUN's dᵢ{x ↦ v}, SOS's C{x ↦ l}, and Prolog's σ. Always variables replaced by terms, always simultaneous.
  • Three paradigms, three notions of "answer": imperative = the final store · functional = the normal form · logic = the bindings that made the proof work.
  • Complete ≠ complete implementation. SLD-resolution finds every solution; Prolog's depth-first search need not. Compare W6: call-by-name always finds the value, call-by-value need not. Same shape of result, twice.
  • Order sensitivity is the recurring practical trap: pattern order in Haskell (W6), equation order in SFUN, clause order in Prolog (W10). In each case the declarative reading is order-free and the implementation is not.
  • Renaming apart — SIMP's fresh l in the block rule (W4) and Prolog's clause renaming (W10) solve the same problem: accidental capture of names.
  • Trees everywhere: parse trees (W1) · derivation trees for ⇓ (W4, W8) · SLD-resolution trees (W10). All are proofs; a missing tree always means "no derivation exists".
  • Course order: imperative (SIMP + transition systems) → functional + type systems → logic (Prolog).
