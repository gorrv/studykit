Functional Programming: Types & Semantics

what a type is, and what a functional program means

Two halves that mirror Part 1 exactly. 7.1–7.2 are about types — Haskell's, polymorphic ones, and how they're inferred. 7.3–7.4 build a formal semantics for a small functional language SFUN, in the same structural operational style used for SIMP in Topic 04.

Typing: static vs dynamic

What types are for
Types help to ensure that a program behaves in a precise, pre-determined way. Values are divided into classes, called types, and each type is associated with a set of operations.

Types may be given explicitly by the programmer or inferred automatically by the type system.

Checking that types are being used in the correct way is sometimes referred to as typing. Typing may be checked before execution (static typing) or during execution (dynamic typing).

Statically typed

C, C++, Java, Haskell

Dynamically typed

Python, JavaScript, PHP

Topic 02 already told you this
The static/dynamic typing distinction appeared in Topic 02 as one of the four properties of a variable ("some languages are untyped, others statically typed — Java, Haskell, ML, Scala — or dynamically typed — Python, Ruby"). Same distinction, now with the consequences spelled out.
Static typing — the claims to quote
Every valid expression must have a type. Expressions that cannot be "typed" are considered erroneous and are rejected by the compiler without evaluation.

Advantages:

  • Types help detecting errors at an early stage.
  • Types help in the design of software, since they are a simple form of specification.

A program that passes the type controls is not guaranteed to be correct, but it is free of type errors at runtime. — memorise this sentence; it's the honest statement of what types do and don't buy you.

Polymorphism

The definition
Type systems can be:
  • monomorphic, where every expression has at most one type, or
  • polymorphic, where some expressions have more than one type.

The standard example is functional composition, where a, b and c are type variables:

(.) :: (b -> c) -> (a -> b) -> (a -> c)

Formally, the language of polymorphic types is defined as a set of terms built out of type variables (a, b, c, …) and type constructors, which are either atomic (Integer, Float, …) or take arguments (e.g. T₁→T₂, [T]):

V ::= a, b, c …
C ::= Int, Bool, Char, →, [ ], ( ) …
T ::= V | C(T₁, T₂, … Tₙ)
A polymorphic type represents the set of its instances, obtained by substituting type variables by types.
Type variables aren't a Haskell peculiarity
They already exist in C++ as templates:
template<typename A, typename B> pair<B,A> flip_pair(const pair<A,B> &p) { return pair<B,A>(p.second, p.first); };

Instantiating type variables — the composition example

From square :: Integer → Integer and sqrt :: Integer → Float, we can infer the types of two different compositions using the signature of (.):

quad = square · square
-- a, b, c all instantiated to Integer (·) :: (Integer → Integer) → (Integer → Integer) → (Integer → Integer) quad :: Integer → Integer
sqrt · square
-- b = Integer, c = Float, a = Integer (·) :: (Integer → Float) → (Integer → Integer) → (Integer → Float) sqrt · square :: Integer → Float

Same (.), two different instances. That's exactly what "a polymorphic type represents the set of its instances" means in practice. (The composition type checker in Topic 05 does this calculation for you.)

error is polymorphic too

error :: String → a fact :: Integer -> Integer fact n | n > 0 = n * (fact (n - 1)) | n == 0 = 1 | n < 0 = error "negative argument"

Here the function error is used with type String → Integer.

Why error :: String → a has to be polymorphic
Every guarded branch of a definition must have the same type. The other two branches of fact return Integer, so the third must too. Since error never actually returns a value, it can honestly claim any result type — and the type variable a is instantiated to whatever the surrounding context needs.

Overloading (ad-hoc polymorphism)

Definition
Overloading is a related notion (also called ad-hoc polymorphism) where several functions, with different types, share the same name. This is useful when we want to use the same operation for distinct types — which may even "look" similar but may be represented differently internally.

The problem it solves: in Haskell we may want addition for both integers and reals. But a polymorphic type such as

(+) :: a → a → a

is too general: it would allow addition to be used with any type, e.g. characters. Whereas 1 + 2 and 1.05 + 2.55 make sense, 'a' + 'b' does not!

Different symbols/names per type

Some languages use different symbols or names for operations on specific types — + and +. in Caml; div 2 3 and 2 / 3 in Haskell.

Enrich the language of types

Allow a function to have several types at once:
(+) :: (Integer → Integer → Integer) ∧ (Float → Float → Float)

Type classes — Haskell's answer

(+) :: Num a ⇒ a → a → a
That is, (+) has type a → a → a where a is in the class Num.

The idea in one line
A type class is a constraint on a type variable — polymorphism that is general, but not unrestrictedly general. a → a → a allows characters; Num a ⇒ a → a → a allows exactly the types that have numeric operations.

Type inference

Most modern functional languages do not require that the programmer provides the type for the expressions used. The compiler is able to infer a type, if one exists.

How inference works — three bullets worth learning
  • The type of a complex expression is inferred using the operations used in the expression and the type of its atomic constituents, assigning the most general type possible.
  • The way the different components are put together to form the expression indicates the constraints that the type variables must satisfy.
  • If the constraints cannot be solved, the inference fails and the expression is deemed untypeable.

The type of an expression only depends on its components.

Example 1 · inferring the type of square x = x * x

It is a function, so the most general type is a → b.
Using square's definition, x :: a and x * x :: b.
We know that (*) :: Int -> Int -> Int is a primitive function.
Therefore, if x :: Int, then x * x :: Int, and then both a and b must be of type Int.
Therefore, square :: Int -> Int.

Example 2 · can we find a more general type?

The most general type of (*) is Num c => c -> c -> c.
So if x :: Num c => c, then x * x :: Num c => c.
We now have the constraints a = (Num c => c) and b = (Num c => c) on the domain and co-domain of square…
…which we solve by instantiating a with Num c => c and b with Num c => c.
Therefore, square :: Num c => c -> c.

Example 3 · when inference fails

Given that square :: Int -> Int, what is the type of square square 3?

The answer, and the reason
Remember that application associates to the left, so the expression reads (square square) 3.

So the first square expects an argument of type Int, but it is given an argument of type (Int -> Int), and the expression cannot be typed. This is because the constraint Int = (Int -> Int) cannot be solved.

Topic 05 flagged this exact expression
There it was a syntactic trap about left-associativity. Here it's the same trap seen through the type system — and the type system is what actually catches it. Notice the shape of the failure: not "this looks wrong" but "this equation between types has no solution". That's what type inference always reduces to.

Finding the most general type — the method

The recipe, in five steps
  1. Give every unknown a type variable. If it's a function of n arguments, start from a₁ → a₂ → … → r. Each parameter and each sub-expression gets its own fresh variable.
  2. Write down the type of every primitive you used, at its most general type — (*) :: Num c ⇒ c → c → c, not Int → Int → Int.
  3. Read off a constraint from every application. If f is applied to x and the result is r, then f's type must equal (type of x) → r.
  4. Solve the constraints by unification. This is the same unification you did for Prolog — same occur check, same clashes.
  5. Read off what survives. Any variable still unconstrained stays a variable. Any class constraint still sitting on a variable becomes the context before the ⇒.
Worked: \x y z -> x + y + z
assume  x :: a,  y :: b,  z :: c,  result :: r
(+) :: Num t ⇒ t → t → t

from x + y  →  a = t,  b = t,  so (x+y) :: t
from (x+y) + z  →  t = t,  c = t,  r = t

everything collapses to one variable, carrying Num
⇒ Num a ⇒ a → a → a → a

Notice the shape of the answer: three arrows for three arguments, then the result — and because + forces all four to be the same type, they are all a.

The four mistakes that cost marks
  1. Answering Int → Int when Num a ⇒ a → a is available. This is exactly Example 2 above — Int is a type, not the most general one. If the only thing you used was arithmetic, you owe a Num context.
  2. Forgetting the context altogether. a → a → Bool is wrong for \x y -> x == y; it needs Eq a ⇒.
  3. Making variables equal when nothing forces it. \x y -> x is a → b → a, not a → a → a — nothing ever compares x with y.
  4. Bracketing the arrows wrongly. → is right-associative, so a function argument must be bracketed: (a → b) → [a] → [b]. Writing a → b → [a] → [b] is a different type entirely.

User-defined types

Definition
We can define our own new types by declaring the data constructors and type constructors of that type.
data Nat = Zero | Succ Nat

Here Nat is a new type and Zero and Succ are its data constructors.

data Seq a = Empty | Cons a (Seq a)

Here Seq a is a new polymorphic, recursive type whose elements are built using one of the data constructors Empty or Cons. Type constructors define new polymorphic types — Seq is a type constructor.

Data constructors are used to build terms of a type:

Zero :: Nat (Succ (Succ Zero)) :: Nat Empty :: Seq a (Cons (Succ Zero) Empty) :: Seq Nat

Data constructors can be used when giving definitions by pattern matching:

isempty Empty = True isempty (Cons x y) = False

Structural induction over recursive types

The principle, instantiated for Nat
To reason with recursive types we use the Principle of Structural Induction. For Nat, to prove a property P for all elements:
  1. Prove P(Zero) — the base case of the induction.
  2. Prove that if P(n) holds — the induction hypothesis — then P(Succ n) holds.

This is the familiar Principle of Mathematical Induction:

(P(0) ∧ ∀n.(P(n) ⇒ P(n + 1)))  ⇔  ∀n.P(n)
This is Topic 04, arriving from the other direction
Topic 04 derived structural induction from mathematical induction, by induction on the size of a tree. Here the point is made in reverse: the data Nat = Zero | Succ Nat declaration is Peano arithmetic, so induction over that type is mathematical induction. Once again: the data declaration gives you the induction principle — one case per constructor.

Worked example: Zero is a neutral element

Addition on Nat, by pattern matching:

add Zero x = x add (Succ x) y = Succ (add x y)

Prove by induction that for all Nat numbers n:  add n Zero = n.

1 · Base case
To prove add Zero Zero = Zero we use the definition of add.
2 · Induction
By definition of add:  add (Succ n) Zero = Succ (add n Zero)
…which is equal to Succ n, by the induction hypothesis.

SFUN: a small functional language

The plan
We give a precise, formal description of the behaviour of functional programs using transition systems. The language is a small, first-order functional programming language working on integers and Booleans, called SFUN. We define its syntax, then give its semantics using the structural operational semantics approach.

Recall the two strategies: call-by-value (arguments evaluated before applying function definitions) and call-by-name (function definitions applied before evaluating arguments). First a call-by-value semantics, then the modification needed for call-by-name.

Let V be a set of variables {x, y, z, …} and F a set of function names {f₁, f₂, …}, each with a fixed arity ⟨fᵢ⟩. The terms of SFUN:

op ::= + | − | ∗ | /        bop ::= > | < | = | ≤ | ≥

t ::= n | b | x | t₁ op t₂ | t₁ bop t₂ | ¬t₁ | t₁ ∧ t₂
     | if t₀ then t₁ else t₂ | f(t₁, …, t⟨f⟩)
where n represents an integer value, n ∈ ℤ, and b a Boolean value, b ∈ {True, False}.
Compare with SIMP (Topic 03) — the differences are the point
  • No commands, no assignment, no store. A configuration is just a term.
  • Variables are function parameters, not memory locations — so there is no !l, and no l-value/r-value distinction.
  • First-order: functions are named and applied to a fixed number of arguments; you cannot pass a function as an argument. So SFUN has no currying, unlike Haskell.

vars(t) denotes the variables occurring in the term t — e.g. vars(x) = {x}, vars(f(y, z)) = {y, z}. A closed term is one with vars(t) = ∅, i.e. containing no variables.

Programs in SFUN

Definition
A program in SFUN is a set of recursive equations
f₁(x₁, …, x⟨f₁⟩) = d₁
⋮
fk(x₁, …, x⟨fk⟩) = dk
such that:
  • d₁, …, dk are terms,
  • vars(dᵢ) ⊆ {x₁, …, x⟨fᵢ⟩} for all i — a body may only use its own parameters,
  • there is only one equation for each function name fᵢ.

Equations may be recursive: the terms dᵢ may contain occurrences of f₁, …, fk.

"Only one equation for each function name"
This is a real restriction compared with Haskell, where fact 0 = 1; fact n = … is idiomatic. In SFUN you must use an explicit if instead — which is exactly why every example program below is written with conditionals.

The example programs given:

max(x, y) = if x ≥ y then x else y fact(x) = if x ≤ 0 then 1 else x ∗ fact(x − 1) square(x) = x ∗ x quadratic(x, a, b, c) = a ∗ square(x) + b ∗ x + c mod(x, y) = if x − y < 0 then x else mod(x − y, y) even(x) = mod(x, 2) = 0 collatz(x) = if x = 1 then 1 else if even(x) then x/2 else 3 ∗ x + 1

Call-by-name: one rule changes

fnval requires that the arguments given to the function are evaluated before the function is applied. That becomes problematic or inefficient for terms such as fortytwo(infinity) or fortytwo(2354²). To model call-by-name we replace it with:

dᵢ{x₁ ↦ t₁, …, x⟨fᵢ⟩ ↦ t⟨fᵢ⟩} ⇓P v
fnname
fᵢ(t₁, …, t⟨fᵢ⟩) ⇓P v
Spot the difference — it is worth one whole exam answer
fnval substitutes values v₁ … vn and needs n + 1 premises. fnname substitutes the unevaluated terms t₁ … tn and needs one premise. That single change gives you:
  • fortytwo(infinity) ⇓P 42 — the argument is discarded without being evaluated.
  • but repeated computation when an argument is used more than once.

The system remains deterministic: for any closed term t, if t ⇓P v₁ and t ⇓P v₂ then v₁ = v₂ (by rule induction).

Determinism: unicity of normal forms

Theorem
The evaluation strategy defined by the axioms and rules is deterministic: for any closed term t, t ⇓P v₁ and t ⇓P v₂ implies v₁ = v₂.  Proof: by rule induction.

The proof distinguishes cases according to the rule that applies to t — for any term, there is only one rule that can be applied.

Base cases (axioms)
If t is an integer n then n ⇓P n using the axiom (n).
If t is a Boolean b then b ⇓P b using the axiom (b).
Therefore there is only one value in both cases. There are no more base cases, because t is closed and thus cannot contain variables.
Inductive cases (rules)
Assume t is the term f(t₁, …, t⟨f⟩).
Then, using fnval,  fᵢ(t₁, …) ⇓P v  if and only if  t₁ ⇓P v₁, …, and dᵢ{x₁ ↦ v₁, …} ⇓P v.
By the induction hypothesis, there is at most one value for each term t₁, …, tn and for dᵢ{…}.
Therefore v is uniquely determined.
The cases corresponding to the other rules are similar.
Note what determinism does not say
It says a term has at most one value — not that it has one. infinity has none under either strategy; fortytwo(infinity) has none under CBV but 42 under CBN. Determinism is about uniqueness, and it holds for both strategies separately; it does not mean the two strategies agree.

Types for SFUN

The grammar defining the syntax of SFUN allows us to build terms such as 1 + True which do not make sense. In the definition of the semantics we only considered well-typed terms. The base types β and the types τ of SFUN:

β ::= int | bool
τ ::= (β₁, …, βₙ)→β
In the case of a type τ such that n = 0 (the type of a function with no arguments), τ may be written simply as β.
SFUN types are not Haskell types
There is no arrow inside a base type: an SFUN function type is a single flat (β₁,…,βₙ)→β, so functions are not values and cannot be arguments. That's what "first-order" means, and it's why there is no currying here — contrast Int → Int → Int in §7.1.
The well-typedness relation Γ ⊢ε t : τ
  • Γ is a variable environment — a finite partial function from variables to base types.
  • ε is a function environment assigning to each function name a type respecting its arity: if ⟨f⟩ = 0 then ε(f) = β, and if ⟨f⟩ = n ≥ 1 then ε(f) = (β₁,…,βₙ)→β.
  • t is an SFUN term and τ is a type.

Read it as: "If the variable x has type Γ(x) for each x ∈ dom(Γ), and the functions f₁,…,fk have types ε(f₁),…,ε(fk), then the term t has type τ."

Two details the lectures point out explicitly
  • In the rule for applying a function f, if ⟨f⟩ = 0 the rule reduces to an axiom, because there are no arguments to check.
  • In the if rule, both branches must have the same type τ — and τ can be either base type. That's the rule that made error :: String → a necessary back in §7.1.

Typing SFUN programs

Definition
Given a program P with equations fᵢ(x₁, …, x⟨fᵢ⟩) = tᵢ and a function environment ε, P is typeable if for each equation there exists an environment Γᵢ and a type τᵢ such that:
  • Γᵢ ⊢ε fᵢ(x₁, …, x⟨fᵢ⟩) : τᵢ
  • Γᵢ ⊢ε tᵢ : τᵢ

In words: the left-hand side and the right-hand side of every equation must get the same type.

For the running program P — infinity = infinity + 1, fortytwo(x) = 42, square(x) = x ∗ x — with ε(infinity) = int, ε(fortytwo) = (int)→int, ε(square) = (int)→int:

Verdict
P is a typeable program. All the equations are typeable with type int — the first in an empty environment, and the latter two using an environment Γ such that Γ(x) = int.
Typeable ≠ terminating
infinity = infinity + 1 is perfectly well-typed and has no value at all. This is the concrete version of §7.1's warning: "a program that passes the type controls is not guaranteed to be correct, but it is free of type errors at runtime." Types rule out 1 + True; they do not rule out non-termination.

Proving properties of SFUN programs

We can use proof by induction on SFUN programs directly. Given fact(x) = if x ≤ 0 then 1 else x ∗ fact(x − 1), prove that fact(n) = n! for all natural numbers n.

Base case (n = 0)
Show fact(0) = 0! = 1.
By the definition of fact(x), 0 ≤ 0 evaluates to True, and then by the left-hand side of the conditional, fact(0) = 1, as expected.
Induction hypothesis
Assume fact(n) = n!
Induction step
Show that fact(n + 1) = (n + 1)!
n + 1 ≤ 0 will evaluate to False. By the right-hand side of the conditional,
fact(n + 1) = (n + 1) ∗ fact((n + 1) − 1)  =  (n + 1) ∗ fact(n)
By the inductive hypothesis, this is equal to (n + 1) ∗ n!, which is simply (n + 1)!

Exam-style takeaways

Key things to nail for Topic 06
  1. What types are — values divided into classes, each type associated with a set of operations; given explicitly or inferred.
  2. Static vs dynamic typing — checked before vs during execution. Static: C, C++, Java, Haskell. Dynamic: Python, JavaScript, PHP.
  3. Static typing claims — every valid expression must have a type; untypeable expressions are rejected without evaluation. Advantages: early error detection; types as a simple form of specification. Passing type controls ≠ correct, but ⇒ free of type errors at runtime.
  4. Haskell's three kinds of type — basic, constructed (tuples, lists, strings), function. The arrow associates to the right.
  5. Monomorphic vs polymorphic — every expression has at most one type, vs some expressions have more than one.
  6. The grammar of polymorphic types — V (variables), C (atomic or argument-taking constructors), T ::= V | C(T₁,…,Tₙ). A polymorphic type represents the set of its instances.
  7. Instantiation in practice — derive the types of square · square and sqrt · square from (.). Know error :: String → a and why it must be polymorphic.
  8. Overloading = ad-hoc polymorphism — several functions with different types sharing a name. Why (+) :: a → a → a is too general ('a' + 'b'). The three solutions: different names per type; enrich the type language with ∧; type classes, (+) :: Num a ⇒ a → a → a.
  9. Type inference — most general type; constraints from how components combine; unsolvable constraints ⇒ untypeable. The type of an expression only depends on its components.
  10. Run the inference for square x = x * x both ways — Int -> Int and the more general Num c => c -> c.
  11. square square 3 is untypeable — application associates left, so it is (square square) 3, and the constraint Int = (Int -> Int) cannot be solved.
  12. List primitives and their types — [] :: [a], (:) :: a -> [a] -> [a], head :: [a] -> a, tail :: [a] -> [a]. Strings are lists of characters.
  13. Write list functions by pattern matching — size, take', elem', and give their types.
  14. User-defined types — data Nat = Zero | Succ Nat; data Seq a = Empty | Cons a (Seq a). Distinguish data constructors (build terms) from type constructors (define new polymorphic types). Be able to write the Tree/height answer.
  15. Structural induction for a recursive type — one case per constructor; for Nat it is mathematical induction. Prove add n Zero = n, and sumNat n = n(n+1)/2.
  16. SFUN syntax — the term grammar; arity ⟨f⟩; vars(t); closed term; a program is a set of recursive equations with vars(dᵢ) ⊆ parameters and one equation per function name.
  17. The call-by-value rules — (n), (b), (op), (bop), (and), (not), (ift), (iff), (fnval). Configurations are just terms; values are integers and Booleans.
  18. The call-by-name rule — (fnname) substitutes the unevaluated terms and has a single premise. Know that only this rule changes.
  19. Build derivations by hand — fortytwo(0), square(2 + 1) under both strategies, and max(3, square(2)) under both. Note CBV evaluates 2 + 1 once, CBN twice; and CBV gives fortytwo(infinity) no value while CBN gives 42.
  20. Determinism — t ⇓P v₁ and t ⇓P v₂ implies v₁ = v₂, by rule induction; be able to give the base cases and the fnval inductive case. Holds for both strategies.
  21. SFUN types — β ::= int | bool; τ ::= (β₁,…,βₙ)→β; n = 0 written as β. First-order: no arrows inside base types.
  22. Γ ⊢ε t : τ — Γ maps variables to base types, ε maps function names to types respecting arity. Be able to read the relation aloud.
  23. Reproduce the typing rules and build derivations — the fact body and max(3, square(2)). Remember both branches of an if must have the same τ, and ⟨f⟩ = 0 makes the application rule an axiom.
  24. Typeable programs — for each equation there are Γᵢ, τᵢ with both the left-hand side and the body typeable at τᵢ. P is typeable even though infinity never terminates.
  25. Prove fact(n) = n! by induction directly on the SFUN program.
