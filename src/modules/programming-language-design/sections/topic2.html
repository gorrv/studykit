Topic 02 · Imperative Languages — Informal Description

Variables & Flow of Control

the informal pass, before SIMP makes it formal

Topic 01 ended with a promise: describe the constructs of imperative languages informally first, then give a formal specification using transition systems. This topic is the informal half. Everything here gets a precise operational semantics in the topics that follow, using the language SIMP.

The three aims of this topic
  1. Distinguish the main components of an imperative language.
  2. Identify the main attributes of variables, and the advantages and disadvantages of different design choices.
  3. Identify the main control structures, and the differences between apparently similar constructs used in different languages.

Aims 2 and 3 both say the same thing in different words: this topire is a catalogue of design trade-offs. Exam questions here are rarely "what is X" — they're "what are the advantages and disadvantages of X", or "these two constructs look the same; how do they differ?"

Imperative languages and the Von Neumann architecture

The founding sentence
Imperative languages are abstractions of the underlying Von Neumann computer architecture.

One of the main components of the computer is its memory, storing instructions and data. In imperative languages, variables represent memory cells.

That one correspondence explains the shape of the whole paradigm. If a variable is a memory cell, then a program is a sequence of instructions that change the contents of cells — which is exactly the definition of "imperative" from Topic 01 (programs decomposed into computation steps, reflecting the computer architecture).

So to understand the behaviour of programs we need to know two things — and they are the two halves of this topic:

Part 1 · Variables

The properties of variables — what they are, where they live, how long they live, and where they can be seen.

Part 2 · Flow of control

The flow of control among instructions — selection, iteration, branching, and how programs are structured.

Variables: the four main properties

Name

Usually a string of characters with some constraints — e.g. maximal length, allowed characters.

Type

Indicates the range of values that are allowed, as well as the operations that are available. Some languages are untyped; others are statically typed (Java, Haskell, ML, Scala) or dynamically typed (Python, Ruby).

Address — the l-value

The memory address to which the variable is associated. This association is not simple: the same name may be associated with different addresses in different parts of the program; and in some languages more than one name can be associated with the same address — e.g. variant records in Pascal, the EQUIVALENCE statement in Fortran.

Value — the r-value

The contents of the memory associated with the variable.

Type does two jobs, not one
Students routinely write "the type is the kind of value". The definition says two things: the range of values allowed and the operations that are available. Both halves earn marks. (It also explains Topic 01's 1 + 'a': + is not among the operations available on characters.)

l-value vs r-value — the distinction that explains assignment

The names come from the two sides of an assignment. In x = y:

l-value · the address

What appears on the left. We need to know where to put something — the memory address associated with the variable.

r-value · the value

What appears on the right. We need to know what is stored there — the contents of that memory.

So x = y means: take the r-value of y and store it at the l-value of x. The same variable name denotes a different thing depending on which side of the = it appears.

After x = y: the r-value of y (7) is written to the l-value of x (0x1000).

Why "this association is not simple" matters
Because the name→address link is not one-to-one in either direction, two of the hardest topics on the course follow directly from it:
  • One name → many addresses (over the program, or over time): this is why we need lifetime and scope. Each recursive call of a procedure gives its local x a fresh address.
  • Many names → one address (aliasing): Pascal variant records, Fortran EQUIVALENCE — and, in modern terms, two references to the same object. Writing through one name silently changes the other.

Lifetime: the four classes of variable

Definition
Lifetime = the time during which the variable is allocated a specific memory location — between allocation and deallocation.

We distinguish four classes of variables according to their lifetime: static, stack dynamic, explicit heap-dynamic, and implicit heap-dynamic. Learn the list, and learn one advantage/disadvantage pair for each.

1 · Static variables

Bound to a memory location before program execution begins, and until it ends.

AdvantageDisadvantage
✓ Efficiency — all addressing can be resolved at compile time; there is no allocation/deallocation at run time. ✗ Storage cannot be reused, and recursive programs need dynamic variables.
Why recursion forces the issue
A recursive procedure is active several times at once, and each activation needs its own copy of its local variables. One statically-fixed address per name simply cannot hold them all — hence the next class.

2 · Stack dynamic variables

Allocated when the declaration of the variable is processed at run time. The canonical example: local variables of recursive procedures.

3 · Explicit heap-dynamic variables

Nameless memory cells that are allocated and deallocated by program instructions, using pointers.

// C++ int *intnode; ... intnode = new int; /* allocates an int cell */ ... delete intnode; /* deallocates the cell to which intnode points */
The Java variant — worth quoting
In Java, objects are explicit heap dynamic and are accessed through reference variables, but there is no way to destroy them explicitly: implicit garbage collection is used.

Footnote: garbage collection was first introduced in Lisp.

Note the subtlety: the cells are nameless — intnode is not the heap cell, it's a pointer variable (itself typically stack dynamic) whose r-value is the address of the nameless cell. This is the l-value/r-value distinction doing real work.

4 · Implicit heap-dynamic variables

Bound to storage only when they are assigned values. E.g. strings and arrays in Perl and JavaScript.

AdvantageDisadvantage
✓ Flexibility ✗ Difficult error detection

📘 The pattern running down the table (background)
Read the four classes in order and you are watching a single dial being turned: binding time moves later and later — from before execution, to declaration-time, to explicit instruction, to first assignment. And with each step you trade the same two things: efficiency and checkability go down, flexibility goes up. If you can state that sentence you can answer almost any "advantages and disadvantages" question on this topic.

Scope: static vs dynamic

Definitions
Scope = the range of instructions in which the variable is visible (can be used).
  • Local variables are those declared in the block of program that is executed.
  • The variables that are visible but are not local are called global.

Some languages have static scoping rules, others have dynamic scoping rules.

Don't confuse scope with lifetime
They are different questions about the same variable. Lifetime is about time: when does this variable have memory allocated? Scope is about place in the program text: where can this name be used? A variable can be alive but invisible (a caller's local while a callee runs), which is exactly the situation dynamic scoping exploits.

Static scope

Can be determined before the execution of the program (at compile time). The rule:

When a variable is referenced, the compiler looks for its declaration in the same block;
if there is no declaration, it looks in the parent block;
…and so on outwards.

If no declaration is found, the compiler detects an error.
Static (lexical) scope resolution — it follows the nesting of the program text.

The example, in Pascal:

program main; var x : real; // main's x procedure P1; var x : integer; // local variable (P1's own x) begin ... x ... // LOCAL variable → P1's integer x end; procedure P2; begin ... x ... // GLOBAL variable → main's real x end; begin main ... x ... // GLOBAL variable → main's real x end.

P1 declares its own x, so the reference inside P1 is local. P2 declares nothing, so its x resolves outwards to main's — it is global. Crucially, this is true no matter who calls P2.

Dynamic scope

The definition, and the exam's favourite sentence
Dynamic scope depends on the calling sequence of subprograms instead of their declaration.

In the example above, with dynamic scope, the reference to x in P2 may refer to the variable in P1 or in main depending on who called P2.

Dynamic scoping — problems
✗ It is not possible to do static type-checking
✗ Programs are very difficult to understand

Why no static type-checking? Look at the example: under dynamic scope the x in P2 is an integer if P1 called it, and a real if main called it. The compiler cannot know which — the type of a reference depends on run-time control flow.

Who actually uses it
Some simple languages use dynamic scoping. Scripting languages such as Perl let the programmer choose static or dynamic scoping when defining a variable. Common Lisp did too — but later versions of Lisp (e.g. Scheme) are statically scoped.

Changing the values of variables: assignment

variable-name  =  expression
The warning
The = sign should not be confused with equivalence in the mathematical sense. Sometimes := is used instead (Pascal, Algol, and — later in this course — SIMP).

The value of the expression is stored in the variable, until a new value is given — either with another assignment or by a side-effect.

In typed languages, the expression and the variable must have compatible types.

Combining assignment with increment/decrement

The language C has a notation for combining assignment and increment. Both forms change the value of i to the current value plus 1 — but they return different things:

ExpressionEffect on iValue returned
i++ (post-increment)i becomes i + 1returns the value of i (the old value)
++i (pre-increment)i becomes i + 1returns the value of i + 1 (the new value)

There are also instructions combining assignment and decrement, written i-- and --i.

Why this belongs in a languages course
i++ is the cleanest small example of a side-effect: it is an expression (it has a value) that also changes the state. That dual nature is precisely what makes imperative semantics harder than functional semantics — and it's why, when we formalise SIMP, expressions and commands get treated separately.

Flow of control: control statements

Programs in imperative languages are sequences of instructions. The next instruction that will be executed is the one that follows in the text of the program — unless a control statement is used.

The main control statements are three:

Selection

choose a path

if-then-else, switch

Looping

repeat

for, while, do, repeat

Branching

jump

go-to

The theoretical claim — a very quotable line
Any sequential algorithm can be coded with just selection (if-then-else) and logically controlled iteration (while). Branching instructions (go-to) are superfluous.

All languages nevertheless contain more constructs to facilitate the writing of programs. Moreover, several statements can be grouped together to form a compound statement.

📘 Where that result comes from (background)
This is the structured program theorem (Böhm–Jacopini, 1966) and it is the reason "goto considered harmful" was a winnable argument — the construct wasn't just ugly, it was provably unnecessary. Note the shape of the claim: it's about expressive power, not convenience. Everything beyond if and while is syntactic sugar — which is also why, when we come to define SIMP formally, the language can be tiny and still be interesting.

Selection statements

Used to choose between two or more execution paths. We distinguish two-way selectors and multiple selectors.

Two-way selectors (if-then-else) — and the dangling else

Depending on the language, the semantics of nested selectors vary. The classic case, in Java:

if (sum == 0) if (count == 0) (result = 0); else result = 1;

Is the else paired with the outer or the inner if?

The rule
The semantics of Java specifies that the else is matched with the most recent unpaired then clause — the inner one in this example.

Note that the indentation lies: it suggests the else belongs to the outer if, but the language rule says otherwise. Since this implicit association may be confusing, some languages require the use of specific syntax for nesting selectors.

Algol 60 uses begin/end to make the association explicit. Both readings become expressible:

else with the INNER if
if sum = 0 then begin if count = 0 then result := 0 else result := 1 end
else with the OUTER if
if sum = 0 then begin if count = 0 then result := 0 end else result := 1
The point to close on
To obtain the latter semantics in Java we need to use extra syntax too — braces. Neither language escapes the problem; they differ only in what the default is when you don't disambiguate.
📘 This is Topic 01 coming back (background)
The dangling else is an ambiguous grammar — exactly the 1 - 2 - 3 problem, in a real language. One string of characters, two parse trees, two different meanings. Java resolves it by fiat ("most recent unpaired then"), which is a disambiguation rule bolted onto the concrete syntax. In abstract syntax the problem cannot arise: if(b₁, if(b₂, c₁, c₂), skip) and if(b₁, if(b₂, c₁, skip), c₂) are simply different trees.

Multiple selectors

Multiple selectors are a generalisation of two-way selectors. In Java (and C, C++):

switch (expression) { case constant-expr-1 : statement-1; ... case constant-expr-n : statement-n; [default : statement-n+1] }
The design difference to remember
In some languages, at the end of a branch the control goes to the instruction after the selector; in others we need an explicit break or return.

C/C++/Java are the second kind — omit the break and control falls through into the next branch. This is a textbook example of the third aim: apparently similar constructs that differ in meaning between languages.

Iterative statements (loops)

Iterative constructs cause a statement or sequence of statements — the body of the loop — to be repeated. There are two independent classifications, and the exam likes both:

By when the test happens

  • Pre-test loop — the test for loop completion is done before the execution of the body.
  • Post-test loop — it occurs after the body is executed.

By what controls it

  • Counter-controlled loops
  • Logically-controlled loops
The consequence to state out loud
A post-test loop always executes its body at least once; a pre-test loop may execute it zero times. That single sentence answers most exam questions comparing while with do.

Counter-controlled loops

The for statement of C and Java:

for (expr-1; expr-2; expr-3) loop-body
PartRole
expr-1Initialises the counter
expr-2The loop control, evaluated before each execution of the loop-body
expr-3Executed after each execution of the loop-body
for (index = 0; index ≤ 10; index++) sum = sum + list[index];

Because expr-2 is evaluated before each execution of the body, the for loop is a pre-test loop.

Logically-controlled loops

Most imperative languages have pre- and post-test loop constructs. In C++ and Java there is a while loop and a do loop:

pre-test
while
while (expression)
    loop-body

The loop-body is executed as long as the expression evaluates to True.

post-test
do
do
    loop-body
while (expression)

The loop-body is executed until the expression evaluates to False.

The variant that catches people out
Pascal's repeat loop executes the body until the expression evaluates to True.
repeat loop-body until (expression)

So do…while(e) and repeat…until(e) are both post-test, but they are opposites: one continues while e is true, the other stops when e is true. Same shape, inverted meaning — precisely the "apparently similar constructs" the aims warned about.

Structuring the program: blocks & subprograms

Blocks

Definition
A block is a group of statements, delimited by keywords such as begin and end, or by separators, like { and }.

A block may contain not only commands, but also declarations (of constants, variables or types). If the language has static scope, these will only be visible inside the block — they are local.

Note how neatly this closes the loop with the first half of the topic: blocks are the units that static scoping searches outwards through. And it's blocks that resolved the dangling else in Algol 60.

Subprograms

Definition
Subprogram is a generic name for a named block that can be invoked explicitly. The block of statements is executed upon invocation, and the control returns to the calling point after the execution of the subprogram.

Examples: procedures in Pascal, functions in C, methods in Java.

Formal vs actual parameters

When a subprogram is declared, together with the name we can associate parameters:

Formal parameters

The ones in the declaration of the subprogram.

Actual parameters

The ones provided when the subprogram is invoked.

The values of the actual parameters will be replaced for the formal parameters when the subprogram is invoked.

A forward pointer
Different languages use different parameter passing mechanisms. The material explicitly defers this: we will study these in more detail for functional languages. So if a question asks about call-by-value vs call-by-name here, the expected answer is only the formal/actual distinction — the mechanisms come later.

Exam-style takeaways

Key things to nail for Topic 02
  1. The founding claim — imperative languages are abstractions of the Von Neumann architecture; variables represent memory cells. To understand programs we need the properties of variables + the flow of control.
  2. The four properties of a variable — name, type (range of values and available operations), address (l-value), value (r-value).
  3. Why name→address is "not simple" — one name may map to different addresses in different parts of the program; several names may share one address (Pascal variant records, Fortran EQUIVALENCE).
  4. Static vs dynamic typing — statically typed: Java, Haskell, ML, Scala. Dynamically typed: Python, Ruby. Some languages untyped.
  5. Lifetime — the time between allocation and deallocation. Name all four classes.
  6. Static variables — bound before execution begins until it ends. ✓ efficiency (addressing resolved at compile time, no run-time allocation). ✗ storage cannot be reused; recursive programs need dynamic variables.
  7. Stack dynamic — allocated when the declaration is processed at run time; e.g. locals of recursive procedures.
  8. Explicit heap-dynamic — nameless cells allocated/deallocated by instructions via pointers (C++ new/delete). Java: objects are explicit heap dynamic, accessed via reference variables, no way to destroy them explicitly → implicit garbage collection (first introduced in Lisp).
  9. Implicit heap-dynamic — bound to storage only when assigned values (strings/arrays in Perl, JavaScript). ✓ flexibility ✗ difficult error detection.
  10. Scope — the range of instructions in which the variable is visible. Local = declared in the executing block; global = visible but not local.
  11. Static scope — determined at compile time; look in the same block, then the parent block, etc.; if no declaration is found the compiler detects an error. Be able to annotate the Pascal example (P1's x local; P2's and main's x global).
  12. Dynamic scope — depends on the calling sequence of subprograms, not their declaration. In the example, x in P2 may be P1's or main's depending on who called P2. Problems: no static type-checking; programs very hard to understand. Perl lets you choose; Common Lisp had it, Scheme is static.
  13. Assignment — = is not mathematical equivalence (:= is sometimes used); value stored until a new value is given by another assignment or a side-effect; typed languages require compatible types.
  14. i++ vs ++i — both add 1 to i; i++ returns the value of i, ++i returns the value of i+1. Same for i-- / --i.
  15. Three kinds of control statement — selection, looping, branching. Any sequential algorithm can be coded with just if-then-else and while; go-to is superfluous. Other constructs exist to facilitate writing programs; statements group into compound statements.
  16. Dangling else — Java matches else with the most recent unpaired then clause. Be able to show both Algol 60 begin/end versions, and note Java needs extra syntax (braces) for the outer reading too.
  17. Multiple selectors — switch generalises two-way selection; some languages leave the selector at the end of a branch, others need an explicit break or return.
  18. Loop classifications — pre-test (test before body) vs post-test (test after body); counter-controlled vs logically-controlled. A post-test loop runs the body at least once.
  19. The for statement — expr-1 initialises the counter; expr-2 is the loop control evaluated before each execution of the body; expr-3 is executed after each execution of the body.
  20. while vs do vs repeat — while is pre-test, body runs as long as the expression is True; do is post-test, body runs until the expression is False; Pascal's repeat runs the body until the expression is True. Know that do…while and repeat…until are opposites.
  21. Blocks — groups of statements delimited by keywords (begin/end) or separators ({/}); may contain declarations, which under static scope are visible only inside (local).
  22. Subprograms — named blocks invoked explicitly; control returns to the calling point. Procedures (Pascal), functions (C), methods (Java). Formal parameters in the declaration vs actual parameters at invocation; actual values replace formal ones on invocation.
