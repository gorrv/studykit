Topic 03 · Imperative Languages — Formal Description

SIMP & the Abstract Machine

making Topic 02's informal descriptions precise

Topic 02 described imperative constructs in English. This topic we do it properly — with a transition system. Topic 01 defined an abstract machine as "a transition system that specifies an interpreter for a programming language"; here we actually build one, for a small imperative language called SIMP.

The three aims
  1. Distinguish between informal and formal descriptions of programming languages.
  2. Be able to use transition systems in the form of abstract machines to give the semantics of the main constructs used in imperative languages.
  3. Understand the differences between alternative semantic descriptions given in terms of transition systems.

Aim 2 is the one that gets examined as a calculation: given a program and a memory, write the sequence of transitions. Practise it until it's mechanical.

Why formal? The f(i++, --i) problem

Informal semantics can be imprecise. The lecture opens with a single devastating example:

What is the meaning of the C expression f(i++, --i)?

Everything about it seems well defined. From Topic 02 we know exactly what each operator does:

  • i++ increases the value of i by 1 and also returns the old value of i.
  • --i decreases the value of i by 1 and returns the new value of i.
The gap
The order of evaluation of parameters of functions was not specified in the definition of the language C.

Therefore different C compilers could generate very different code for f(i++, --i). Both operators are individually precise; what's missing is the order in which they happen. And since both have side-effects on the same variable, the order changes the answer.

Why this argument works so well
It isn't that the C designers were careless about ++ — it's that an informal description cannot even express the thing that was left out. A formal semantics is forced to say, for every construct, exactly what happens and in what order: the transition rules either specify it or the relation isn't a function. Formality makes omissions visible.

The move the lecture makes next
The first approach to giving a precise, formal description of the behaviour of programming constructs was in terms of an abstract machine.

And, restating Topic 01's definition: an abstract machine is a transition system, which specifies an interpreter for the programming language. We give an example for a small imperative language: SIMP.

Abstract syntax of SIMP

Three syntactic categories — programs, commands, expressions — with booleans separated from integers.

Programs
P ::= C | E | B

Commands
C ::= skip | l := E | C ; C | if B then C else C | while B do C

Integer expressions
E ::= !l | n | E op E        op ::= + | − | ∗ | /

Boolean expressions
B ::= True | False | E bop E | ¬B | B ∧ B        bop ::= > | < | =
n ∈ ℤ = {…, −2, −1, 0, 1, 2, …} — the integers.
l ∈ L = {l₀, l₁, …} — locations (or variables). The expression !l denotes the value stored in l.
The ! is the whole l-value/r-value distinction, made syntactic
This is the single most important notational point of the topic, and it comes straight from Topic 02. In SIMP, a location l and its contents !l are different pieces of syntax:
  • l on its own is the l-value — the address. That's why assignment is written l := E, with a bare l on the left.
  • !l is the r-value — the contents. That's why l := !l − 1 has the ! on the right but not the left.

C and Java hide this by letting context decide; SIMP makes it explicit, and the machine rules depend on it. Forgetting a ! is the most common way to lose marks in SIMP questions.

Two more things to notice about this grammar
  • Booleans and integers are separate categories. There is no rule letting a B appear where an E is expected, so 1 + True is not even a SIMP program — a whole class of type errors is excluded by the syntax, before any type system is needed.
  • There is no ∨ and no ≥. The language is deliberately minimal (recall Böhm–Jacopini from Topic 02: if and while suffice). Anything else you need, you encode — e.g. B₁ ∨ B₂ as ¬(¬B₁ ∧ ¬B₂).

Example programs in SIMP

Swapping the contents of x and y

z := !x ; x := !y ; y := !z

Read the !s carefully: each left-hand side is a bare location, each right-hand side dereferences one. z := !x copies the contents of x into the cell z.

Factorial

Assuming the variable l contains a natural number n, this program computes the factorial of n:

factorial := 1; while !l > 0 do (factorial := !factorial ∗ !l; l := !l − 1)

Note the brackets around the loop body: they group the two assignments into a single command C₁ ; C₂, which is what while B do C requires. This program is used again below as the worked transition example.

These grammars specify trees

Straight from the lectures
The grammars specify the abstract syntax of SIMP, therefore rules specify labelled trees rather than strings.
  • The leaf nodes of the tree are labelled by elements of ℤ ∪ {True, False} ∪ L ∪ {skip}.
  • The non-leaf nodes are labelled by operators and commands.

The example given — this tree:

Leaves (blue / green) are elements of ℤ ∪ {True, False} ∪ L ∪ {skip}; non-leaves (orange / purple) are operators and commands.

…is written in a textual notation as:

if 5 > 0 then skip else (skip; l := 0)

…using brackets where there is ambiguity.

The role brackets play here — a Topic 01 callback
The tree is the program; the textual notation is just a convenient way of writing it down. Brackets are not part of the abstract syntax — there is no bracket node in the tree. They exist only because we're flattening a tree into a line of text, and without them the reader couldn't recover which tree was meant. This is exactly Topic 01's point that abstract syntax is unambiguous while its textual rendering need not be.

The abstract machine: control, results, memory

The machine is defined with three components:

A control stack c

What the machine still has to do. Holds program phrases waiting to be processed, and operator tokens waiting to be applied.

An auxiliary stack r

Also called the results stack. Holds values already computed, plus locations and command phrases saved for later.

Memory m — the store

Modelled by a partial function mapping each address to an integer. dom(m) denotes the locations where m is defined.

Memory update notation — you will need to write this
m[l ↦ n] is the function that maps each l′ ≠ l to the value m(l′), and l to the value n. More precisely:
m[l ↦ n](l)  =  n
m[l ↦ n](l′)  =  m(l′)    if l ≠ l′

In words: the same memory as before, except that l now holds n. Note it is a new function, not a mutation — the formalism has no notion of "changing" anything; each transition simply produces a new triple.

Why "partial" matters
m is a partial function, so m(l) may be undefined. Look at the rule for !l below: it applies only if m(l) = n. If l ∉ dom(m) there is no applicable transition and the machine is stuck — a configuration that is not final but has no successor. That is exactly how "reading an uninitialised variable" is modelled: not as an error message, but as the absence of a transition.

An abstract machine is a transition system. Therefore it is defined by a set of configurations and a set of transition rules.

Configurations

A configuration is a triple: ⟨Control, Results, Memory⟩. The two stacks are themselves defined by grammars:

c ::= nil | i · c
i ::= P | op | ¬ | ∧ | bop | := | if | while
r ::= nil | P · r | l · r
where P, bop and op are the non-terminals used in the rules defining SIMP programs.

So the control stack holds either whole program phrases or one of eight bare tokens — the operators, plus :=, if and while. Those tokens are instructions to the machine meaning "the operands are ready; now apply me".

To model the execution of a program we define transitions between initial and final configurations:

Initial configurations

⟨C · nil,  nil,  m⟩

The whole command sits alone on the control stack; nothing computed yet.

Final configurations

⟨nil,  nil,  m⟩

Both stacks empty. Recall from Topic 01: a terminal configuration has no outgoing transition.

Semantics of SIMP programs

The two definitions — quote these

For a command. If there is a sequence of transitions

⟨C · nil, nil, m⟩  →*  ⟨nil, nil, m′⟩

then we say that the program C executed in the state m terminates successfully producing the state m′. The semantics of a command C in the state m is described by giving the sequence of transitions that transform ⟨C · nil, nil, m⟩ into ⟨nil, nil, m′⟩.

For an expression. If there is a sequence of transitions

⟨E · c, r, m⟩ →* ⟨c, v · r, m′⟩      ⟨B · c, r, m⟩ →* ⟨c, v · r, m′⟩

then we say that the value of the expression E (resp. B) in the state m is v.

Read the expression definition carefully — it's cleverer than it looks
It is stated for an arbitrary surrounding c and r, and says the machine ends up with the same c and r, plus one new value v on top. That is a precise way of saying: evaluating an expression consumes itself from the control stack and leaves exactly one value behind, disturbing nothing else. It's what lets expression evaluation be used as a subroutine inside command rules.

A transition rule has the form c → c′, where c and c′ describe configurations. The transition rules generate the transition relation. They divide into two groups: rules for the evaluation of expressions, and rules for the evaluation of commands.

Transition rules: evaluation of expressions

Pushing values · decomposing phrases
⟨n · c, r, m⟩→⟨c, n · r, m⟩num
⟨b · c, r, m⟩→⟨c, b · r, m⟩bool
⟨¬B · c, r, m⟩→⟨B · ¬ · c, r, m⟩not-decomp
⟨(B₁ ∧ B₂) · c, r, m⟩→⟨B₁ · B₂ · ∧ · c, r, m⟩and-decomp
⟨(E₁ op E₂) · c, r, m⟩→⟨E₁ · E₂ · op · c, r, m⟩op-decomp
⟨(E₁ bop E₂) · c, r, m⟩→⟨E₁ · E₂ · bop · c, r, m⟩bop-decomp
Applying operators · reading memory
⟨¬ · c, b · r, m⟩→⟨c, b′ · r, m⟩if b′ = not bnot-apply
⟨∧ · c, b₂ · b₁ · r, m⟩→⟨c, b · r, m⟩if b₁ and b₂ = band-apply
⟨op · c, n₂ · n₁ · r, m⟩→⟨c, n · r, m⟩if n₁ op n₂ = nop-apply
⟨bop · c, n₂ · n₁ · r, m⟩→⟨c, b · r, m⟩if n₁ bop n₂ = bbop-apply
⟨!l · c, r, m⟩→⟨c, n · r, m⟩if m(l) = nderef
The pattern — learn this, not the eleven rules
Every operator gets two rules, and they always have the same shape:
  1. A decomposition rule: the compound phrase is popped and replaced by its sub-phrases followed by the operator token. Nothing is computed. This is what the lecture later calls "phrase analysis".
  2. An application rule: the token surfaces on the control stack, its operands are now on the results stack, and it consumes them and pushes one value.

Once you see that, the table is just the same idea repeated for ¬, ∧, op and bop.

The argument-order trap — this is where marks are lost
In the application rules the results stack is written n₂ · n₁ · r — the second operand is on top. That's because decomposition pushes E₁ · E₂ · op, so E₁ is evaluated first, then E₂ lands on top of it. The side condition is therefore n₁ op n₂, not n₂ op n₁.

It only matters for non-commutative operators — but that's exactly what an exam will test. 5 − 3 must give 2, not −2.

And notice what this machine does specify
Look back at f(i++, --i). The op-decomp rule pushes E₁ · E₂ · op in that order, so the machine fixes left-to-right evaluation — no ambiguity is possible. SIMP has no side-effecting expressions, so it couldn't have bitten us here anyway; but the rule shows how a formal semantics settles the question that C's informal definition left open.

Worked example: evaluating !l > 0

Assume m = {l ↦ 4} and we want to evaluate the expression !l > 0. Initial configuration: ⟨!l > 0 · nil, nil, m⟩.

0⟨!l > 0 · nil,  nil,  m⟩
1→⟨!l · 0 · > · nil,  nil,  m⟩bop-decomp
2→⟨0 · > · nil,  4 · nil,  m⟩deref  (m(l) = 4)
3→⟨> · nil,  0 · 4 · nil,  m⟩num
4→⟨nil,  True · nil,  m⟩bop-apply  (4 > 0 = True)

The machine reached a final configuration. The expression !l > 0 evaluates to True in the given memory state.

Watch step 4 to fix the argument order in your head
At step 3 the results stack is 0 · 4 · nil: n₂ = 0 on top, n₁ = 4 beneath. The rule computes n₁ bop n₂ = 4 > 0 = True. Had you read the stack top-down you'd have computed 0 > 4 = False — the wrong answer, from the right stack.

Transition rules: evaluation of commands

⟨skip · c, r, m⟩→⟨c, r, m⟩skip
⟨(l := E) · c, r, m⟩→⟨E · := · c, l · r, m⟩assign-decomp
⟨:= · c, n · l · r, m⟩→⟨c, r, m[l ↦ n]⟩assign-apply
⟨(C₁ ; C₂) · c, r, m⟩→⟨C₁ · C₂ · c, r, m⟩seq
⟨(if B then C₁ else C₂) · c, r, m⟩→⟨B · if · c, C₁ · C₂ · r, m⟩if-decomp
⟨if · c, True · C₁ · C₂ · r, m⟩→⟨C₁ · c, r, m⟩if-true
⟨if · c, False · C₁ · C₂ · r, m⟩→⟨C₂ · c, r, m⟩if-false
⟨(while B do C) · c, r, m⟩→⟨B · while · c, B · C · r, m⟩while-decomp
⟨while · c, True · B · C · r, m⟩→⟨C · (while B do C) · c, r, m⟩while-true
⟨while · c, False · B · C · r, m⟩→⟨c, r, m⟩while-false

Three rules worth staring at

1 · Assignment — where the ! distinction pays off
⟨(l := E) · c, r, m⟩ → ⟨E · := · c, l · r, m⟩

The location l is pushed onto the results stack unevaluated — it is not looked up in memory. Meanwhile E goes on the control stack to be evaluated normally. When := surfaces, the results stack holds n · l · r: the value on top, the address beneath. That's an l-value and an r-value sitting next to each other, and the rule writes one into the other.

2 · If — the branches are parked, not executed
⟨(if B then C₁ else C₂) · c, r, m⟩ → ⟨B · if · c, C₁ · C₂ · r, m⟩

Both branches are pushed onto the results stack, where nothing executes them — the results stack is storage, not work. Only B goes on the control stack. When if surfaces it finds True/False · C₁ · C₂, discards all three, and moves the chosen branch onto the control stack. This is how the machine guarantees exactly one branch runs.

3 · While — the rule that explains looping
⟨while · c, True · B · C · r, m⟩ → ⟨C · (while B do C) · c, r, m⟩

This is the heart of the topic. When the test is True, the machine pushes the body and then rebuilds the entire loop behind it. So after C finishes, the whole while B do C phrase is next on the control stack and the process starts again. When the test is False, the loop and its saved copies are simply discarded.

Note why while-decomp pushes B · C onto the results stack: the machine must remember the test and the body in order to reconstruct the loop on the next iteration. Nothing else in SIMP needs to do this — it's what makes while the only genuinely recursive rule.

Example: transitions of the factorial loop

Let C = while B do C′,  B = !l > 0,  C′ = factorial := !factorial ∗ !l; l := !l − 1,  and m = {l ↦ 4, factorial ↦ 1}.

0⟨C · nil,  nil,  m⟩
1→⟨B · while · nil,  B · C′ · nil,  m⟩while-decomp
2→⟨!l · 0 · > · while · nil,  B · C′ · nil,  m⟩bop-decomp
3→⟨0 · > · while · nil,  4 · B · C′ · nil,  m⟩deref
4→⟨> · while · nil,  0 · 4 · B · C′ · nil,  m⟩num
5→⟨while · nil,  True · B · C′ · nil,  m⟩bop-apply
6→⟨C′ · C · nil,  nil,  m⟩while-true  — note C is rebuilt behind C′
⋯(three more iterations)
n→⟨nil,  nil,  m[l ↦ 0, factorial ↦ 24]⟩
The sentence the lecture ends this example with
The abstract machine describes the exact behaviour of a while loop. Compare with the informal definition: "…the body of the loop is executed as long as the value of the expression is true."

The informal sentence is not wrong — it's just not a definition. It doesn't say when the expression is re-evaluated, what happens to the saved body, or in what order side-effects occur. The six transitions above answer all of that, mechanically. This contrast is the thesis of the whole lecture, and is very likely to be an essay-style exam question.

Operational semantics: the verdict on abstract machines

AdvantageDisadvantage
✓ The abstract machine explains the execution of the commands step by step, which is useful if we have to implement the language. ✗ It is not very intuitive. Many transitions are doing just phrase analysis; only a few really perform computations.
You can see the disadvantage in your own trace
Run the factorial example in the tool and count. The overwhelming majority of steps are decomposition rules — pulling phrases apart and pushing tokens. Only op-apply, bop-apply and assign-apply actually compute anything. That ratio is the disadvantage, and quoting it with a number from your own trace makes for a strong exam answer.
The fix, and the bridge to next lecture
Structural Approach to Operational Semantics. To overcome the previous problem, another approach to operational semantics based on transition systems was developed: the structural approach (Plotkin).

Idea: the transitions for a compound statement should be defined in terms of the transitions for its constituent sub-statements. In other words: the definition should be inductive.

Compare with Topic 01, which put it identically: "each command is described in terms of its components." The next lecture builds this alternative — and aim 3 of this lecture ("understand the differences between alternative semantic descriptions") is asking you to compare the two.

Exam-style takeaways

Key things to nail for Topic 03
  1. Why formal semantics — be able to reproduce the f(i++, --i) argument: both operators are precisely defined, but the order of evaluation of parameters was not specified in the definition of C, so different compilers could generate very different code.
  2. Abstract machine = a transition system which specifies an interpreter for the programming language. It was the first approach to formal description.
  3. Write out the abstract syntax of SIMP — P ::= C | E | B; the five commands; E ::= !l | n | E op E; B ::= True | False | E bop E | ¬B | B ∧ B; op ::= + − ∗ /; bop ::= > < =.
  4. The meaning of !l — the value stored in l. Bare l = address (l-value); !l = contents (r-value). Get this right in every program you write.
  5. Write the two example programs — swap (z := !x; x := !y; y := !z) and factorial.
  6. Leaves vs non-leaves — leaves are labelled by ℤ ∪ {True, False} ∪ L ∪ {skip}; non-leaves by operators and commands. Be able to convert between a tree and the textual notation (brackets used where there is ambiguity).
  7. The three machine components — control stack c, auxiliary/results stack r, memory (store) m, a partial function from addresses to integers; dom(m) = where m is defined.
  8. Memory update notation — m[l ↦ n](l) = n and m[l ↦ n](l′) = m(l′) if l ≠ l′.
  9. Configurations — a triple ⟨Control, Results, Memory⟩; the grammars for c, i and r; initial ⟨C · nil, nil, m⟩ and final ⟨nil, nil, m⟩.
  10. Definition of successful termination — if ⟨C · nil, nil, m⟩ →* ⟨nil, nil, m′⟩ then C executed in state m terminates successfully producing m′.
  11. Definition of the value of an expression — if ⟨E · c, r, m⟩ →* ⟨c, v · r, m′⟩ then the value of E in state m is v.
  12. Reproduce the expression rules — and know the two-rule pattern (decomposition then application) rather than memorising eleven separate lines.
  13. The argument order — results stack is n₂ · n₁ · r, and the side condition is n₁ op n₂. Get this backwards on a subtraction and the answer is wrong.
  14. Reproduce the command rules — especially assignment (location pushed unevaluated), if (branches parked on the results stack), and while.
  15. The while rule — ⟨while · c, True · B · C · r, m⟩ → ⟨C · (while B do C) · c, r, m⟩: the loop rebuilds itself behind the body. Explain why while-decomp saves B · C on the results stack.
  16. Do a full trace by hand — the !l > 0 evaluation with m = {l ↦ 4} (4 steps), and the opening steps of the factorial loop. Expect exactly this as a calculation question.
  17. Advantage vs disadvantage — ✓ explains execution step by step, useful for implementing the language; ✗ not very intuitive, many transitions are doing just phrase analysis, only a few really perform computations.
  18. The structural approach (Plotkin) — transitions for a compound statement defined in terms of the transitions for its constituent sub-statements; i.e. the definition should be inductive. Know that this is the answer to the abstract machine's disadvantage.
