PDDL 2.1: Fluents & Time

resources that run out, actions that take a while

What classical planning cannot say

The four limitations
  • Actions are instantaneous.
  • The planner has to decide which actions to apply and in what order.
  • Plans are sequential.
  • Actions don't define quantity or resource, and goals cannot define resource constraints.

All actions take uniform time and have no costs.

The fix
"PDDL 2.1: An Extension to PDDL for Expressing Temporal Planning Domains" adds:
  • Numbers, resources, costs ("metrics")
  • Time
Why you can't fake numbers with predicates
You could in principle write fuel-30, fuel-29, … as separate facts, but the state space explodes and nothing can express "enough fuel" or "minimise total fuel". Fluents make quantity first-class: you can compare it in a precondition and change it by an amount in an effect.

Fluents

Definition
  • PDDL 2.1 introduces the ability to model numeric values through fluents.
  • We identify a particular resource within the domain by having action effects increase or decrease the value of that resource.
  • This helps maintain an understanding of the costs of actions.
The new syntax
  • (:requirements :typing :fluents) — declare what the domain uses.
  • (:types vehicle location) — real types, so ?v - vehicle replaces type predicates.
  • (:functions …) — declares the numeric fluents, exactly as :predicates declares the boolean ones.
  • In preconditions: comparisons — (>= (fuel-level ?v) (fuel-required ?from ?to)).
  • In effects: updates — (decrease …), (increase …), also (assign …).
  • In the problem file: assignments — (= (fuel-level truck) 100).
  • In the problem file: (:metric minimize …) — what "optimal" means for this problem.

The metric vehicle domain

(define (domain metricVehicle)
(:requirements :typing :fluents)
(:types vehicle location)
(:predicates (at ?v - vehicle ?p - location)
             (accessible ?v - vehicle ?p1 ?p2 - location))

(:functions (fuel-level ?v - vehicle) (fuel-used ?v - vehicle)
            (fuel-required ?p1 ?p2 - location) (total-fuel-used))

(:action drive
 :parameters (?v - vehicle ?from ?to - location)
 :precondition (and (at ?v ?from) (accessible ?v ?from ?to)
                    (>= (fuel-level ?v) (fuel-required ?from ?to)))
 :effect (and (not (at ?v ?from)) (at ?v ?to)
              (decrease (fuel-level ?v) (fuel-required ?from ?to))
              (increase (total-fuel-used) (fuel-required ?from ?to))
              (increase (fuel-used ?v) (fuel-required ?from ?to)))))
Three kinds of fluent in one action
  • fuel-level ?v — a consumable resource: guarded by a precondition, decreased by the effect. This is what makes plans fail when you run dry.
  • fuel-used ?v and total-fuel-used — accumulators: never tested, only increased. They exist purely so the metric has something to minimise.
  • fuel-required ?p1 ?p2 — a static table: set in the problem file, never modified. It's a numeric fact about the map, not a resource.

Notice total-fuel-used has no parameters — a single global number. That's the standard way to write a plan metric.

The problem file:

(define (problem metricVehicle-example)
(:domain metricVehicle)
(:objects truck car - vehicle
          Paris Berlin Rome Madrid - location)
(:init
  (at truck Rome)
  (at car Paris)
  (= (fuel-level truck) 100)      (= (fuel-level car) 100)
  (accessible car Paris Berlin)     (accessible car Berlin Rome)
  (accessible car Rome Madrid)      (accessible truck Rome Paris)
  (accessible truck Rome Berlin)    (accessible truck Berlin Paris)
  (= (fuel-required Paris Berlin) 40)   (= (fuel-required Berlin Rome) 30)
  (= (fuel-required Rome Madrid) 50)    (= (fuel-required Rome Paris) 35)
  (= (fuel-required Rome Berlin) 40)    (= (fuel-required Berlin Paris) 40)
  (= (total-fuel-used) 0) (= (fuel-used car) 0) (= (fuel-used truck) 0))

(:goal (and (at truck Paris) (at car Rome)))
(:metric minimize (total-fuel-used)))
Work the example out — it rewards a close look
Truck: Rome → Paris. Two options: direct (35) or via Berlin (40 + 40 = 80). Direct wins.
Car: Paris → Rome. Only route is Paris → Berlin → Rome (40 + 30 = 70). Note the car cannot use Rome → Paris — accessible takes the vehicle as an argument, so the two have different road networks.
Total = 35 + 70 = 105, and both start with 100 units, so both stay in range.

Also notice accessible and fuel-required are directed — (accessible car Paris Berlin) does not give you Berlin → Paris. Missing reverse edges are a classic modelling bug.

Durative actions (temporal planning)

Why time is a separate problem from resources
  • Fluents handle resources and how they change during execution — but we still need to handle the passage of time. How long does an action take?
  • This influences conditions as well as effects: conditions might hold true at different times, and effects can occur at different times.
(:durative-action move-up-slow
  :parameters (?lift - slow-elevator ?f1 - floor ?f2 - floor)
  :duration (= ?duration (travel-slow ?f1 ?f2))
  :condition (and (at start (lift-at ?lift ?f1))
                  (at start (above ?f1 ?f2))
                  (at start (reachable-floor ?lift ?f2)))
  :effect (and (at start (not (lift-at ?lift ?f1)))
               (at end (lift-at ?lift ?f2))))

; problem file
(above f0 f1)
(reachable-floor slow1 f1)
(= (travel-slow f0 f1) 12)

Read the lift action as a story
At the start, the lift is at f1, f1 is above f2, and f2 is reachable. The instant it starts moving, lift-at f1 is deleted — the lift is now between floors and nowhere in particular. Only at the end does lift-at f2 become true, 12 time units later.

That gap is the whole point. Splitting one action into a start effect and an end effect means another action can be happening in the interval — which is how temporal plans get genuine parallelism, unlike the sequential plans of Part 1.

The board action — and over all

(:durative-action board
  :parameters (?p - passenger ?lift - elevator ?f - floor)
  :duration (= ?duration 3)
  :condition (and (over all (lift-at ?lift ?f))
                  (at start (passenger-at ?p ?f))
                  (at start (< (passengers ?lift) (capacity ?lift))))
  :effect (and (at start (not (passenger-at ?p ?f)))
               (at end (boarded ?p ?lift))
               (at start (increase (passengers ?lift) 1))))

; problem file
(above f0 f1)   (reachable-floor slow1 f1)   (= (travel-slow f0 f1) 12)
(passenger-at p0 f1)   (= (passengers slow1) 0)   (= (capacity slow1) 4)
Everything worth noticing here
  • over all (lift-at ?lift ?f) — the lift must stay at that floor for the whole three seconds. Not just at the start: the doors must not close mid-boarding. This is the condition type the previous action didn't have.
  • Fixed duration — (= ?duration 3), a constant rather than a fluent lookup. Both forms are legal.
  • Fluent + durative combined — the capacity check (< (passengers ?lift) (capacity ?lift)) is exactly the Part-3-fluents machinery inside a temporal action. This is how you say "capacity 4" rather than the gripper's one-ball-per-free trick.
  • The counter increases at start, not at end — deliberately. It reserves the seat the moment boarding begins, so a second passenger deciding at the same instant sees the space already taken. Putting it at end would let five people board a lift with capacity 4.
Summary of the decks
  • PDDL 2.1 handles more complex temporal and resource-heavy problems.
  • Fluents allow management of resources — check a resource is within a limit, increase/decrease it.
  • Temporal planning considers how planning must execute within fixed time frames: the overall duration; conditions that must hold at the start, until the end, or throughout; effects applied at the start or upon completion.

Exam-style takeaways

Key things to nail for Part 3
  1. Classical PDDL's limits — instantaneous actions, sequential plans, no quantities or resources, goals cannot express resource constraints.
  2. PDDL 2.1 adds numbers, resources, costs (metrics) and time.
  3. Fluents = numeric values; effects increase/decrease them; preconditions compare them.
  4. Know the sections — :requirements, :types, :predicates, :functions, :action; and in the problem :objects, :init with (= (f x) n), :goal, :metric minimize ….
  5. Be able to write a fluent action — the drive action is the model answer: a >= guard plus a decrease and matching increasees.
  6. Durative actions — :durative-action with :duration, :condition and :effect.
  7. The three condition types: at start, over all, at end. The two effect types: at start, at end. Be able to draw the timeline.
  8. What over all is for — something that must remain true for the whole duration, e.g. the lift staying at the floor while a passenger boards.
  9. Why the delete happens at start — the object leaves its old state immediately; the new state only becomes true at the end. That interval is what lets other actions run concurrently.
