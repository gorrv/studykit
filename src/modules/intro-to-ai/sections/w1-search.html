Week 01 · Part 2 · Search

Search: BFS, DFS, UCS

turning "what should I do?" into "find me a path"

What search is

Definition — learn this sentence
Search is the process of computing a sequence of actions that form a path to a goal.

Recall the model-based agent from Part 1: it defines an encoding of the world, defines how the world can change, and then searches for good strategies. Search is that third step, made precise.

The five components of a search problem

Note what a "goal" is
The goal is a test, not necessarily a single named state. "Any state where all tiles are in order" or "any city with a hospital" are perfectly good goals. That matters later: an algorithm stops when the test passes, whichever state triggered it.
A search problem does not come with the answer
The five components describe a world. They don't say which sequence of actions is good — finding that is the algorithm's job. Different algorithms explore the same problem in different orders and give different answers, and that's the whole content of the rest of this week.

Three example problems

1 · Sliding tiles

State space: every arrangement of the tiles. Initial state: the scrambled board. Goal test: are the tiles in order? Actions: slide a tile adjacent to the gap into the gap. Transition model: the board with that tile and the gap swapped. Costs: 1 per move — so cheapest path = fewest moves.

2 · Navigation (Romania)

The running example for the rest of the week. States = cities, actions = roads, costs = distances. Here the costs are not all equal, which is exactly what separates the algorithms below.

3 · Self-service checkout — giving change

A state is a vector of coin counts, e.g. (3, 3, 0, 1, 3, 0, 3, 1) — how many of each denomination the machine holds. Actions = dispense one coin of some denomination. Goal test = the dispensed amount equals the change owed. Costs = 1 per coin, so the cheapest path uses the fewest coins.

The pattern across all three
None of these look like "navigation", yet all three fit the same five slots. That's the point of the formalism: once you can write a problem as ⟨states, initial, goal test, actions, transitions, costs⟩, every algorithm in this module applies to it unchanged. In an exam, "formulate this as a search problem" means: fill in those five slots.

Search trees

Search tree
  • A node is a state.
  • An edge is an action taking you from one state to another.
  • The root is the initial state; a path from root to a node is a candidate plan.
Redundant paths make the tree infinite

A graph with a cycle (drive A→B, then B→A, then A→B…) unrolls into an infinite search tree, even though the state space is tiny. Two fixes:

  • Check the path back to the root — refuse to expand into a state already on the current branch. Cheap, only kills cycles on this path.
  • Track visited states (a reached set) — refuse to expand any state seen before anywhere. Stronger, costs memory.
Tree vs graph — why the distinction keeps showing up
The graph is the map, and it's finite. The tree is the set of all paths through that map, and it can be infinite. Algorithms walk the tree; the reached set is what keeps them from re-walking the same part of the graph forever. Whenever a slide says "complete if redundant paths are prevented", this is what it means.

Breadth-first search

Idea
Explore the tree in slices of the same depth: all nodes 1 action away, then all nodes 2 actions away, and so on. Implemented with a queue (first in, first out) plus a reached set.
PropertyBFS
Complete? (finds a solution if one exists)Yes
Optimal? (finds the best solution)Yes — if all action costs are equal
Timeb + b² + … + b^d
Spaceb + b² + … + b^d

b = branching factor (actions per state), d = depth of the shallowest solution, m = maximum depth of the tree.

Why "optimal only if costs are equal"
BFS returns the solution with the fewest actions. If every action costs the same, fewest actions = cheapest. If they don't — as on a road map — BFS will happily return a 2-hop route of length 310 while a 3-hop route of length 278 exists. That exact example appears under UCS below.
The space cost is the killer
BFS's memory is the same order as its time, because it must hold an entire depth slice at once. With b = 10 and d = 10 that's about ten billion nodes. Time you can wait for; memory you cannot buy.

Depth-first search

Idea
Always expand the deepest node first — dive down one branch to the bottom, then back up and try the next. Implemented with a stack (last in, first out).
PropertyDFS
Complete?Yes — if redundant paths are prevented (otherwise it can fall down an infinite branch)
Optimal?No — it finds the left-most solution, not the best one
Timeb^m
Spaceb · m
The trade in one line
DFS trades solution quality for memory. It only ever stores the current branch plus its siblings — b·m instead of b^d — which is the difference between a few thousand nodes and a few billion. In exchange it can return an absurdly long path, and its time bound depends on m (how deep the tree goes) rather than d (how deep the answer is), so a shallow solution hidden on the right can take exponentially long to reach.

Best-first search — the general framework

The idea that unifies everything
Keep the frontier in a priority queue ordered by an evaluation function f(n). Always expand the node with the lowest f. Every algorithm this week is just a different choice of f.
Algorithmf(n)Effect
BFSdepth(n)shallowest first
DFS−depth(n)deepest first
UCSg(n) — cost so farcheapest-so-far first
Greedy (Part 3)h(n) — estimate to goalclosest-looking first
A* (Part 3)g(n) + h(n)best total estimate first
This is the single most useful fact in the topic
You don't have five algorithms to memorise — you have one algorithm and five values of f. If you can write best-first search, you can write all of them. It also explains the exam favourite "what happens to A* when h ≡ 0?": f = g + 0 = g, which is literally the UCS row.

Uniform-cost search

Definition
f(n) = the sum of the action costs from the start state to n — usually written g(n). Expand the node with the smallest accumulated cost.

UCS finds the minimum-cost plan, not the minimum-action plan.

The slide's worked contrast
On the same map, from D to BUCHAREST:
  • BFS — D → F → BUCHAREST: 2 actions, total cost 99 + 211 = 310
  • UCS — D → E → G → BUCHAREST: 3 actions, total cost 80 + 97 + 101 = 278

BFS wins on hop count, UCS wins on distance. Neither is "wrong" — they optimise different things. 310 vs 278 is the number to remember.

PropertyUCS
Complete?Yes
Optimal?Yes (for non-negative costs)
Timeproportional to the number of nodes with cost less than the cost of the goal
Spacesame
Read that complexity carefully
UCS's cost is measured in cost contours, not depth: it expands every node cheaper than the optimal goal before it stops. If lots of cheap actions surround the start, that's a lot of nodes. And note that UCS uses no information about where the goal is — it expands outward in all directions equally. Fixing that is exactly what Part 3 does.

Exam-style takeaways

Key things to nail for Part 2
  1. The definition — search computes a sequence of actions that form a path to a goal.
  2. The five components — state space; initial state + goal test; actions; transition model; action costs. Be able to fill them in for an unfamiliar problem (tiles, navigation, coins).
  3. Search tree — node = state, edge = action; redundant paths make it infinite; prevent by checking parents up to the root, or by tracking visited states.
  4. BFS — queue + reached; complete yes; optimal yes if equal costs; time and space b + b² + … + b^d.
  5. DFS — deepest first; complete yes if redundant paths prevented; optimal no, returns the left-most solution; time b^m; space b·m.
  6. Best-first — priority queue on f(n); BFS is f = depth, DFS is f = −depth. Everything else is a choice of f.
  7. UCS — f(n) = g(n), the summed cost from the start; finds minimum-cost, not minimum-action plans; complete and optimal; time and space proportional to the number of nodes cheaper than the goal.
  8. The 310 vs 278 contrast — BFS's 2-action route costs more than UCS's 3-action route. It's the cleanest way to show you understand what "optimal" is relative to.
