Forward Chaining & RPG

where a domain-independent heuristic comes from

Forward-chain planning

The algorithm
  • Choose a state s and expand it, beginning with the initial state Sinit.
  • Consider the actions applicable in s — those whose preconditions are satisfied in s.
  • One successor state s′ is generated for each applicable action a:
    S′ = S − {delete effects of a} + {add effects of a}
  • Create a plan for S′ by chaining a to the end of the plan for s.
  • A goal state is a state containing the goal conditions. If the state does not satisfy them, loop and expand more states.
This is Topic 01's search, with the graph generated on the fly
Node = a set of facts. Edge = a ground action. "Expand" means: find every action whose preconditions are in this fact set, and apply the delete-then-add rule.

Delete first, then add — the order matters when an action both deletes and adds the same fact. And note the goal test is a subset test, not equality: a goal state is any state containing the goal conditions, so many different full states can be goals.

What a planner is
A planner takes the domain, the initial state and the goal, and generates a plan — a sequence of actions from A which transforms Sinit into Sgoal. It performs search to consider the different possible plans available until Sgoal is found.

"How do we know this is the best state?"

The question left hanging
Forward chaining generates a tree of states. Fine — but which one should you expand next? Topic 01's answer was A*, which needs h(n). So: is it possible to define heuristics that work for any PDDL domain?

Yes — domain-independent heuristics. No knowledge about the specific problem is used.

Why this is harder than the Romania map
In Topic 01 you had straight-line distance handed to you — a human looked at the map and supplied it. A planner is given an arbitrary PDDL file it has never seen and must invent its own heuristic from the domain description alone. The recipe is the one from Topic 01: relax the problem. The only question is which constraint to drop.

The Relaxed Planning Graph

Definition
The Relaxed Planning Graph (RPG) is a domain-independent heuristic used in actual planners (e.g. the FF planner).
  • It involves finding a plan from the current state S which achieves the goals G but ignores the delete effects of each action.
  • The length of this plan is used as the heuristic value for the state S.

J. Hoffmann and B. Nebel, 2001, "The FF Planning System: Fast Plan Generation through Heuristic Search", Journal of AI Research vol. 14.

Ignoring deletes is the relaxation — and it's the perfect one
Drop the delete lists and facts can only ever become true, never false. Nothing you do can undo anything, so there is no such thing as a wrong move and no need to backtrack. The relaxed problem is solvable in polynomial time.

And because the relaxed problem is easier — every real plan is still a valid relaxed plan — its optimal length can never exceed the real one. That's admissibility, straight from Topic 01. (The relaxed plan that FF actually extracts isn't guaranteed optimal, so hFF is not strictly admissible — but the idea is the same, and it works extremely well in practice.)

Fact layers and action layers

The construction rules
  • The RPG is made of alternating fact layers and action layers.
  • The first fact layer f(0) is the initial state of the problem.
  • Fact layer f(n) determines which actions can appear in action layer a(n+1) — those whose preconditions are satisfied in f(n).
  • f(n+1) = f(n) plus all the add effects of the actions in a(n+1) — remember we ignore delete effects!
  • Hence fact layers get bigger and bigger as more actions become applicable.
Two consequences of "fact layers only grow"
It always terminates. There are finitely many ground facts, so eventually a layer adds nothing new — a fixpoint. If the goals aren't in that fixpoint, no relaxed plan exists, so no real plan exists either, and the state can be discarded outright. That's a free dead-end detector.

And the layer at which a fact first appears is a measure of how hard it is to achieve — that number is what the extraction phase turns into a heuristic.

For our state, the graph builds like this:

Why nothing involving A appears in a(1)
A has C sitting on it, so clearA is false in f(0) and no action can move A. Once any action in a(1) shifts C off A, clearA enters f(1) — and a pile of actions become applicable at once. Watch clearA: it is the fact that unlocks the layer.
a(2) is bigger than it looks — and that's the relaxation showing through
Six actions are usually listed in a(2); the true count is nine. The extra three are B to A from C, C to A from B and C to T from B, and they are applicable for a revealing reason.

f(1) contains both onBT and onBC — B is on the table and on C at the same time. That is physically impossible, and it happens precisely because we deleted nothing. So the relaxed graph offers moves the real world never would.

This is exactly why the RPG under-estimates: the relaxed world is more permissive than the real one. It doesn't affect the answer here — the extraction still picks the same three actions and h = 3 — but if you're listing a(2) by hand, don't stop at six. The RPG builder tool below shows all nine.

Extracting the relaxed plan

The backwards pass
To get a solution, work backwards through the RPG. At each fact layer f(n) we have goals to achieve, g(n). Start with g(n) containing the problem goals. For each fact in g(n):
  • If it was already in f(n−1), add it to g(n−1).
  • Otherwise, choose an action from a(n) that achieves it, and add its preconditions to g(n−1).

Stop when you are at g(0).

The worked extraction

g(2) = {onAB, onBC} — the problem goals.

  • onAB was not in f(1) → need the action "A to B from T", whose preconditions are clearA, onAT, clearB.
  • onBC was already in f(1) → carry it straight down.

g(1) = {clearA, clearB, onAT, onBC}

  • clearB and onAT were in f(0) → carry down.
  • onBC was not in f(0) → need "B to C from T" (preconditions clearB, onBT, clearC).
  • clearA was not in f(0) → need "C to T from A" (preconditions clearC, onCA).

g(0) = {clearB, onAT, clearC, onBT, onCA} — all in the initial state. Done.

Final relaxed plan:
O₀ = { Put C on T from A , Put B on C from T }
O₁ = { Put A on B from T }
h(s) = |O₀| + |O₁| = 2 + 1 = 3
Constructing the RPG value — the formal statement
For each state S reached during forward search, the length of the relaxed plan P′ which achieves the goals G starting from S is computed. This is an estimate of the goal distance.

P′ = ⟨O₀, O₁, …, Om−1⟩, where each Oi is the set of actions selected in parallel at time step i, and m is the number of the first fact layer containing all goals.

h(s) := Σ |Oi|

i.e. the heuristic is an estimate of the sequential solution length.

h is the number of actions, not the number of layers
Here m = 2 layers but h = 3, because O₀ contains two actions. Summing |O_i| rather than counting layers is what makes it an estimate of the sequential plan length — you still have to execute those two actions one after another. Confusing the two is the standard mistake.
Sanity-check it against the real plan
The genuine plan here is also three moves: C→table, B→C, A→B. So h = 3 is exact for this state — the relaxation cost nothing, because no action needed to undo another. RPG becomes an under-estimate precisely in the states where you must dismantle something you built, since the relaxed version never has to take it apart again.

How the RPG is used in a planner
  • RPG provides a heuristic automatically — no domain knowledge.
  • Use it in heuristic search (e.g. A*) where h comes from the RPG.
  • Every time we want to add a new node to the open list, we solve a simplified version of the problem (the RPG) to find out h.
Read that last bullet twice
The heuristic is not a lookup — it is an entire sub-problem solved from scratch for every single node. That is enormously more expensive per node than Topic 01's straight-line distance. It pays off anyway, because the reduction in nodes expanded is far larger than the extra cost per node — and it is the reason FF beat the field in 2000.

Exam-style takeaways

Key things to nail for Part 4
  1. Forward-chain planning — expand a state, find the applicable actions, and for each one produce S′ = S − {delete effects} + {add effects}, chaining the action onto the plan.
  2. A goal state is a state containing the goal conditions — a subset test, not equality.
  3. Put X on Y from Z — pre: clear X, on X Z, clear Y; add: clear Z, on X Y; del: on X Z, clear Y.
  4. Domain-independent heuristics work for any PDDL domain using no problem-specific knowledge.
  5. RPG — find a plan from S achieving G that ignores the delete effects; the length of that plan is h(S). Used in FF (Hoffmann & Nebel 2001).
  6. Construction — f(0) is the initial state; a(n+1) holds the actions whose preconditions are satisfied in f(n); f(n+1) = f(n) + the add effects of a(n+1); layers only grow.
  7. Extraction — start with g(m) = the goals; a fact already in f(n−1) drops straight down, otherwise pick an action from a(n) and add its preconditions to g(n−1); stop at g(0).
  8. h(s) := Σ |Oi|, where Oi is the set of actions chosen at step i and m is the first fact layer containing all goals. It estimates the sequential plan length.
  9. Be able to run the demo by hand — from onCA, onAT, onBT, clearB, clearC to onAB, onBC: a(1) = {C to T from A, C to B from A, B to C from T}; the plan is Put C on T from A, Put B on C from T, Put A on B from T; h = 3 over 2 layers.
  10. Using it — A* with h from the RPG, recomputing the RPG for every node added to the open list.
