PDDL Basics

the language every planner speaks

Language + algorithm

The general approach to solving planning problems
  • A planning language — allows you to write the definition of a planning problem in text.
  • A planning algorithm — allows you to solve any problem given to it in that language.
This separation is the entire idea
Because the language is standard, your model and their solver are independent. Improve the model and every planner benefits; improve the planner and every model benefits. It is the same bargain as SQL: describe what, and someone else's engine works out how.

Hence the long list of planners in the slides — Zeno, FF, MetricFF, VHPOP, Marvin, Crikey, POPF, MIPS-XXL, LPGP, LPRPG, CoLin, Fast Downward, UPMurphi, Gamer, MBP — all competing in the International Planning Competition, all consuming the same input.

PDDL and its versions

PDDL — Planning Domain Definition Language
The standard language spoken by the planners. If you write a correct model of your planning problem in PDDL, you can use existing planners to solve it.

Different versions (levels), each able to handle different features:

PDDLpropositional planning
PDDL 2.1numbers + time
PDDL 3preferences
PDDL+continuous change, processes, events

Domain and problem files

Domain file — one

  • General description of the world.
  • Which types of objects are involved.
  • What actions can be applied, etc.

Problem file(s) — many

  • The specific situation you want to solve.
  • List of objects.
  • Initial state, goal state.
One domain, many problems
The slides draw one Domain in the middle with eight Problems orbiting it. That's the shape to remember: the rules of the world are written once, and each puzzle you want solved is a small file naming the objects, what's true at the start, and what you want true at the end.

Quick test of whether something belongs in the domain: would it still be true for a different puzzle in the same world? "A gripper can hold one ball" → domain. "There are four balls and they start in room A" → problem.

The Gripper domain

The problem
A robot can move between two rooms and pick up or drop balls with either of his two arms.
  • Initial state: balls b1..b5 in room A, robot in room A.
  • Goal state: balls b1..b5 in room B, robot in room B.
  • Actions: move from one room to the other; pick up a ball in a gripper; drop a ball.

Where the "two arms" constraint actually is
Nowhere explicit — it falls out of free(g). PickUp requires the gripper to be free and deletes that fact; Drop restores it. So each gripper holds at most one ball, and with two gripper objects the robot carries at most two. There's no counting anywhere. That's the classical-PDDL style: capacity limits are encoded as facts that get consumed and released. When you want to say "capacity 4" instead of "capacity 1", you need fluents — Part 3.

In PDDL

Objects and predicates:

(:objects roomA roomB
          ball1 ball2 ball3 ball4
          left right)

(:predicates (ROOM ?x) (BALL ?x) (GRIPPER ?x)
             (at-robot ?x) (at ?x ?y)
             (free ?x) (carry ?x ?y))
Why ROOM, BALL and GRIPPER are predicates here
This version of PDDL has no type system, so "x is a room" has to be stated as an ordinary fact — hence the upper-case type predicates, asserted in :init and tested in every precondition. With :typing (used in Part 3) you write ?x - room instead and the checking is free. Conventionally the type predicates are capitalised so you can see at a glance which preconditions are real and which are just type checks.

Initial state:

(:init (ROOM rooma) (ROOM roomb)
       (BALL ball1) (BALL ball2) (BALL ball3) (BALL ball4)
       (GRIPPER left) (GRIPPER right)
       (free left) (free right)
       (at-robot rooma)
       (at ball1 rooma) (at ball2 rooma)
       (at ball3 rooma) (at ball4 rooma))

Goal state:

(:goal (and (at ball1 roomb)
            (at ball2 roomb)
            (at ball3 roomb)
            (at ball4 roomb)))

The three actions:

(:action move
 :parameters (?x ?y)
 :precondition (and (ROOM ?x) (ROOM ?y)
                    (at-robot ?x))
 :effect
   (and (at-robot ?y) (not (at-robot ?x))))

(:action pick-up
 :parameters (?x ?y ?z)
 :precondition (and (BALL ?x) (ROOM ?y) (GRIPPER ?z)
                    (at ?x ?y) (at-robot ?y)
                    (free ?z))
 :effect
   (and (carry ?z ?x) (not (at ?x ?y)) (not (free ?z))))

(:action drop
 :parameters (?x ?y ?z)
 :precondition (and (BALL ?x) (ROOM ?y) (GRIPPER ?z)
                    (carry ?z ?x) (at-robot ?y))
 :effect
   (and (at ?x ?y) (free ?z) (not (carry ?z ?x))))
The syntax rules worth writing on a cheat sheet
  • Everything is a parenthesised list — Lisp style.
  • ?x is a variable; a bare name is an object.
  • An action has :parameters, :precondition, :effect.
  • Multiple conditions are joined with (and …).
  • Delete effects are written (not (fact)) inside the effect — there is no separate delete list.
  • The goal is (:goal (and …)), the start is (:init …).

The full domain file

(define (domain gripper-strips)
  (:predicates (room ?r) (ball ?b) (gripper ?g)
               (at-robot ?r) (at ?b ?r) (free ?g) (carry ?o ?g))

  (:action move
     :parameters (?from ?to)
     :precondition (and (room ?from) (room ?to) (at-robot ?from))
     :effect (and (at-robot ?to) (not (at-robot ?from))))

  (:action pick
     :parameters (?ball ?room ?gripper)
     :precondition (and (ball ?ball) (room ?room) (gripper ?gripper)
                        (at ?ball ?room) (at-robot ?room) (free ?gripper))
     :effect (and (carry ?ball ?gripper) (not (at ?ball ?room))
                  (not (free ?gripper))))

  (:action drop
     :parameters (?ball ?room ?gripper)
     :precondition (and (ball ?ball) (room ?room) (gripper ?gripper)
                        (carry ?ball ?gripper) (at-robot ?room))
     :effect (and (at ?ball ?room) (free ?gripper)
                  (not (carry ?ball ?gripper)))))
Summary of the deck
  • PDDL allows us to define problems in a set-theoretic language.
  • Domain files store all the predicates and actions we require.
  • We store the actual problem instances in other files.

Appendix: the Blocks World domain

Five predicates, four actions. This is the domain Part 4 uses, so it's worth knowing well.

(:predicates (on ?x ?y) (ontable ?x) (clear ?x) (handempty) (holding ?x))
(define (domain blocks)
  (:predicates (on ?x ?y) (ontable ?x) (clear ?x) (handempty) (holding ?x))

  (:action pick-up
     :parameters (?x)
     :precondition (and (clear ?x) (ontable ?x) (handempty))
     :effect (and (not (ontable ?x)) (not (clear ?x))
                  (not (handempty)) (holding ?x)))

  (:action put-down
     :parameters (?x)
     :precondition (holding ?x)
     :effect (and (not (holding ?x)) (clear ?x)
                  (handempty) (ontable ?x)))

  (:action stack
     :parameters (?x ?y)
     :precondition (and (holding ?x) (clear ?y))
     :effect (and (not (holding ?x)) (not (clear ?y)) (clear ?x)
                  (handempty) (on ?x ?y)))

  (:action unstack
     :parameters (?x ?y)
     :precondition (and (on ?x ?y) (clear ?x) (handempty))
     :effect (and (holding ?x) (clear ?y) (not (clear ?x))
                  (not (handempty)) (not (on ?x ?y)))))
The four actions come in two mirror pairs
pick-up ↔ put-down (table) and unstack ↔ stack (another block). Each pair swaps handempty for holding ?x and back.

Note that (clear ?x) is deleted when you pick a block up — because while you're holding it, nothing can be placed on it either. And the table is never mentioned as an object: "on the table" is its own predicate, ontable. Part 4's slides simplify all four of these into a single action, Put X on Y from Z, by treating the table as just another destination.

Exam-style takeaways

Key things to nail for Part 2
  1. Language + algorithm — a planning language lets you write the problem down; a planning algorithm solves any problem written in it.
  2. PDDL = Planning Domain Definition Language, the standard language spoken by planners.
  3. The versions — PDDL propositional · PDDL 2.1 numbers + time · PDDL 3 preferences · PDDL+ continuous change, processes, events.
  4. Two file types — one domain file (types, predicates, actions) and many problem files (objects, initial state, goal).
  5. Be able to write an action: :parameters, :precondition, :effect, with (and …) and delete effects as (not (…)).
  6. Be able to reproduce the Gripper table — Move / PickUp / Drop with their parameters, preconditions and effects, and translate it into PDDL.
  7. Type predicates like (ROOM ?x) exist because plain PDDL has no type system.
  8. Blocks World — predicates on, ontable, clear, handempty, holding; actions pick-up, put-down, stack, unstack.
  9. A likely exam task: given an informal domain description, write the PDDL predicates and one or two actions. Practise on something unfamiliar.
