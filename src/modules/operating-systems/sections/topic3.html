Topic 03 · Memory Management

Virtual Memory & Address Translation

how every process gets the illusion of its own private memory

This is one of the deepest topics in the course. It solves a single problem in progressively cleverer ways. The whole topic is a story: each solution fixes a flaw in the one before. Understanding why each step happens is the key to the entire topic.

The evolution at a glance
Load-time relocation → Base & limit registers → Segmentation → Paging → Multi-level page tables. Each step trades complexity for better fault isolation, security, and less fragmentation.

The address-binding problem

Recall the OS gives each process the illusion of its own computer — including its own memory. We need this for:

  • Reliability: stop a buggy process from corrupting another's memory.
  • Security: stop a malicious process from reading/trashing another's memory — or the OS's.

But here's the catch. Programs embed memory addresses directly in their machine code. An instruction like callq 0x001330 references a specific, concrete address baked into the binary:

83 ff 02 cmp $0x2,%edi 53 push %rbx 74 07 je 0x00139d ; jump to a fixed address e8 93 ff ff ff callq 0x001330 ; call code at a fixed address 48 8b 3e mov (%rsi),%rdi be 0d 3f 00 00 mov $0x003f0d,%esi ; load from a fixed address
The problem in a nutshell
How can programs be written as if memory is private to themselves (concrete instructions referencing specific addresses)... but still execute in a shared slice of physical memory... efficiently, reliably, and securely? If two processes both want to start at address 0, they can't both physically be there!

Why the obvious "non-solutions" fail

IdeaWhy it fails
Only keep one program in memory at a timeForgoes efficiency & functionality; swapping all of memory to/from disk on every switch is unworkably slow.
Statically assign address ranges to programsWhat about multiple instances of the same program? How much does each need? Causes unworkable fragmentation; every program needs space reserved at all times.

Solution 1 · Load-time relocation

We already have to copy a program into memory to run it. Idea: while copying, rewrite all its embedded addresses to point to wherever we actually placed it.

// Original (assumes load at 0x0) je 0x00139d callq 0x001330 mov $0x003f0d,%esi
// Relocated to load at 0x400000 je 0x40139d callq 0x401330 mov $0x403f0d,%esi

The fatal flaws
No fault isolation: a buggy process can still trash another's (or the OS's) memory — nothing stops it. No security: a malicious process can read/trash anything. Plus rewriting is slow and blocks memory sharing. Relocation solves address binding but nothing else.

Solution 2 · Base & limit registers (a simple MMU)

Add hardware to the CPU: a Memory Management Unit (MMU) with two special registers:

  • Base: where this process's memory starts in physical RAM.
  • Limit: how big its region is.

Now every memory access is checked by the hardware: the address must fall within [base, base+limit]. The CPU adds the base automatically, so the program still thinks it starts at 0.

1
Program issues a virtual address, e.g. 0x1000 (thinks it owns memory from 0).
2
Hardware checks: is 0x1000 < limit? If no → hardware interrupt → OS kills the process.
3
If yes: physical address = base + 0x1000.

Key mechanics
Base and limit are set by privileged instructions (kernel mode only). On a context switch, they're saved and restored — just like other registers. On a system call, they're saved and reset, restored on return. This is how the OS controls each process's memory window.

Two kinds of fragmentation (important!)
Internal: wasted space inside a process's allocated region (allocated but unused). External: free memory exists but is scattered in non-contiguous chunks, so a big new process won't fit anywhere. Fragmentation is a problem whenever allocations must be contiguous.

Solution 3 · Segmentation

A natural evolution: instead of one (base, limit) pair per process, support many. Each pair is a segment — a logical chunk like the stack, code, or data.

A complete address becomes a pair (s, o) — segment number + offset. Each segment has its own base, limit, and even permission bits (e.g. can't write to a code segment, can't execute a stack segment).

Segmented process

Instructions usually have a default segment: a jump works within the text segment, a stack push uses the stack segment, etc. This was historically handy for extending the address space of small-word-size machines — e.g. a 16-bit machine naturally gets multiple 64kB segments. (The Intel 80286 of 1982 used exactly this: 16-bit segment offsets, 24-bit physical addresses, with DS/CS/SS/ES segment registers.)

The remaining headache
Segments have a "funny shape": different sizes, can overlap, need contiguous physical memory. Even if lots of RAM is free, if it's not contiguous the OS may fail to load a new program. The MMU is also complex to build for arbitrary sizes/alignments. This is what paging fixes.

Solution 4 · Paged virtual addressing

The key insight: "What if we had lots and lots of segments, but all the same small size?"

Divide physical memory into equal-sized frames (e.g. 4kB each), aligned from zero. Divide each process's virtual address space into same-sized pages. A page is just a frame-sized chunk of virtual memory; once mapped to a frame, it's "a mapped frame."

Why equal sizes are magic
Any aligned 4kB physical chunk is as good as any other → no external fragmentation. Contiguous virtual areas need not be contiguous physically. Internal fragmentation is limited: worst case a program wastes only 4,095 bytes (the tail of its last page).

Splitting an address into page number + offset

With 4kB pages, the low 12 bits of any address are the offset (since 2¹² = 4096), and the upper bits are the page number. (One hex digit = 4 bits, so the offset is the bottom 3 hex digits.)

page number pupper bits
offset olow 12 bits

Programs only ever use virtual addresses (p, o). The MMU's job is to translate the page number p into a physical frame number f, leaving the offset o untouched.

Address translation & the page table

Each process has its own page table: conceptually an array mapping page number → frame number. The PTBR (page table base register) tells the MMU where the current process's page table lives.

Problem 1: it's now TWO memory accesses

What was one access is now two: (1) look up the page table for the translation, then (2) do the actual access. Memory is already slow — won't doubling it be unacceptable?

Solution: the TLB
Add a hardware cache of recent page-table entries to the MMU — the TLB (Translation Lookaside Buffer). It's a custom, very fast content-associative memory storing recently-used translations. It exploits locality of reference (programs tend to reuse the same pages).

📘 Why the TLB works: a concrete example (OSTEP Ch.19)
Imagine looping over an array of 10 integers, with a tiny page size where 4 array elements fit per page. Walking through the accesses:

a[1]VPN 6hit
a[2]VPN 6hit
a[3]VPN 7MISS
a[4]VPN 7hit
a[5]VPN 7hit

Only the first access to each page misses; the rest hit because they're on the same page already cached. That's 3 misses, 7 hits → 70% hit rate, even on the very first pass through the array. Two reasons caches like the TLB work:

  • Spatial locality: if you access address x, you'll likely soon access something near x (e.g. the next array element). Bigger pages → even fewer misses.
  • Temporal locality: if you access something now, you'll likely access it again soon (e.g. a loop variable). Loop over the array a second time and you'd get 10/10 hits.
📘 Who handles a TLB miss? (hardware vs software)
Hardware-managed (CISC, e.g. x86): the hardware itself knows the page-table format, "walks" it on a miss, fills the TLB, and retries — no OS involvement.

Software-managed (RISC, e.g. MIPS/SPARC): on a miss the hardware just raises an exception; an OS trap handler does the lookup, updates the TLB with a privileged instruction, and returns so the instruction retries.

Subtle detail: unlike a syscall's return-from-trap (which resumes at the next instruction), a TLB-miss return-from-trap must retry the same instruction — this time it hits.
📘 Why not just build one giant TLB/cache?
Because physics. A fast cache must be small — speed-of-light and other physical constraints mean any large memory is inherently slow. So we're stuck with small, fast caches, and the whole art is using them well (exploiting locality to make the common case fast).

Problem 2: page tables are huge

In a 32-bit address space with 4kB pages: offset is 12 bits, so the page number p is 20 bits → 2²⁰ = 1,048,576 entries per process! If each entry is 4 bytes:

PT size = m × 2ⁿ = 4 bytes × 2²⁰ = 4,194,304 bytes = 4 MB per process // just for the page table!

That's unacceptable per process. The fix is the next topic.

What's actually in a Page Table Entry (PTE)?
Not just a frame number! A real PTE also has flag bits: V (valid?), R/W (permissions), U (used?), D (dirty?), plus the frame number. E.g. in a 32-bit PTE, 6 bits for flags + 26 bits for the frame number.

Solution 5 · Multi-level page tables

The insight: most processes don't use all 2ⁿ pages, so most page-table entries are invalid (empty). Why store a giant array that's mostly empty? Use a data structure that handles sparseness better — a tree (of fixed depth, since hardware isn't recursive).

A simpler first attempt: PTLR
Before the tree: a Page Table Length Register caps the table length — start short, grow on demand. But it requires the virtual address space to be contiguous (breaks our "stack grows down, heap grows up" layout with two growable areas), and growing still needs contiguous physical memory. The tree handles both.

How the two-level scheme works

Split the 20-bit page number into two 10-bit halves. The top 10 bits index a page directory (root); the bottom 10 bits index a leaf page table. Each table has 2¹⁰ = 1024 entries (a "1024-ary tree" of depth 2).

The magic: if an entry in the page directory is marked invalid (X), that means an entire chunk of the page table is unused — and doesn't need to be stored at all. That's the space saving.

Two-stage translation (worked example)

Translating virtual address 0xfffff123 → physical 0xf00f123:

p[high] = 1023top 10 bits
p[low] = 1023next 10 bits
o = 0x123offset
1
Index the page directory by the high bits of p (1023) → get a pointer to the relevant leaf page table.
2
Follow that pointer to the leaf-level page table.
3
Index the leaf table by the low bits of p (1023) → retrieve frame number f = 0xf00f.
4
Combine with the unchanged offset o = 0x123.
physical address = 0xf00f123

The trade-off, and why TLBs become critical

The idea generalises — modern 64-bit architectures (secretly usually only 48-bit) often use 4 levels (on x86-64: PML4, PDP, PD, PT). But each level adds a memory access!

The performance crunch
A 4-level scheme means 4 extra memory accesses for every single translation — on top of the actual access. This would be catastrophic without the TLB. Like any cache, a TLB lookup either hits (use the cached translation — fast) or misses (do the full multi-level walk). The more levels, the more critical TLB hit rate becomes.
AspectMulti-level page tables
Space overhead✓ Greatly reduced (unused chunks not stored)
Sparseness handling✓ Excellent (tree, not flat array)
Lookup speed~ Slower (more levels = more accesses) — relies on TLB
Number of levels depends on...
(1) the size of the virtual address space, and (2) the page size (how many bits are in p vs o). More levels = slower lookups = TLB performance matters more.
