Topic 05 · User-Space Topics

malloc, the Stack, Files & I/O

the machinery that lives on top of the kernel

This topic steps up from the kernel into user space — the things that run on top of the OS but lean heavily on it. Four threads, all connecting back to ideas you've already met (fragmentation, the stack, system calls, interrupts).

malloc & the heap

The OS only deals in big chunks of memory — at least a page. But programs want small pieces: malloc(42 * sizeof(int)) wants 168 bytes, not a 4kB page. The job of a memory allocator (malloc/free in C, new/delete in C++) is to parcel out small pieces from a bigger chunk the OS gave it — the heap.

What malloc actually means
int *pn = malloc(42 * sizeof(int)); means: "find a free range of ≥ 168 bytes, chop out 168 bytes, mark it as used, and return a pointer to the start." free(pn) does the opposite: "mark this chunk as free." Crucially, the OS has nothing to do with these calls — both malloc and new are library code running inside the user process.

Why study malloc?

  • Allocators do use the OS to get their raw memory (in page-sized chunks and larger).
  • An OS kernel has its own internal malloc-like allocator for its own use.
  • They show another layer of fragmentation — this time within the heap, on top of the OS's page-level fragmentation.
  • Higher-level languages (C++, Java, Python) almost always have a malloc-like allocator underneath.
Two layers of allocation
From the OS's point of view, the whole heap arena is "allocated" to the process. From malloc's point of view, parts of that arena are still "free." So you have allocation-within-allocation, and fragmentation-within-fragmentation. malloc means manual — here we only consider manual memory management (you call free/delete yourself), not garbage collection.

First-fit vs best-fit

Allocation involves a search through the free list. Two classic strategies:

StrategyHowTrade-off
First-fitUse the first free block big enoughFast (stops early), but can leave awkward leftovers near the list head
Best-fitSearch all blocks, use the smallest that fitsLess wasted space per allocation, but slower (must scan everything) and can create tiny unusable fragments

A better real-world structure: segregated free lists — separate lists bucketed by size class, so the search is much faster.

Getting more memory: brk & mmap

When the heap is full and fragmented, a big malloc can't be satisfied. The allocator must ask the OS for more memory via a system call. Two ways on Unix-like systems:

brk() — the classic

Moves the program break (the end of the heap; a vestige of segmentation!) to a later address, gaining memory in between. The break's location is part of the per-process state the OS maintains. brk(curbrk + 100*PAGE_SIZE) asks for 100 more pages.

mmap() — the modern, flexible way

Doesn't care about the program break. Returns a fresh, possibly non-contiguous arena anywhere. malloc can add it to the free list. No contended single resource (unlike the one program break), so it's better for multi-threaded allocators.

Connecting back to demand paging
Asking for memory via brk/mmap need not allocate physical memory immediately — it just reserves virtual address space. Physical frames arrive lazily on first access, via page faults (Topic 04!). Note mmap with MAP_ANONYMOUS gives blank memory; mapping a named file instead is how you get memory-mapped files.
malloc is a highly-optimised concurrent codebase
Many threads may call malloc() at once, so the free list must be concurrent (thread-safe). Doug Lea — who designed much of java.util.concurrent — also wrote dlmalloc, one of the most widely-used implementations. (InfOS's kernel malloc is dlmalloc, for the kernel's own chunk allocation; frames use a different algorithm.) Real allocators are measured per workload (a program+input pair) on speed of alloc/free and internal/external fragmentation.

The stack in depth

Back to the stack — now in detail, because (a) you need it for the mini-project, and (b) many security exploits target it. When a function is called, a stack frame (or "activation record") is pushed. In the x86-64 scheme shown in the lectures, the first two things in each frame are:

  1. The caller's return address (saved program counter — where to jump back to)
  2. The caller's frame pointer (saved rbp)

...followed by saved registers and local variables (e.g. that Hello, world! buffer, or saved rbx/r12).

Two things the stack encodes
Using the frame pointer, you can "walk up" the stack, following the chain of frames. This tells you:
  • History — what uncompleted calls got us here? (Useful for a backtrace when debugging — that's the Medium mini-project.)
  • Continuation — where will we return to next? (One answer per active call.)

Influence the stack and you influence the program's future. That sentence is the entire premise of the next section.

A lovely detail
The instruction movabs $0x77202c6f6c6c6548, %rax in the hello-world disassembly looks like a magic number — but those 8 bytes, read little-endian, literally spell "Hello, w". The string is being loaded as an immediate integer constant.

Buffer overflows & stack smashing

Consider this innocent-looking program:

char buf[10]; scanf("%s", buf); // read a string into buf... return 0;

Danger: what if you type more than 10 characters? scanf doesn't check the buffer size — it just keeps writing. The stack grows toward lower addresses but arrays fill toward higher addresses, so an over-long input writes past the buffer and over the saved registers, the saved frame pointer, and eventually the return address.

The attack
If an attacker knows the address of a powerful library function elsewhere in the process, they can craft input where the overflowing bytes are that address — overwriting the return address so that when main returns, it "returns" into the attacker's chosen code instead. This is a stack-smashing attack, a kind of buffer overflow.

Why does this happen — and why doesn't the compiler stop it?

When array indexing / pointer arithmetic is not bounds-checked, the code is trusting that input won't exceed the buffer. C and C++ don't insert bounds checks by default (for speed, and because the language permits raw pointer arithmetic that makes checks hard). Safer interfaces exist and should be used: strncpy() over strcpy(), vector::at() over operator[].

📘 Why can Java do this but C can't?
Java arrays carry their length and the runtime bounds-checks every access (throwing ArrayIndexOutOfBoundsException). C arrays are just raw memory with no length attached, and pointer arithmetic can produce any address — so the compiler often can't know the bound to check. That safety is exactly what C trades away for speed and low-level control.

Files, handles & inter-process communication

Processes are inherently communicative — with the OS and with each other. They make requests in terms of identifiable objects ("write these bytes to this file", "listen on this network interface"), identified using handles.

Why opaque handles, not addresses?
Processes don't share memory with the OS → they can't use memory addresses to name kernel objects. They also can't use device-level identifiers (the OS abstracts those away), and some "objects" are pure OS constructs (threads, processes) with no hardware identifier at all. So the OS hands out an opaque handle — in InfOS, an arbitrary 64-bit integer; in Unix, a small int called a file descriptor (fd) — that indexes a table the OS controls.

File descriptors

A Unix process starts with three open file descriptors by default:

0
standard input (stdin)
1
standard output (stdout)
2
standard error (stderr)
3
→ first file you open()
4
→ a network socket, perhaps

An fd can refer to many kinds of object: terminals, files on disk, network connections, devices (sound card, camera). Most support read() and write(); some support extras like seek() (files, but not live audio) or the catch-all ioctl().

You could say fds are "dynamically typed" — the same interface, many underlying object types. (Threads/processes are the exception — they use pid_t/tid_t, not fds.)

A security problem with handles
If a handle is just an integer indexing a table, what stops a process from guessing another handle's number and using it? The OS must check that the handle belongs to the process using it (the InfOS ObjectDescriptor records an owner thread for exactly this reason). Forgetting that check is a real vulnerability class.

Inter-process communication (IPC)

fds aren't just for devices — they're also channels to other processes:

  • Shared files — two processes read/write the same file.
  • Sockets on a loopback "network" card — local network-style comms.
  • Pipes — one-way in-memory channels.
  • Pseudo-terminals — two-way in-memory channels.
Avoiding slow user↔kernel crossings: shared memory
Every read/write is a system call (slow-ish mode switch). To avoid them, processes can share memory directly using the MMU: mmap() the same named file with MAP_SHARED (not MAP_PRIVATE). Now both processes see the same physical frames and can communicate by simply reading/writing memory — no syscall per exchange. This ties paging (Topic 03–4) directly to IPC.

How I/O works (intro)

I/O devices are many and varied, so it's not workable for each program to know each device. Device drivers are the OS's code for talking to a specific device, exposing a higher-level, device-agnostic interface to the rest of the OS — which is then abstracted further to user programs via system calls. Devices must also be multiplexed securely and concurrently. There are three evolutionary approaches to actually moving the data:

1

Programmed I/O + polling

The CPU writes commands to the device's I/O ports, then repeatedly asks "are you done yet?" in a loop (polling the status register). Problem: the disk is millions of CPU cycles slow — the CPU is kept 100% busy doing nothing useful. Very inefficient.

2

Interrupt-driven I/O

The CPU issues the command then carries on with other work. When the device finishes, it raises a hardware interrupt: the CPU saves its registers, looks up the handler in the interrupt table, and jumps to it. The handler reads the now-ready data. Far less wasted time. (An interrupt controller, e.g. an APIC on x86, multiplexes the interrupt line between devices.)

3

Direct Memory Access (DMA)

A DMA controller transfers data between the device and memory by itself, without the CPU running in/out instructions for every word. The CPU is freed entirely during the transfer; it still gets one interrupt on completion, but by then the data is already in memory. Maximum efficiency.

Full-circle: timer interrupts & preemptive scheduling
Interrupts aren't just for talking to the outside world. The timer is itself a device on an I/O bus, programmed to interrupt the CPU at a set frequency. When the timer interrupt fires, its handler calls the scheduler to pick another process — which is exactly how preemptive Round-Robin (Topic 02) works, and how the OS guarantees it regains control (Topic 01's "limited direct execution"). Everything connects.
