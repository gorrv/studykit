Unix History & Microkernels

where operating systems came from — and where they didn't go
⚠ Examinability note
Most of this topic is reinforcement and context — fascinating, but non-examinable. Only two things here are examinable: fork() and exec() (OSTEP ch.5) and microkernels. Those two are marked with a ★ below. The rest is for your interest (and makes you a better-rounded engineer).

Why Unix matters context

Unix was created at AT&T Bell Labs in 1969–71 by Dennis Ritchie and Ken Thompson, as a deliberately simple reaction to the over-ambitious, delayed Multics project. Much of the technical vocabulary of OSes comes from Unix: kernel, shell, inode, pipe, root. It popularised concepts now taken for granted: hierarchical filesystem, byte-oriented files, shell commands as files, I/O redirection, forking processes. It became the basis of the POSIX standard.

Why so popular?
Deliberate simplicity; written mostly in a high-level language (C, created by Ritchie for the 1973 rewrite — radically lowering the cost of porting); and early academic licensing. This enabled use in education, portability across machines, and a wave of clones/derivatives. In the 1990s, free clones (Linux + GNU) and derivatives (the BSDs) displaced commercial Unix. Today almost all widely-used OSes are Unix-like — only Windows isn't (it's more VMS-based, though Unix-influenced).

Big idea (1): fork() & exec() ★ examinable

To create a new process in Unix, you don't build one from scratch — you fork() (duplicate) the current process, then optionally exec() (replace yourself with a different program).

The key fact about fork() — a classic exam point
fork() is called once but returns twice:
  • In the parent: returns the child's PID (a positive number).
  • In the child: returns 0.
  • On failure: returns negative (no child created).

Both processes then continue from the same point (right after the fork), each with their own copy of memory — implemented efficiently with copy-on-write (Topic 04!).

int rc = fork(); if (rc < 0) { // fork failed } else if (rc == 0) { // CHILD (new process) — rc is 0 // optionally set up fds/env, then exec() a new program } else { // PARENT — rc is the child's PID }

Why is fork-then-exec a good design?
Between the fork and the exec, the child can set itself up in code — hook up pipes/IPC channels, redirect file descriptors (e.g. dup2 to make stdout a pipe), modify the environment. This avoids needing a giant "mega-API" that can specify every attribute of a new process up front. It also makes sharing (memory, fds, IPC channels) between parent and child easy, and was great for concurrent servers in the pre-thread days.

Big idea (2): "Everything is a file" context

Instead of separate categories (with separate interfaces) for system commands, devices, and files, Unix maximises use of the single file abstraction:

  • Devices appear as special files (e.g. /dev/tty0, /dev/hd0).
  • Commands are just executable files.
  • Even non-file IPC (pipes) is accessed via file descriptors.
Good and bad
Good: avoids special interfaces, maximises compositionality (everything plugs together). Bad: not everything is conceptually a file! seek() makes sense for a file but not live audio/video; ioctl() is the catch-all for "any operation that doesn't fit." Unix gives no explicit way for files to express how they differ (operations, behaviour, formats). ("Use plain text; it is universal" was one optimistic rejoinder.)

Microkernels ★ examinable

A traditional Unix/Linux kernel is a monolith: filesystems, network stack, device drivers, scheduling, and memory management all run together in kernel mode. What's wrong with that?

Problems with the monolith
No fault isolation: kernels contain bugs — especially in device drivers (the classic cause of Windows' "blue screen of death"). One faulty driver can crash the whole system. No least privilege: kernels contain security exploits (search "CVE Linux kernel") — and every component runs with full privilege.

The microkernel idea: move as much as possible out of the kernel into ordinary, isolated server processes. The microkernel itself keeps only the bare minimum: interrupt handling and basic IPC primitives.

The catch: IPC overhead
Moving components into separate processes means far more crossing of protection boundaries — every interaction that used to be a function call is now IPC. This overhead was microkernels' big problem. Liedtke's work on the L3/L4 microkernels (1993+) showed that architecture-aware optimisation of IPC could hugely reduce these overheads.
The Tanenbaum–Torvalds debate (1992)
Microkernels were such a big deal that in 1992, OS professor Andrew Tanenbaum posted "LINUX is obsolete", arguing monolithic kernels were "a giant step back into the 1970s" and that among OS designers "the debate is essentially over — microkernels have won." History had other plans: Linux (monolithic) went on to dominate. The lesson isn't that one side was simply right — it's that development model and pragmatism often beat architectural elegance.
What Linux actually did instead
Linux kept the monolithic design (no driver fault isolation, no least privilege for kernel components) and the same old Unix user-space API. Its innovation was in the development model, not the architecture. To stay reliable without fault isolation, it relies on aggressive quality control (drivers merged into the kernel tree). For performance it moved from a single "big kernel lock" to fine-grained locking and lock-free techniques like RCU (Read-Copy-Update), where writers make a copy and atomically swap it in, letting readers proceed without locks.

Advanced topics (interest only) context

Two big questions the course leaves you with:

1. Why not "just" design a better system with capabilities everywhere?

Much research has explored pervasive capabilities — the Cambridge CAP computer (1970s, where memory addresses are capabilities enforced by hardware), KeyKOS, and modern work like Capsicum (generalising file handles) and CHERI (where "pointers are capabilities on memory", carrying bounds + permissions, with new hardware to enforce unforgeability). The hard part isn't the clean-slate design — it's retrofitting capabilities onto the everyday Unix-like file/process abstractions everyone already uses.

Which identifiers are capabilities?
A capability combines access rights + identifier. By that test: Unix file handles (fd) are <access, object> pairs — true capabilities! But process IDs, pointers, and filenames are just <object> — their permissions are implicit (in user IDs, the page table, or the file's ACL). Pervasive capabilities would mean baking access rights into all of these.

2. Do we even need an operating system at all?

Microsoft Research's Singularity (2000s) asked: instead of hardware-isolated processes (MMUs, the basis of limited direct execution), why not software-isolated processes (SIPs) — use a memory-safe language (like C#/Java-style bytecode + JIT) and verify safety statically? A driver could fail without crashing the system, sharing could be finer-grained than page granularity, and hardware could be simpler. The catch: C/C++ have no memory-safe implementation, so porting existing code is hard.

A modern echo: WebAssembly
"Compile to the browser" (first JavaScript, now WebAssembly) is the same idea reborn: run code over a software-emulated memory ("memory" is a JS array) with JIT compilation for speed. Ironically, people end up re-implementing a POSIX-like OS in the browser — "that virus again," as the lectures put it. Unix-style primitives remain endemic.
