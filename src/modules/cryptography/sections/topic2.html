Topic 02 · Games

Saying It Precisely Enough to Lose

the formal definitions, Kerckhoffs, and security as a game an adversary can win

The previous topic ended with a sentence that was nearly a definition: no further meaningful information, even given chosen encryptions and decryptions. Nearly, because "meaningful" and "information" were still carrying the weight. This topic replaces them with something that cannot be argued about — a game, an adversary, and a win condition — and the four tools below play those games and count who wins.

SKE, formally this time

Which algorithms may use randomness, and which may not
KGenRandomised. Samples and outputs sk ∈ K.  sk ← KGen
EncPotentially randomised. Takes sk ∈ K and m ∈ M, outputs c ∈ C.  c ← Enc(sk, m) if randomised, else c = Enc(sk, m)
DecDeterministic. Takes sk and c, outputs m ∈ M or the failure symbol ⊥.

Two things are new since the informal version. Dec may now fail rather than return nonsense — which is what makes it possible for a scheme to reject a ciphertext. And the arrow ← is load-bearing: it marks exactly those algorithms that may consume randomness.
Randomness as an extra input
A randomised algorithm is a deterministic one that has been handed some random bits. Writing those bits down turns one into the other: 
ρ ← R = {0,1}r      c = Enc(sk, m; ρ)
That is worth holding on to, because it is how randomised encryption gets analysed at all — and because a scheme whose Enc is deterministic has no ρ to hide behind. Every historical cipher is in that position, and the second tool below shows exactly what it costs them.
Correctness, stated over the whole space
for all sk ∈ K and m ∈ M:   Dec(sk, Enc(sk, m)) = m
And still no security: Enc(sk, m) = m with Dec(sk, c) = c satisfies it exactly.

MAC, formally

MAC = (KGen, Tag, Vf)
KGenRandomised. Outputs ik ∈ K.
TagPotentially randomised. Takes ik and m, outputs τ ∈ T.
VfDeterministic. Takes ik, m, τ, outputs 0 or 1.

Correctness: for all ik ∈ K and m ∈ M, Vf(ik, m, Tag(ik, m)) = 1. And a Vf that always says 1 satisfies it, so once again correctness is not security.
Canonical verification, and the condition on it
When Tag is deterministic — which is the case throughout here — verification can always be done the obvious way, and nothing is lost by assuming it is: 
Vf(ik, m, τ):  compute τ′ = Tag(ik, m)
             output 1 if τ = τ′, else 0
The condition matters. Ask why it needs Tag to be deterministic before reading on — and then let the fourth tool answer it by running the thing.

What the spaces actually are

Sets, and then something more useful
Formally K, M, C and T are just sets — collections without repeats, of anything at all. That is so general as to be unhelpful, and in practice they are strings over an alphabet. Writing α for the alphabet:
α0 = {ε}the empty string
α1 = {0, 1}single bits, for the binary alphabet
α2 = {00, 01, 10, 11}pairs
α* = ⋃i∈ℕ αithe Kleene star: strings of any length
Two shapes worth recognising
  • Historical. αK = αM = αC = {a..z}, with K = αKn, M = αM* and C = αC*.
  • Contemporary. αK = αM = {0,1} with αC = {0,1}ℓ.
Historical ciphers work over alphabets in the ordinary sense of the word; modern ones work over bits. Spotting which is in play tells you what a "length" means in the game rules below.

Kerckhoffs' principles

Six requirements, from an 1883 military manual
  1. The system must be substantially, if not mathematically, indecipherable.
  2. The system must not require secrecy, and can be stolen by the enemy without causing trouble.
  3. It must be easy to communicate and retain the key without written notes, and easy to change it at will.
  4. It must be compatible with telegraph communication.
  5. It must be portable, and usable by one person alone.
  6. It must be easy to use — no mental strain and no long list of rules.
The second one is the one people mean
"The system must not require secrecy" is why every game below hands the adversary the algorithms and keeps back only the key. It is a statement about what is realistic: algorithms get published, reverse-engineered, leaked or simply guessed, and a key can be changed afterwards while a design cannot. A scheme whose security rests on nobody knowing how it works has not been shown to be secure — it has only been left untested.

The rest of the list has aged in an interesting way. Four, five and six are plainly about equipment and people, and they are the ones that get dropped when the list is quoted — which is itself worth noticing, because usability failures are still how deployed cryptography goes wrong.

Security as a game

The intuition is unchanged: an adversary without sk should not learn anything meaningful about messages. What changes is that the sentence is replaced by a procedure. A challenger samples a key and a uniform bit b; the adversary is given some powers and must name b. In all of them the algorithms are public and only the key is not.

IND-EAV indistinguishability against eavesdroppers
  1. A sends two messages m0, m1.
  2. C aborts if |m0| ≠ |m1|; otherwise returns cb ← Enc(sk, mb).
  3. A outputs b′ and wins if b′ = b.
IND-CPA … against chosen plaintext attack
  1. A may call OEnc(m) as often as it likes.
  2. Then the same challenge as above.

The oracle is the whole difference, and it is fatal to any scheme with a deterministic Enc.

IND-CCA … against chosen ciphertext attack
  1. A may call OEnc(m) and ODec(c).
  2. ODec returns ⊥ for c = cb — and only for that.
  3. Then the same challenge.

Without that one exception the adversary would hand back the challenge and be told the answer, so every scheme would lose and the definition would mean nothing.

Why indistinguishability captures "learns nothing"
Suppose an adversary can work out the Hamming weight of m from c. That is not obviously the same as recovering the message — but it wins the game outright: submit m0 = 0 and m1 = 1, and read off the answer.

That is the trick of the definition. Any leak you can name is a way to tell apart some pair of messages, so a scheme where no pair can be told apart has no leaks at all — including the ones nobody thought to forbid.
What secure means
SKE is IND-{EAV, CPA, CCA} secure if no efficient adversary wins with probability noticeably different from one half.

One half because the adversary can always flip a coin, so half is what a win rate looks like when nothing has been learned. Efficient means PPT — probabilistic polynomial time. Noticeably different means by a non-negligible amount, where negligible is a function eventually smaller than every inverse polynomial.

🛠️ Play the game

Practice tool

Four thousand rounds, and the measured win rate

Pick a scheme, a game and a strategy. The challenger samples a key and a bit each round; the adversary plays; the wins are counted. Half is guessing.
Three things that tool will show you
  • A deterministic Enc cannot survive IND-CPA. Ask the oracle to encrypt m0 and compare with the challenge. Nothing about the key matters.
  • A fresh key is not the same as a randomised Enc. A shift with a new key every time still sends aa to a pair of equal letters, and that is enough.
  • Taking a power away can make a broken scheme look fine. The same shift cipher that loses IND-CPA every time wins IND-EAV exactly half the time against a strategy that needs the oracle it no longer has.

Forging a tag

EUF-CMA — existential unforgeability under chosen message attack
The challenger samples ik ← KGen and starts with Q = ∅.
  1. A may call OTag(m), which returns τ = Tag(ik, m) and adds m to Q.
  2. A outputs a pair (m′, τ′).
  3. A wins when Vf(ik, m′, τ′) = 1 and m′ ∉ Q.

MAC is EUF-CMA secure if no efficient adversary wins with probability noticeably different from zero. Zero, not a half, because here the adversary must produce something rather than choose between two equally likely answers.
Why "existential" is the right bar
It does not ask for a forgery on a message of anyone's choosing, or a useful message, or the key. Any new message with a valid tag is a win. That looks almost unfairly weak as a requirement on the adversary — which is exactly why it is the right requirement on the scheme: ruling out the easiest possible forgery rules out all the harder ones too.

Takeaways

If you remember seven things
  1. KGen is randomised, Dec and Vf are deterministic, Enc and Tag may be either. Dec may output ⊥.
  2. Randomness is just an extra input: c = Enc(sk, m; ρ) with ρ ← R.
  3. Canonical verification recomputes the tag and compares, and is only available when Tag is deterministic.
  4. Encsk is injective, so |C| ≥ |M|. There are ts functions M → C and C(t,s)·s! injective ones.
  5. Kerckhoffs: the system must not require secrecy — the key is the secret, not the design.
  6. IND-EAV / CPA / CCA differ only in which oracles the adversary gets. Secure means no efficient adversary wins noticeably more than half the time.
  7. EUF-CMA: a valid tag on any message not already queried. Secure means winning with probability noticeably different from zero.
Things that catch people out
  • Forgetting the |m0| = |m1| rule. Without it every scheme loses, because ciphertext length leaks message length — and that is a real leak the definition deliberately does not forbid.
  • Forgetting that ODec refuses cb and nothing else. A ciphertext differing in one letter is fair game, which is how a malleable scheme loses IND-CCA.
  • Reading "one half" as the win condition. The adversary must do noticeably better than one half; achieving exactly one half is what guessing does.
  • Expecting EUF-CMA's bar to be one half too. Forging is creation, not a choice between two answers, so the bar is zero.
  • Thinking a fresh random key per message makes Enc randomised in the sense that matters. What matters is whether the same message can produce different ciphertexts and whether the structure survives.
  • Treating injectivity as a design choice. It is forced by correctness.
