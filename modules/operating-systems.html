Week 01 · Introductory Topics

The Operating System

a program for running programs

This week sets the scene: what an operating system is, why it exists, how to study it, and a preview of the five core concepts you'll use throughout the course. It's mostly conceptual — be patient with it, the practical stuff comes later.

What is an Operating System?

You have a computer: a CPU, memory, a disk, a keyboard, a screen. You want to run multiple programs (Chrome, Spotify, VS Code) for one or more users, all sharing this hardware without stepping on each other's toes.

The OS is the middleman software that sits between your programs and the hardware. It shares the hardware fairly and safely, and hides the messy hardware details behind a clean, abstract interface.

┌────────────────────────────────────────────┐
│  Application software  (Chrome, your code)   │
├────────────────────────────────────────────┤
│  Operating system  (the middle of the stack)│
├────────────────────────────────────────────┤
│  Hardware  (CPU, memory, I/O devices)    │
└────────────────────────────────────────────┘
The OS as the middle of the stack — apps above, hardware below.

Two ways to describe it

  • Intensionally (by what it does): a program for running programs.
  • Extensionally (by where it sits): the software in the middle of the stack.
Key phrase
"Secure multiplexing of the computer's resources" — fancy way of saying sharing one machine among many programs/users, safely. Multiplexing = sharing ("making many out of one"). Secure = nobody can grab more than their share, or interfere with someone else's share.

What an OS actually handles

Before OSes existed, a human operator did this job — loading programs by hand, scheduling jobs, etc. The 1951 EDSAC film shows this. The OS is essentially software that takes over the human operator's role. Specifically, it must handle:

JobWhat it means
LoadingGet programs from disk into memory so they can run. A program in execution is a process.
SchedulingDecide which process/thread runs on which CPU, and when.
MemoryManage where each program lives in RAM, how much it gets, and let programs request more.
I/OLet programs talk to disk, network, keyboard, screen, etc., in a portable way.
SecurityStop programs and users from interfering with each other — but let them communicate when they want to.
ControlLet admins start/stop/debug things while the system is running.

Modern OSes also add virtualisation (giving each process an illusory "virtual computer"), communication (programs talking to each other), and abstraction (e.g. giving you "files" instead of raw disk blocks).

Virtualisation in one breath
Each process thinks it has its own CPU(s), its own private memory, its own storage, its own network. The OS maintains this illusion. A program that only virtualises hardware (and does nothing else) is called a hypervisor or virtual machine monitor.

What makes an OS "good"?

Seven qualities — and almost every pair of them trades off against each other:

QualityMeaning
EfficiencyMinimal overhead, maximum use of hardware
FairnessShares resources according to policy
ReliabilityKeeps working when programs are buggy or hardware faulty
SecurityKeeps working when users/programs are adversarial
UsabilityHelps humans get things done
AbstractionOffers high-level, general services
SimplicitySmall, maintainable, auditable codebase
Exam-style angle
Be ready to pick two of these and explain the tension between them. E.g. Security vs Simplicity: more security checks = more code = harder to audit. Efficiency vs Fairness: greedy scheduling is fast but unfair. Abstraction vs Efficiency: nicer interfaces add layers.

Concurrency vs Parallelism

This trips people up. They're not the same thing.

Concurrency

Multiple things in progress, not necessarily at the same instant.

The OS rapidly switches between them (~10ms slices). They're "concurrent" because nobody controls the order of their interactions.

Parallelism

Multiple things physically happening at the same instant.

Requires multiple cores / CPUs / devices. Real simultaneity.

Rob Pike
"Concurrency is not parallelism, but it enables parallelism."

The key insight: what makes things complicated is interaction, not physical timing. Two parallel processes that never interact are easy. Two threads on a single CPU that share memory are hard.

Why OSes are inherently concurrent

Even if no programs were running, the OS itself is concurrent because the hardware is parallel — CPU, disk, network card, keyboard, etc. are all active at once. The OS coordinates them using hardware interrupts: a device sends a signal to the CPU, causing it to jump into a special OS routine.

The Five Core Concepts

These are the foundation everything else builds on. Memorise them.

Address Space

Memory is a giant list of numbered boxes. Each number is an address. The whole set of addresses for one process is its address space. Pointers (and Java references!) are just addresses.

Loading a Program

A program sits on disk as a file. To run it, the OS copies its parts into memory and sets up an address space. A running program is called a process.

User vs System (Kernel) Mode

The CPU has two modes. In user mode, dangerous instructions are blocked. In kernel mode, the OS runs and everything is permitted. To switch, you use a software interrupt — a.k.a. a system call.

Limited Direct Execution

Your program runs directly on the real CPU at full speed, but with two limits: (a) it runs in user mode, so it can't do dangerous things; (b) periodic timer interrupts force a jump back into the OS so it can regain control.

System Calls

How a program asks the OS to do something privileged (read a file, send data, fork a process). Looks like a normal function call, but uses a special CPU instruction that switches mode and jumps to OS code identified by a number, not an address.

System calls: the journey

// Your program (user mode) read(fd, buffer, 100); // looks like a function call... // ...but actually executes a special instruction: syscall #3 // "do syscall number 3 (read)" // Then, magically: 1. CPU switches: user mode → kernel mode 2. Maybe switch address space 3. Jump to OS routine (looked up by NUMBER, not address) 4. OS does the privileged work (reads from disk, etc.) 5. CPU switches back: kernel mode → user mode 6. Returns to your code with the result
Why a number, not an address?
Because the OS code is in a separate, protected place — your program isn't allowed to know where exactly it lives. The number is a stable ID into a table the OS controls. This also means the OS can change its internal layout without breaking your programs.
📘 The trap table (OSTEP Ch.6)
How does the hardware know which OS code to jump to on a trap? At boot time (in kernel mode), the OS sets up a trap table — telling the hardware the address of each handler (syscall handler, timer-interrupt handler, keyboard-interrupt handler, etc.). The hardware remembers these until reboot.

The instruction that installs the trap table is itself privileged — if a user program could set its own trap table, it could point the "syscall handler" at its own code and take over the machine. (Worth pondering: this is exactly the kind of Very Bad Idea the user/kernel split exists to prevent.)
📘 Why does a system call look like a normal function call?
In your C/C++ code, open() or read() looks exactly like an ordinary function call — so how does the system know it's special? Because it is a real procedure call... into the C library. Hidden inside that library function is the actual trap instruction. The library follows an agreed calling convention with the kernel: it places the arguments and the system-call number in known registers/stack locations, then executes the trap. That's why you never have to write assembly to make a syscall — somebody already wrote that stub for you.

📘 Regaining control: cooperative vs non-cooperative (OSTEP)

Here's a subtle problem the slides gloss over: if a process is running on the CPU, then by definition the OS is not running. So how can the OS ever take back control to switch processes? Two approaches:

Cooperative

The OS trusts processes to give up the CPU voluntarily — they do so naturally whenever they make a system call (or hit an illegal operation that traps). Some systems add an explicit yield() call. Flaw: a process stuck in an infinite loop that makes no syscalls never gives control back — your only recourse is to reboot. (Old Mac & Xerox Alto worked this way.)

Non-cooperative

The hardware helps: a timer interrupt is programmed at boot to fire every few milliseconds. When it fires, the running process is halted and a pre-set OS handler runs — so the OS always regains control, no matter how badly a process behaves. This is what makes preemptive scheduling possible.

📘 Reboot is a legitimate tool
OSTEP makes a surprising point: rebooting isn't just an ugly hack. It moves software back to a known, well-tested state, reclaims leaked resources (like memory), and is easy to automate. Large-scale internet services deliberately reboot machines periodically for exactly these reasons.

How they all fit together

1. You type ./hello in a terminal.
2. Shell makes a system call [5] asking the OS to start a new process.
3. OS loads the program [2] from disk into a fresh address space [1].
4. OS sets the CPU to user mode [3] and jumps to your code — this is limited direct execution [4].
5. Your program runs at full hardware speed... until it needs to print.
6. printf() triggers a system call [5] → CPU flips to kernel mode [3] → OS writes to screen → flips back.
7. Eventually a timer interrupt fires → CPU jumps into OS → OS may switch to another process.
A complete trip through all five concepts in a single program execution.
📘 The two-phase LDE protocol (OSTEP) — exam-ready summary
Phase 1 — at boot (kernel mode): OS initialises the trap table; hardware remembers handler locations. OS starts the timer.
Phase 2 — running a process: OS sets up the process (process-list entry, memory, kernel stack), then uses return-from-trap to drop to user mode and jump into the code. The process runs directly on hardware until it either (a) makes a syscall → trap into OS → handle → return-from-trap back, or (b) gets hit by a timer interrupt → OS regains control → maybe context-switch to another process.

Why store return addresses on the stack?
Old machines like MARIE stored the return address inside the function's code. This breaks recursion — if a function calls itself, the second call overwrites the first's return address. The stack handles nested/recursive calls naturally: each call gets its own frame on top, and they unwind in reverse order. Early machines didn't bother because they lacked hardware stack support and recursion was uncommon.

Week 02 · Processes & Scheduling

Processes, Scheduling & Threads

how the OS juggles many programs on few CPUs

This week answers a fundamental question: a computer has only a handful of CPUs, yet runs dozens of programs "at once." How? The answer is processes (tracked instances of running programs), scheduling (deciding who runs next), and threads (multiple strands of work within one program).

Multitasking & types of task

For most of computing history, a computer had one CPU and could run one program at a time, doing one thing at a time. To switch programs you'd shut one down and start another. Painful.

The fix was multitasking: the CPU switches between tasks rapidly, letting each run for a slice of time. Only one runs at any instant, but switching fast creates the illusion of simultaneity. This is concurrency — multiple tasks making progress.

Connects to Week 1
This is exactly the concurrency-vs-parallelism distinction. One CPU multitasking = concurrency (illusion). Multiple cores = parallelism (real simultaneity).

CPU-bound vs I/O-bound tasks

Not all tasks are alike, and that affects how we should schedule them:

CPU-bound

Spends most of its time executing code on the CPU. E.g. video encoding, simulations, number crunching.

I/O-bound

Spends most of its time waiting on I/O devices (disk, network, printer). E.g. file copying, web requests.

I/O devices are extremely slow relative to the CPU. Without multitasking, a task reading from disk would force the CPU to sit idle until the read finishes. Early multitasking systems learned to detect I/O starting, then switch to another task until the I/O completed (helped by a disk controller + buffer holding the data until the CPU is ready).

Program vs Process

A subtle but crucial distinction:

ProgramProcess
A file on disk — passive. The contents of an executable (instructions + constants + global data). A program in execution — active. An instance loaded into memory and running.
The classic question
"If I start Google Chrome twice, how many programs am I running?" → One program, two processes. Same file on disk, two independent running instances.

What's in an executable file (ELF)

Unix-based systems use the ELF format. Simplified, it contains:

  • Code (text) segment — the program instructions, plus read-only constants (rodata)
  • Data segment — the global data defined in the program

Why stack + heap are dynamic
Code and data sizes are fixed and known from the file. But local variables, parameters, and objects don't exist until the program runs — and each run may use them differently (some methods may never be called). So the OS creates the stack and heap to let the process build these on the fly. The OS ensures stack and heap never overlap as they grow toward each other.

If two processes run the same program, the OS might share the code and data segments between them (they're identical and read-only). But the stack and heap are never shared — each process gets its own.

Context switching

When the CPU switches from running process A to process B, the register values currently in the CPU belong to A. To switch cleanly:

// Switching from Process A → Process B 1. SAVE A's context (program counter + registers) into A's PCB 2. LOAD B's context (program counter + registers) from B's PCB 3. Resume execution — CPU now runs B as if never interrupted
Why context switching matters
It's pure overhead — no useful work happens during a switch. If it were slow, it would dominate everything. Modern CPUs/OSes do a context switch in about 1–2 microseconds. The faster it is, the more aggressively the OS can multitask.

Scheduling algorithms

A modern system has many processes ready to run. The CPU scheduler decides which one runs next. (There's also a long-term scheduler that decides which processes get loaded from storage into RAM — but we focus on CPU scheduling.)

Preemptive vs non-preemptive

Non-preemptive

A process keeps the CPU until it terminates or waits (for I/O). The OS can't forcibly take it back.

Preemptive

The OS can interrupt a running process to let another run. Modern schedulers are usually preemptive.

The oldest approach was cooperative multitasking: processes voluntarily yield to each other. Problem: a process that never yields hogs the CPU forever. (Old Windows and Mac OSes worked this way.)

Key metric: Average Waiting Time (AWT)
Waiting time = time a process spends in the ready queue (not running). AWT = average across all processes. We usually want to minimise AWT. Burst time = total CPU time a process needs (excluding I/O).
📘 From the textbook (OSTEP Ch.7): two different metrics
The slides focus on waiting time, but OSTEP frames scheduling around two metrics that pull in opposite directions:
  • Turnaround time = Tcompletion − Tarrival. How long from arriving to finishing. A performance metric.
  • Response time = Tfirst run − Tarrival. How long until you first get the CPU. An interactivity metric — this is what matters when you're typing at a terminal and want to see something happen.

This distinction is the key to understanding why different algorithms exist. SJF/STCF win on turnaround; Round-Robin wins on response. You can't have both — it's a fundamental trade-off (see below).

1 · First Come First Served (FCFS)

Simplest possible: a FIFO queue. Whoever's been waiting longest runs next. Non-preemptive. Problem: order of arrival massively affects AWT.

📘 The convoy effect (OSTEP)
OSTEP gives FCFS's flaw a memorable name: the convoy effect. When several short jobs queue up behind one long job, they all wait ages — like being stuck behind someone with three full carts at the supermarket while you hold a single item. The fix (a "10-items-or-less" lane) is exactly the intuition behind Shortest Job First.

2 · Shortest Job First (SJF)

Instead of arrival order, pick the process with the shortest burst time next. This is provably optimal for minimising AWT.

The catch
You need to know the burst time in advance — but you usually don't! Solution: estimate it from the process's previous burst times (a running average). FCFS didn't have this problem because it ignores burst times entirely.

SJF can be preemptive or non-preemptive. Preemptive version: when a new process arrives, compare its burst time to the remaining time of the running process — if shorter, preempt.

Starvation
If short jobs keep arriving, a long job might never run. This is starvation. Fix: add an ageing factor — the longer a process waits, the higher its priority climbs, guaranteeing it eventually runs. (Priority = combination of burst time + age.) This idea generalises into priority scheduling.
📘 STCF — preemptive SJF (OSTEP)
Plain SJF is non-preemptive, so a long job already running can't be interrupted when a short job arrives (the convoy effect returns). The preemptive version is Shortest Time-to-Completion First (STCF), also called Preemptive SJF: whenever a new job arrives, compare its burst to the remaining time of the running job and switch if shorter. Like SJF, STCF is provably optimal for turnaround time — but, as we'll see, terrible for response time.

3 · Priority Scheduling

Generalise SJF: burst time becomes just one factor in a process's priority. Build a function combining many factors:

  • Internal factors: burst time, I/O usage, memory requirements
  • External factors: who owns the machine, who submitted the job

Also comes in preemptive and non-preemptive flavours. Same starvation risk → same ageing fix.

4 · Round-Robin (RR)

Like FCFS but preemptive, using a circular FIFO queue. Each process gets a fixed time quantum (max time per turn). If it doesn't finish, it goes to the back of the queue.

  • Finishes / waits before quantum expires → preempted early, next process runs
  • Reaches the quantum → preempted, sent to back of queue (unless it's the only one)

📘 The fundamental trade-off (OSTEP) — great exam discussion point
OSTEP crystallises the whole chapter into one insight:
  • SJF / STCF optimise turnaround time, but are bad for response time (a job arriving third waits for two full jobs before running once).
  • Round-Robin optimises response time, but is bad for turnaround (it stretches every job out by only running it a slice at a time — often worse than FCFS!).

Any policy that is fair (evenly sharing the CPU on a short timescale) will do poorly on turnaround. If you're willing to be unfair, you can run short jobs to completion (good turnaround) but hurt response; if you value fairness, you improve response but hurt turnaround. You can't have both.

📘 Two more OSTEP gems
Amortization: the time quantum is a balancing act. If a context switch costs 1ms and the quantum is 10ms, you waste ~10% on switching. Make the quantum 100ms and you waste <1% — but responsiveness drops. Bigger quantum amortises the switch cost.

Overlap / incorporating I/O: when a job blocks on I/O, the scheduler runs another job on the CPU meanwhile. A good scheduler treats each CPU burst between I/O operations as its own mini-job, so interactive (I/O-heavy) jobs stay responsive while CPU-heavy jobs soak up the spare cycles. This overlap is what keeps the whole system busy.

5 · Multilevel Queue & Multilevel Feedback Queue

Multilevel Queue

Multiple queues for different classes of process (time-critical, UI, background), arranged by priority. Each queue can use a different algorithm. Processes do NOT move between queues.

Multilevel Feedback Queue

More flexible: processes CAN move between queues based on behaviour. E.g. a process hogging CPU gets demoted to a lower-priority queue.

Real-world
Linux and Windows use preemptive priority scheduling. macOS appears to use a multilevel feedback queue.

Threads

Processes let you run multiple programs at once. But a single program often needs to do several things at once too. A word processor wants to let you keep typing while it spell-checks, repaginates, and auto-saves in the background. Enter the thread.

A thread is a strand of execution within a process. One process can have many threads running "at the same time." Threads can even create more threads. (In Java: the Thread class and Runnable interface.)

Classic uses: a web server spawning a thread per incoming connection; a UI keeping one thread responsive while another does heavy work.

Week 03 · Memory Management

Virtual Memory & Address Translation

how every process gets the illusion of its own private memory

This is one of the deepest topics in the course. It solves a single problem in progressively cleverer ways. The whole week is a story: each solution fixes a flaw in the one before. Understanding why each step happens is the key to the entire topic.

The evolution at a glance
Load-time relocation → Base & limit registers → Segmentation → Paging → Multi-level page tables. Each step trades complexity for better fault isolation, security, and less fragmentation.

The address-binding problem

Recall the OS gives each process the illusion of its own computer — including its own memory. We need this for:

  • Reliability: stop a buggy process from corrupting another's memory.
  • Security: stop a malicious process from reading/trashing another's memory — or the OS's.

But here's the catch. Programs embed memory addresses directly in their machine code. An instruction like callq 0x001330 references a specific, concrete address baked into the binary:

83 ff 02 cmp $0x2,%edi 53 push %rbx 74 07 je 0x00139d ; jump to a fixed address e8 93 ff ff ff callq 0x001330 ; call code at a fixed address 48 8b 3e mov (%rsi),%rdi be 0d 3f 00 00 mov $0x003f0d,%esi ; load from a fixed address
The problem in a nutshell
How can programs be written as if memory is private to themselves (concrete instructions referencing specific addresses)... but still execute in a shared slice of physical memory... efficiently, reliably, and securely? If two processes both want to start at address 0, they can't both physically be there!

Why the obvious "non-solutions" fail

Solution 4 · Paged virtual addressing

The key insight: "What if we had lots and lots of segments, but all the same small size?"

Divide physical memory into equal-sized frames (e.g. 4kB each), aligned from zero. Divide each process's virtual address space into same-sized pages. A page is just a frame-sized chunk of virtual memory; once mapped to a frame, it's "a mapped frame."

Why equal sizes are magic
Any aligned 4kB physical chunk is as good as any other → no external fragmentation. Contiguous virtual areas need not be contiguous physically. Internal fragmentation is limited: worst case a program wastes only 4,095 bytes (the tail of its last page).

  • Temporal locality: if you access something now, you'll likely access it again soon (e.g. a loop variable). Loop over the array a second time and you'd get 10/10 hits.
📘 Who handles a TLB miss? (hardware vs software)
Hardware-managed (CISC, e.g. x86): the hardware itself knows the page-table format, "walks" it on a miss, fills the TLB, and retries — no OS involvement.

Software-managed (RISC, e.g. MIPS/SPARC): on a miss the hardware just raises an exception; an OS trap handler does the lookup, updates the TLB with a privileged instruction, and returns so the instruction retries.

Subtle detail: unlike a syscall's return-from-trap (which resumes at the next instruction), a TLB-miss return-from-trap must retry the same instruction — this time it hits.
📘 Why not just build one giant TLB/cache?
Because physics. A fast cache must be small — speed-of-light and other physical constraints mean any large memory is inherently slow. So we're stuck with small, fast caches, and the whole art is using them well (exploiting locality to make the common case fast).

Solution 5 · Multi-level page tables

The insight: most processes don't use all 2ⁿ pages, so most page-table entries are invalid (empty). Why store a giant array that's mostly empty? Use a data structure that handles sparseness better — a tree (of fixed depth, since hardware isn't recursive).

A simpler first attempt: PTLR
Before the tree: a Page Table Length Register caps the table length — start short, grow on demand. But it requires the virtual address space to be contiguous (breaks our "stack grows down, heap grows up" layout with two growable areas), and growing still needs contiguous physical memory. The tree handles both.

How the two-level scheme works

Split the 20-bit page number into two 10-bit halves. The top 10 bits index a page directory (root); the bottom 10 bits index a leaf page table. Each table has 2¹⁰ = 1024 entries (a "1024-ary tree" of depth 2).

The magic: if an entry in the page directory is marked invalid (X), that means an entire chunk of the page table is unused — and doesn't need to be stored at all. That's the space saving.

The trade-off, and why TLBs become critical

The idea generalises — modern 64-bit architectures (secretly usually only 48-bit) often use 4 levels (on x86-64: PML4, PDP, PD, PT). But each level adds a memory access!

The performance crunch
A 4-level scheme means 4 extra memory accesses for every single translation — on top of the actual access. This would be catastrophic without the TLB. Like any cache, a TLB lookup either hits (use the cached translation — fast) or misses (do the full multi-level walk). The more levels, the more critical TLB hit rate becomes.

Week 04 · Memory Management II

Demand Paging & Virtual Memory

turning page faults from errors into superpowers

Week 3 built page tables that map virtual pages to physical frames. This week's big idea: a page fault isn't necessarily an error — it's an opportunity. When a process touches an unmapped page, the hardware traps into the OS. Instead of just killing the process, the OS can do something clever and then resume. This single hook enables a whole family of "useful illusions."

The illusions, in order of ambition
Lazy allocation → lazy zeroing → copy-on-write → demand-paged virtual memory (the illusion of more RAM than you physically have) → and the hard decisions that follow: page replacement & frame allocation.

Page faults as a point of interposition

Recall: most of a process's virtual address space is unmapped (unused). The MMU translates addresses; accessing an unmapped address causes a page fault — a hardware interrupt that hands control to the OS.

The simple response is to kill the process — this is the dreaded "Segmentation fault" (a misnomer these days). But the OS doesn't have to. It can handle the fault and resume the process, which is where all the magic comes from.

Lazy allocation & lazy zeroing

The first illusion: reserve virtual address space without actually allocating physical memory. Run the process as if memory is there. When it touches that "memory," a fault fires, and only then does the OS allocate a real frame. This is lazy allocation — work deferred until actually needed.

Lazy zeroing — a beautiful trick

Programs often need large zero-initialised regions. Naively, you'd allocate and zero out tons of frames upfront. Instead:

  1. Map the whole region read-only to a single shared zero frame — many pages → one frame.
  2. Reads work fine (they all see zeroes).
  3. On the first write, a page fault fires; the handler maps a fresh frame just for that page.
Why this is clever
Allocation appears instant, it allows sparse use of memory (O(n) zeroes fit in O(1) memory until written), and the zeroes are readable at all times. You only pay for pages you actually modify.

Virtual memory: swapping to disk

So far we've lazily given out memory. Now the reverse: taking it back. Memory is scarce, so can we create the illusion of having more than we physically do — to run more or bigger processes?

Yes — by swapping data to and from disk, using page faults to trigger re-loading. Not all memory is used at once, so not-recently-used pages can be evicted to disk, freeing their frames. When the process touches an evicted page later, a fault brings it back.

Precise terminology
"Virtual memory" properly refers to this specific illusion: that the machine has more memory available than its physical DRAM. (That's why the slides carefully said "virtual address space" / "virtual addressing" earlier — those are different things from "virtual memory.") Data is moved to a swap device — a disk further down the storage hierarchy.

Notice the resemblance to a cache: not-recently-used pages get replaced, just like cache lines. The difference is that this cache is managed by software (the OS), not hardware.

The storage hierarchy

For the best performance-per-£, systems mix technologies: small/fast/expensive at the top, big/slow/cheap at the bottom.

Interlude: disks are block devices
Disks read/write in blocks (typically 512 bytes – 4kB), not individual bytes/words. They're persistent but only block-addressable. The disk controller exposes a linear sequence of blocks; the OS builds the filesystem (a tree of files & directories) on top. Block devices can alternatively hold swap areas or databases instead of a filesystem.

Tracking swapped-out pages

Problem: hardware page tables only know how to map a page to a frame or "invalid." But now we need richer states like "swapped out to disk block 42," "load deferred," or "treat as copy-on-write." Two approaches:

Cheap & nasty

Stash extra info in invalid PTEs. If the valid bit is clear, the hardware ignores the other bits — so the OS is free to use them however it likes (e.g. encode a disk block number). This is your lab exercise: "stash a cookie" in the PTE for lazy loading.

Realistic

Keep a separate OS data structure. Linux uses a red-black tree of virtual memory areas (VMAs). This even allows lazy creation of the page table entries themselves.

Naming wart
InfOS uses "VMA" to mean the whole virtual address space (better called "VAS"). Linux uses "VMA" for individual regions. Don't get confused between the two.

If you stash data in the PTE, the encoding is entirely up to the OS — but it must capture everything needed to handle a future fault: which disk block, what permissions, whether CoW applies, etc. It needn't even be a block number; something more abstract can work.

Demand paging + prefetching

Modern systems are demand-paged: they transfer page-sized chunks on demand, i.e. when a fault arrives (the lazy approach). But laziness isn't free — fault handling makes processes wait on slow I/O, and frequent swapping kills performance.

Prefetching
Being more eager can save time — if we can accurately predict which pages will be needed. Proactively transferring data before it's needed is prefetching. Modern systems combine demand paging with judicious prefetching, guided by heuristics or predictive models.

Page replacement

When physical memory is full and a process needs more, the OS must evict a page to free a frame. Which page? This is page replacement — analogous to cache replacement, but done in software. Common policies:

📘 Memory IS a cache (OSTEP Ch.22)
OSTEP's key reframing: main memory is just a cache for the pages living on disk. So the goal of page replacement is exactly a cache goal — minimise misses (maximise hits). This lets us measure it with AMAT (Average Memory Access Time):
AMAT = TM + (Pmiss × TD) ↑ memory access ↑ disk access cost (always paid) (only on a miss)
With realistic numbers (TM = 100ns, TD = 10ms), even a tiny miss rate dominates: at 90% hits, AMAT ≈ 1ms (~10,000× slower than memory!). At 99.9% hits, AMAT drops to ~10µs. This is the concrete version of the "T ≥ 10,000" idea — the whole game is pushing the hit rate towards 100%.

Optimal (MIN)Evict the page that will be used furthest in the future. Provably the fewest misses — but needs to see the future, so it's impossible to build. Used only as a comparison baseline.
FIFOTreat the resident-page list as a queue; evict from the head (oldest / least-recently-added).

📘 Why the Optimal policy matters even though it's impossible
You can't build it (you don't know the future), but it's invaluable as a yardstick. Saying "my policy gets 80% hits" is meaningless alone; saying "optimal gets 82%, mine gets 80%" tells you you're nearly perfect and can stop optimising. Its logic: if you must evict something, evict the page you'll need furthest away — all the others will be touched before it.
📘 The Three C's — types of miss (OSTEP)
Useful vocabulary for why a miss happened:
  • Compulsory (cold-start) — the very first reference to a page; the cache was empty, so it's unavoidable.
  • Capacity — the cache ran out of room and had to evict something it later needed.
  • Conflict — a hardware-cache artifact (placement restrictions). Doesn't occur for OS page caches, since any page can go in any frame (fully associative).
Why we can't implement true LRU
LRU needs a timestamp on every access — but the hardware doesn't give us that! All we get is a Used bit (a.k.a. Referenced bit) that the hardware sets whenever a page is accessed, plus a Dirty bit set on writes. The OS periodically clears all Used bits, so a set bit means "used recently" — but not how recently relative to others.
📘 Belady's Anomaly — a favourite exam "gotcha"
You'd expect more frames → fewer faults. Usually true — but with FIFO it can get worse! The classic stream 1 2 3 4 1 2 5 1 2 3 4 5 gives 9 faults with 3 frames but 10 with 4 frames. (Try it in the tool below!)

LRU never does this because it has the stack property: a cache of size N+1 always contains everything a size-N cache would. FIFO and Random lack this property, so they can behave anomalously.

The Clock algorithm (Second-Chance FIFO)

Our best practical approximation of LRU. Walk the resident pages oldest→newest like FIFO:

  • See a page with Used = 0 → evict it.
  • See a page with Used = 1 → give it a "second chance": clear its Used bit and move on (it survives this round).

To avoid expensive list manipulation, use a circular list with a "hand" pointer that resumes from where it stopped. That's the Clock algorithm.

Frame allocation & thrashing

The other big decision: how many frames does each process get? The key concept is the working set.

Working Set (WSS)
Each process has a set of pages it's "using now" — the pages it needs to make uninterrupted progress over a small interval (say 100ms). That's its working set; its size is the working set size (WSS). You can estimate WSS by counting Used bits set since you last cleared them ~100ms ago.

The thrashing curve

Here's why this matters. The cost of a page fault is enormous — the "traverse time" T ≥ 10,000 (a disk swap-in is ~10,000× slower than a memory access). So even a tiny rise in miss probability crushes efficiency:

As soon as a process can't keep its working set in memory, efficiency falls off a cliff. (After Denning, 1968.)

Thrashing
"Equal shares" is a bad policy! If all processes get less than their WSS, the system spends ~all its time waiting on I/O, the number of runnable processes plummets, and throughput drops to nearly zero. This is thrashing.
The fix
Better to give some processes at least their WSS of frames (and make others wait) than to starve everyone equally. Other strategies exist too — e.g. Linux's OOM killer (the big hammer: kill a process to reclaim memory). Also: never let physical memory fill completely — the OS itself needs some free memory just to perform page replacement!

Week 05 · User-Space Topics

malloc, the Stack, Files & I/O

the machinery that lives on top of the kernel

This week steps up from the kernel into user space — the things that run on top of the OS but lean heavily on it. Four threads, all connecting back to ideas you've already met (fragmentation, the stack, system calls, interrupts).

malloc & the heap

The OS only deals in big chunks of memory — at least a page. But programs want small pieces: malloc(42 * sizeof(int)) wants 168 bytes, not a 4kB page. The job of a memory allocator (malloc/free in C, new/delete in C++) is to parcel out small pieces from a bigger chunk the OS gave it — the heap.

What malloc actually means
int *pn = malloc(42 * sizeof(int)); means: "find a free range of ≥ 168 bytes, chop out 168 bytes, mark it as used, and return a pointer to the start." free(pn) does the opposite: "mark this chunk as free." Crucially, the OS has nothing to do with these calls — both malloc and new are library code running inside the user process.

Why study malloc?

  • Allocators do use the OS to get their raw memory (in page-sized chunks and larger).
  • An OS kernel has its own internal malloc-like allocator for its own use.
  • They show another layer of fragmentation — this time within the heap, on top of the OS's page-level fragmentation.
  • Higher-level languages (C++, Java, Python) almost always have a malloc-like allocator underneath.
Two layers of allocation
From the OS's point of view, the whole heap arena is "allocated" to the process. From malloc's point of view, parts of that arena are still "free." So you have allocation-within-allocation, and fragmentation-within-fragmentation. malloc means manual — here we only consider manual memory management (you call free/delete yourself), not garbage collection.

Getting more memory: brk & mmap

When the heap is full and fragmented, a big malloc can't be satisfied. The allocator must ask the OS for more memory via a system call. Two ways on Unix-like systems:

brk() — the classic

Moves the program break (the end of the heap; a vestige of segmentation!) to a later address, gaining memory in between. The break's location is part of the per-process state the OS maintains. brk(curbrk + 100*PAGE_SIZE) asks for 100 more pages.

mmap() — the modern, flexible way

Doesn't care about the program break. Returns a fresh, possibly non-contiguous arena anywhere. malloc can add it to the free list. No contended single resource (unlike the one program break), so it's better for multi-threaded allocators.

Connecting back to demand paging
Asking for memory via brk/mmap need not allocate physical memory immediately — it just reserves virtual address space. Physical frames arrive lazily on first access, via page faults (Week 4!). Note mmap with MAP_ANONYMOUS gives blank memory; mapping a named file instead is how you get memory-mapped files.
malloc is a highly-optimised concurrent codebase
Many threads may call malloc() at once, so the free list must be concurrent (thread-safe). Doug Lea — who designed much of java.util.concurrent — also wrote dlmalloc, one of the most widely-used implementations. (InfOS's kernel malloc is dlmalloc, for the kernel's own chunk allocation; frames use a different algorithm.) Real allocators are measured per workload (a program+input pair) on speed of alloc/free and internal/external fragmentation.

The stack in depth

Back to the stack — now in detail, because (a) you need it for the mini-project, and (b) many security exploits target it. When a function is called, a stack frame (or "activation record") is pushed. In the x86-64 scheme shown in the slides, the first two things in each frame are:

  1. The caller's return address (saved program counter — where to jump back to)
  2. The caller's frame pointer (saved rbp)

...followed by saved registers and local variables (e.g. that Hello, world! buffer, or saved rbx/r12).

Two things the stack encodes
Using the frame pointer, you can "walk up" the stack, following the chain of frames. This tells you:
  • History — what uncompleted calls got us here? (Useful for a backtrace when debugging — that's the Medium mini-project.)
  • Continuation — where will we return to next? (One answer per active call.)

Influence the stack and you influence the program's future. That sentence is the entire premise of the next section.

A lovely detail
The instruction movabs $0x77202c6f6c6c6548, %rax in the hello-world disassembly looks like a magic number — but those 8 bytes, read little-endian, literally spell "Hello, w". The string is being loaded as an immediate integer constant.

Buffer overflows & stack smashing

Consider this innocent-looking program:

char buf[10]; scanf("%s", buf); // read a string into buf... return 0;

Danger: what if you type more than 10 characters? scanf doesn't check the buffer size — it just keeps writing. The stack grows toward lower addresses but arrays fill toward higher addresses, so an over-long input writes past the buffer and over the saved registers, the saved frame pointer, and eventually the return address.

The attack
If an attacker knows the address of a powerful library function elsewhere in the process, they can craft input where the overflowing bytes are that address — overwriting the return address so that when main returns, it "returns" into the attacker's chosen code instead. This is a stack-smashing attack, a kind of buffer overflow.

Why does this happen — and why doesn't the compiler stop it?

When array indexing / pointer arithmetic is not bounds-checked, the code is trusting that input won't exceed the buffer. C and C++ don't insert bounds checks by default (for speed, and because the language permits raw pointer arithmetic that makes checks hard). Safer interfaces exist and should be used: strncpy() over strcpy(), vector::at() over operator[].

📘 Why can Java do this but C can't?
Java arrays carry their length and the runtime bounds-checks every access (throwing ArrayIndexOutOfBoundsException). C arrays are just raw memory with no length attached, and pointer arithmetic can produce any address — so the compiler often can't know the bound to check. That safety is exactly what C trades away for speed and low-level control.

Files, handles & inter-process communication

Processes are inherently communicative — with the OS and with each other. They make requests in terms of identifiable objects ("write these bytes to this file", "listen on this network interface"), identified using handles.

Why opaque handles, not addresses?
Processes don't share memory with the OS → they can't use memory addresses to name kernel objects. They also can't use device-level identifiers (the OS abstracts those away), and some "objects" are pure OS constructs (threads, processes) with no hardware identifier at all. So the OS hands out an opaque handle — in InfOS, an arbitrary 64-bit integer; in Unix, a small int called a file descriptor (fd) — that indexes a table the OS controls.

File descriptors

A Unix process starts with three open file descriptors by default:

0

1

An fd can refer to many kinds of object: terminals, files on disk, network connections, devices (sound card, camera). Most support read() and write(); some support extras like seek() (files, but not live audio) or the catch-all ioctl().

You could say fds are "dynamically typed" — the same interface, many underlying object types. (Threads/processes are the exception — they use pid_t/tid_t, not fds.)

A security problem with handles
If a handle is just an integer indexing a table, what stops a process from guessing another handle's number and using it? The OS must check that the handle belongs to the process using it (the InfOS ObjectDescriptor records an owner thread for exactly this reason). Forgetting that check is a real vulnerability class.

Inter-process communication (IPC)

fds aren't just for devices — they're also channels to other processes:

  • Shared files — two processes read/write the same file.
  • Sockets on a loopback "network" card — local network-style comms.
  • Pipes — one-way in-memory channels.
  • Pseudo-terminals — two-way in-memory channels.
Avoiding slow user↔kernel crossings: shared memory
Every read/write is a system call (slow-ish mode switch). To avoid them, processes can share memory directly using the MMU: mmap() the same named file with MAP_SHARED (not MAP_PRIVATE). Now both processes see the same physical frames and can communicate by simply reading/writing memory — no syscall per exchange. This ties paging (Week 3–4) directly to IPC.

How I/O works (intro)

I/O devices are many and varied, so it's not workable for each program to know each device. Device drivers are the OS's code for talking to a specific device, exposing a higher-level, device-agnostic interface to the rest of the OS — which is then abstracted further to user programs via system calls. Devices must also be multiplexed securely and concurrently. There are three evolutionary approaches to actually moving the data:

1

Programmed I/O + polling

The CPU writes commands to the device's I/O ports, then repeatedly asks "are you done yet?" in a loop (polling the status register). Problem: the disk is millions of CPU cycles slow — the CPU is kept 100% busy doing nothing useful. Very inefficient.

2

Interrupt-driven I/O

The CPU issues the command then carries on with other work. When the device finishes, it raises a hardware interrupt: the CPU saves its registers, looks up the handler in the interrupt table, and jumps to it. The handler reads the now-ready data. Far less wasted time. (An interrupt controller, e.g. an APIC on x86, multiplexes the interrupt line between devices.)

3

Direct Memory Access (DMA)

A DMA controller transfers data between the device and memory by itself, without the CPU running in/out instructions for every word. The CPU is freed entirely during the transfer; it still gets one interrupt on completion, but by then the data is already in memory. Maximum efficiency.

Full-circle: timer interrupts & preemptive scheduling
Interrupts aren't just for talking to the outside world. The timer is itself a device on an I/O bus, programmed to interrupt the CPU at a set frequency. When the timer interrupt fires, its handler calls the scheduler to pick another process — which is exactly how preemptive Round-Robin (Week 2) works, and how the OS guarantees it regains control (Week 1's "limited direct execution"). Everything connects.

Week 07 · Security

Access Control, Authentication & Cryptography

a mindset of constant suspicion

This is the big security week. The core mindset: security means adversarial — someone is actively trying to break your system. This is different from mere fault-tolerance (protecting against accidental error/incompetence). C, Unix, and the Internet weren't really designed for adversaries — which is why security is hard.

Access control basics

Most modern OSes are multi-user: they give each process a user identity (alice, bob, ...) — abstractly, a label denoting privilege. Access to shareable objects (like files) is controlled by the system according to a policy: "Alice can read Alice's mail, but Bob can't."

System defines mechanism; users define policy
The OS provides expressive mechanisms that can represent a range of policies. The specific policy is decided by the users. E.g. Alice might make a file plan that anyone can read but only she can write, and a file project that only she and Bob can read/write. Keeping the mechanism simple, flexible, expressive and efficient is the deep challenge.

Unix example: pathnames, inodes & file descriptors

In Unix you open() a file by pathname, then read()/write() on the returned handle:

int fd = open("/home/alice/mail", O_RDONLY); $ ls -l ~/mail -rw------- 1 alice alice 450871 Mar 4 2023 /home/alice/mail ↑ permission bits ↑ owner ↑ group rw- : owner (alice) can read+write, not execute --- : group members can do nothing --- : other users can do nothing
Checks happen only at open()!
Permission bits live in the file's inode (~one per file). The check is done once, at open() — after that, having the file handle is enough; read()/write() don't re-check. This design has consequences:
  • Cost of checking is amortised (checked once, not per access).
  • Delegation is possible — you can even transmit the fd to another process.
  • Revocation is hard — changing permissions doesn't revoke already-open fds.

The access control matrix: ACLs vs capabilities

We can model all policy as one big table — the access control matrix — of who (subject) has what access to which object:

Storing the whole matrix is impractical. There are two ways to slice it into a real data structure:

slice by column — store with each object

Access Control Lists (ACLs)

Each object stores a list of (who, what access) pairs. Unix's user/group/other bits are a limited ACL. The ACL lives on the object and protects it there.

Good: easy to revoke (remove from list), easy to audit/understand, easy to retrofit. Bad: can get large & slow with many users/files; authority is ambient ("based on who you are").

slice by row — store with each subject

Capabilities

Each subject holds a list of (which object, what access) pairs. Each pair is a capability — exactly like a file descriptor! An unforgeable token: possessing a valid reference is enough.

Good: easy to delegate, easily fine-grained, distributes scalably, authority is designated. Bad: hard to revoke, hard to audit (after delegation), must "design in".

The keyring analogy
A capability is like a key on a keyring: each key embodies distinct, fine-grained authority; to open a door you must pick a specific key (designated, not ambient); and more than one key might open the same door in different ways. A "secret link" emailed to you (that grants access without logging in) is also a capability — made unforgeable with cryptography.

Security properties (the CIA triad + more)

Confidentiality

Information is not disclosed to unintended parties.

Integrity

Information is not modified by unintended parties — tamper-proof, or at least tamper-evident.

Availability

Attackers can't deprive others of the service (e.g. denial-of-service, like a fork() bomb).

Always relative to an attack model
These properties only hold up to certain assumptions (the "attack model") and the attacker's budget/resources — e.g. can they break into your house? plant agents in your org? They also almost always trade off against performance and convenience ("we've just texted you a convenient code..."). ACLs and capabilities give us confidentiality & integrity; for availability we need resource limits (max processes/memory per user, rate-limit process creation).

The Swiss cheese model

Security is never absolute — methods are complex and can be performed incorrectly. So effective security relies on layers of defence: each layer has holes, but an attack only succeeds if it passes through holes in every layer.

Least privilege

When you run a program, how much privilege does it get? Usually all of yours — it can access any of your files, run anything you can run. That's fine if the program is correct and trustworthy. But what about a big, complex program like a web server running as root (the superuser, who can do everything)?

Privilege escalation
A web server doesn't need to do everything — but if it runs as root and gets exploited, the attacker gets everything. Complex software can be tricked into doing unintended things; using that to gain more privilege than intended is privilege escalation. The principle of least privilege: give each program only the authority it actually needs.

One fix: run the web server as a dedicated, restricted user: sudo -u httpd ./httpd. Then even if exploited, the worst it can do is "things the httpd user can do," not "anything." But splitting privilege finely is hard work — you must create all those users and set up their permissions, and mistakes cause programs to fail mid-execution.

Unix's "80% solution": setuid / setgid

Some programs genuinely need to combine multiple authorities (e.g. submit needs your permission on your coursework + the system's permission on the submission directory). Unix handles this with special permission bits:

$ ls -l /shared/5CCS2OSC/submit -rwsrws--x 1 k2144518 k2144518 ... submit ↑ ↑ first s : setuid — runs with the OWNER's uid, not the invoker's second s: setgid — runs with the owner's gid final x : anyone can run it

A setuid program owned by root is setuid root — it runs as the all-powerful root user no matter who invokes it. seteuid() lets a program drop the owner's privileges and switch to the invoker's. Powerful, but "flexible" means "complex" means "liable to be got wrong."

The confused deputy & the PwnKit exploit

A confused deputy is a specific kind of privilege escalation: buggy code acting under two or more authorities is tricked by a crafty input/environment into doing something under the wrong one. The classic real-world example is PwnKit (CVE-2021-4034) in pkexec — a setuid-root program installed by default on every major Linux distro, vulnerable from its creation in 2009 until 2022.

How PwnKit worked (chain of tricks)
  1. Invoke unusually: call pkexec with an empty argument list (argc = 0). A loop counter then reads/writes out of bounds past the arguments into adjacent environment memory.
  2. Re-introduce an unsafe env var: that out-of-bounds write smuggles back a dangerous variable (like GCONV_PATH) that the system normally strips from setuid programs.
  3. Exploit logging: to print an error, pkexec calls a logging function that needs character-set conversion...
  4. Character conversion loads code: conversion routines are dynamically loaded shared libraries, located via GCONV_PATH.
  5. Point to a nefarious library: the attacker's GCONV_PATH points to their library, whose code then runs as root. Game over.
Post-mortem — why this is a confused deputy
The key vulnerability is a buffer overflow (out-of-bounds write). But the deeper lesson: pkexec ran its logging code (an incidental task) with root authority instead of the invoking user's. The logging was tricked into loading nefarious code — harmless if run as the user, catastrophic as root. The deputy was "confused" about which authority to act under.

What could prevent attacks like this?

  • Memory safety / bounds checking — in Java the buffer overflow simply couldn't happen.
  • Eliminate ambient authority — the root-ness was "ambient" in the user ID. If every operation had to explicitly designate its authority via a handle/capability, the logging code wouldn't have had root to abuse.
  • Ideally, pkexec would be granted a single narrow capability ("create a new process as a different user") and nothing else — so "accidental use of root" becomes impossible. (This is essentially a more object-oriented, capability-based syscall interface.)

Authentication

A new property: authenticity — communicated information (and communicating parties) are what/who they purport to be. Authentication is establishing trust in identity — and trust goes both ways: does the system trust the user's claimed identity, and does the user trust the system's? (Thinking adversarially: people lie about who they are, and software lies about what it is.)

The human bottleneck
Correctly enforcing policy is the easy part. The hard parts are human: getting the policy right, and users who re-use passwords, write them down, or pick guessable personal ones. Also worth knowing: most password authentication happens in random web sites and apps, not the OS — and is usually implemented badly. "Think twice before implementing an authentication service. Then if you still want to, think again."

System-to-user authentication

It goes the other way too: before you type your password, you should trust the machine is what it claims (not a fake fullscreen login). OS approach: an untrappable key combination (e.g. Ctrl+Alt+Delete) the OS guarantees apps can't intercept — so the login screen that appears must be genuine. Websites use cryptographic certificate verification instead (a chain of trusted authorities). Either way, phishing still defeats the human.

Cryptography

Cryptography = techniques for secure communication in the presence of adversaries, using codes. (If your channel is physically secure — only intended parties can participate — you don't need it.) Interesting OS insight: operating systems contain lots of communication (and isolate processes), so they use relatively little crypto internally — but the layer above (browsers, networked apps) uses it heavily, because data paths out of the machine aren't controlled.

Ciphers, formalised

A cipher is a pair of functions: E (encrypt), D (decrypt) plaintext P → ciphertext C C = E(P) P = D(C) Problem: ciphers are well-known maths. No security if the method is known. Fix: parameterise by a secret KEY K: C = E(P, K) P = D(C, K) // works only if K stays secret

How the CIA properties fall out of this:

  • Confidentiality: send C = E(P, K); recipient recovers P = D(C, K).
  • Integrity: send C = E(P ++ hash(P), K). Recipient decrypts to (Q ++ H) and checks H == hash(Q). Without K, an attacker can't tamper and fix the hash → tampering is detected.
  • Authenticity: a challenge–response protocol — send a random nonce X; a correct response of E(X, K) proves the responder knows K. (Passwords are the degenerate case: empty challenge, E is the identity function — which is why you're sending a secret in the clear and the channel had better be secure!)

Symmetric vs asymmetric

Symmetric

The same key encrypts and decrypts. Goal: computationally infeasible to crack without the key, but affordable with it. Many are block ciphers (fixed-size chunks + fixed-size key), e.g. AES. Exploit exponentials: key space grows exponentially with length, so pick a length where brute force takes longer than the age of the universe. Problem: key distribution — how do both sides get the shared secret?

Asymmetric (public-key)

Keys come in two parts: public and private. To send Bob a secret: Alice encrypts with Bob's public key; only Bob's private key can decrypt. Solves key distribution! RSA (1977, Turing-award-winning) relies on factoring large near-primes being hard. Downside: exponentials are slow — so in practice you use RSA just to exchange a fresh symmetric key, then switch to that (ssh does exactly this).

Cryptographic hash functions
Like any hash, h(m) maps arbitrary data to fixed-width integers. It's cryptographic if, given an output h(m), it's computationally infeasible to find m — or any m' with h(m') == h(m) (collision resistance). Uses: storing passwords (store the hash!) and authenticating software/data (publish a file's hash). Examples: MD5 & SHA-1 (both broken), SHA-2 (still secure).

Two simple ciphers (for the tool below)

  • Caesar / ROT13: shift each letter by K positions mod 26. ROT13 is the special case K=13 (and is self-inverting). Trivially broken by frequency analysis.
  • One-time pad: key is a random string as long as the message; XOR each byte. Capable of perfect secrecy — but needs enormous key material, and key distribution is again the practical problem.

Unix History & Microkernels

where operating systems came from — and where they didn't go
⚠ Examinability note
Most of this week is reinforcement and context — fascinating, but non-examinable. Only two things here are examinable: fork() and exec() (OSTEP ch.5) and microkernels. Those two are marked with a ★ below. The rest is for your interest (and makes you a better-rounded engineer).

Why Unix matters context

Unix was created at AT&T Bell Labs in 1969–71 by Dennis Ritchie and Ken Thompson, as a deliberately simple reaction to the over-ambitious, delayed Multics project. Much of the technical vocabulary of OSes comes from Unix: kernel, shell, inode, pipe, root. It popularised concepts now taken for granted: hierarchical filesystem, byte-oriented files, shell commands as files, I/O redirection, forking processes. It became the basis of the POSIX standard.

Why so popular?
Deliberate simplicity; written mostly in a high-level language (C, created by Ritchie for the 1973 rewrite — radically lowering the cost of porting); and early academic licensing. This enabled use in education, portability across machines, and a wave of clones/derivatives. In the 1990s, free clones (Linux + GNU) and derivatives (the BSDs) displaced commercial Unix. Today almost all widely-used OSes are Unix-like — only Windows isn't (it's more VMS-based, though Unix-influenced).

Big idea (1): fork() & exec() ★ examinable

To create a new process in Unix, you don't build one from scratch — you fork() (duplicate) the current process, then optionally exec() (replace yourself with a different program).

The key fact about fork() — a classic exam point
fork() is called once but returns twice:
  • In the parent: returns the child's PID (a positive number).
  • In the child: returns 0.
  • On failure: returns negative (no child created).

Both processes then continue from the same point (right after the fork), each with their own copy of memory — implemented efficiently with copy-on-write (Week 4!).

int rc = fork(); if (rc < 0) { // fork failed } else if (rc == 0) { // CHILD (new process) — rc is 0 // optionally set up fds/env, then exec() a new program } else { // PARENT — rc is the child's PID }

Why is fork-then-exec a good design?
Between the fork and the exec, the child can set itself up in code — hook up pipes/IPC channels, redirect file descriptors (e.g. dup2 to make stdout a pipe), modify the environment. This avoids needing a giant "mega-API" that can specify every attribute of a new process up front. It also makes sharing (memory, fds, IPC channels) between parent and child easy, and was great for concurrent servers in the pre-thread days.

Big idea (2): "Everything is a file" context

Instead of separate categories (with separate interfaces) for system commands, devices, and files, Unix maximises use of the single file abstraction:

  • Devices appear as special files (e.g. /dev/tty0, /dev/hd0).
  • Commands are just executable files.
  • Even non-file IPC (pipes) is accessed via file descriptors.
Good and bad
Good: avoids special interfaces, maximises compositionality (everything plugs together). Bad: not everything is conceptually a file! seek() makes sense for a file but not live audio/video; ioctl() is the catch-all for "any operation that doesn't fit." Unix gives no explicit way for files to express how they differ (operations, behaviour, formats). ("Use plain text; it is universal" was one optimistic rejoinder.)

Microkernels ★ examinable

A traditional Unix/Linux kernel is a monolith: filesystems, network stack, device drivers, scheduling, and memory management all run together in kernel mode. What's wrong with that?

Problems with the monolith
No fault isolation: kernels contain bugs — especially in device drivers (the classic cause of Windows' "blue screen of death"). One faulty driver can crash the whole system. No least privilege: kernels contain security exploits (search "CVE Linux kernel") — and every component runs with full privilege.

The microkernel idea: move as much as possible out of the kernel into ordinary, isolated server processes. The microkernel itself keeps only the bare minimum: interrupt handling and basic IPC primitives.

The catch: IPC overhead
Moving components into separate processes means far more crossing of protection boundaries — every interaction that used to be a function call is now IPC. This overhead was microkernels' big problem. Liedtke's work on the L3/L4 microkernels (1993+) showed that architecture-aware optimisation of IPC could hugely reduce these overheads.
The Tanenbaum–Torvalds debate (1992)
Microkernels were such a big deal that in 1992, OS professor Andrew Tanenbaum posted "LINUX is obsolete", arguing monolithic kernels were "a giant step back into the 1970s" and that among OS designers "the debate is essentially over — microkernels have won." History had other plans: Linux (monolithic) went on to dominate. The lesson isn't that one side was simply right — it's that development model and pragmatism often beat architectural elegance.
What Linux actually did instead
Linux kept the monolithic design (no driver fault isolation, no least privilege for kernel components) and the same old Unix user-space API. Its innovation was in the development model, not the architecture. To stay reliable without fault isolation, it relies on aggressive quality control (drivers merged into the kernel tree). For performance it moved from a single "big kernel lock" to fine-grained locking and lock-free techniques like RCU (Read-Copy-Update), where writers make a copy and atomically swap it in, letting readers proceed without locks.

Advanced topics (interest only) context

Two big questions the course leaves you with:

1. Why not "just" design a better system with capabilities everywhere?

Much research has explored pervasive capabilities — the Cambridge CAP computer (1970s, where memory addresses are capabilities enforced by hardware), KeyKOS, and modern work like Capsicum (generalising file handles) and CHERI (where "pointers are capabilities on memory", carrying bounds + permissions, with new hardware to enforce unforgeability). The hard part isn't the clean-slate design — it's retrofitting capabilities onto the everyday Unix-like file/process abstractions everyone already uses.

Which identifiers are capabilities?
A capability combines access rights + identifier. By that test: Unix file handles (fd) are <access, object> pairs — true capabilities! But process IDs, pointers, and filenames are just <object> — their permissions are implicit (in user IDs, the page table, or the file's ACL). Pervasive capabilities would mean baking access rights into all of these.

2. Do we even need an operating system at all?

Microsoft Research's Singularity (2000s) asked: instead of hardware-isolated processes (MMUs, the basis of limited direct execution), why not software-isolated processes (SIPs) — use a memory-safe language (like C#/Java-style bytecode + JIT) and verify safety statically? A driver could fail without crashing the system, sharing could be finer-grained than page granularity, and hardware could be simpler. The catch: C/C++ have no memory-safe implementation, so porting existing code is hard.

A modern echo: WebAssembly
"Compile to the browser" (first JavaScript, now WebAssembly) is the same idea reborn: run code over a software-emulated memory ("memory" is a JS array) with JIT compilation for speed. Ironically, people end up re-implementing a POSIX-like OS in the browser — "that virus again," as the slides put it. Unix-style primitives remain endemic.

Java Threads & the Memory Model

where shared data meets uncontrolled interleaving
Where this fits
This begins the concurrency mini-course that runs alongside the OS material (and makes up ~40% of the exam). It builds directly on the threads ideas from Week 2 — especially the crucial fact that threads share the heap but each has its own stack. That sharing is exactly what makes concurrency powerful and dangerous.

Multithreading basics

A single-threaded program has one thread of execution — the traditional style. A multithreaded program has multiple threads executing "at the same time." Whether that's literally the same time depends on cores: one core → multithreading creates the illusion of simultaneity (interleaving); multiple cores → threads can run truly in parallel. (Same concurrency-vs-parallelism distinction from Week 1.)

All Java programs are threaded
Even if you never create a thread, the JVM does: a Main thread runs your program, plus background threads for garbage collection etc. Add a UI (JavaFX) and that's threaded too. So you're always in a multithreaded world.

Creating threads — three ways

The work a thread does lives in its run() method (like a main() for threads). Crucially: you never call run() yourself — you call start(), and the JVM calls run() at some point. When a thread reaches the end of run(), it terminates.

Way 1 Extend the Thread class

public class ExtendThreadExample extends Thread { @Override public void run() { System.out.println("running..."); } public static void main(String[] args) { ExtendThreadExample t = new ExtendThreadExample(); t.start(); // NOT t.run() ! } }

Way 2 Implement Runnable

public class RunnableExample implements Runnable { @Override public void run() { System.out.println("running..."); } public static void main(String[] args) { Thread t = new Thread(new RunnableExample()); t.start(); } }

Way 3 Lambda (Runnable is a functional interface)

Runnable r = () -> { System.out.println("running..."); }; Thread t = new Thread(r); t.start();

Runnable has only one abstract method, so it's a functional interface — the lambda's body is run() (the name is implied; empty parens = no parameters).

Extend Thread vs implement Runnable — common exam question
Prefer Runnable. Two reasons:
  • Inheritance: Java allows only single inheritance. If you extend Thread you can't extend any other class. Implementing Runnable leaves you free to extend something else (and you can implement many interfaces).
  • Decoupling & sharing: extending Thread couples thread-management with behaviour in one object — each thread has its own. With Runnable you can pass the same Runnable object to multiple threads, making data sharing between them easy. (Thread = the "vehicle"; Runnable = the "behaviour".)
Threads are independent
The Main thread and any thread you create are independent peers — neither owns the other; the OS manages both. Your new thread does not "belong" to Main.

Thread lifecycle: sleep, stop, join

Pausing — Thread.sleep()

A static method that pauses the current thread for ~N milliseconds (timings are approximate), relinquishing the CPU. Used for cooperative behaviour (a low-priority background task acknowledging it doesn't need much CPU) or for timing. Must be wrapped in try/catch for InterruptedException.

Stopping — use a boolean, not stop()

Never use Thread.stop()
stop() exists but is deprecated — it leaves your thread (and app) in an indeterminate state. Instead, control termination yourself with a boolean flag the run loop checks:
private volatile boolean stopped = false; public void setStopped() { this.stopped = true; } public void run() { while (!stopped) { // do work... Thread.sleep(1000); } }

Daemon threads

By default the JVM keeps running while any non-daemon thread lives — even after Main exits (Main is "just another thread"). To make a thread die when Main does, call thread.setDaemon(true) before starting it.

Coordinating — Thread.join()

The default is no coordination. If one thread must wait for another to finish (e.g. it needs a value the other computes), use join(): if thread A calls B.join(), A blocks until B terminates.

Thread t = new Thread(runnable); t.start(); t.join(); // this thread blocks here until t finishes System.out.println("t has terminated");

Passing references = sharing the object
When you pass an object reference to a method, the reference is copied onto the stack, but it still points to the same object on the heap. So a mutator call like message.setMessage("SUCCESS") changes the one shared object — visible to the caller afterwards. Race conditions

Consider two threads each incrementing a shared counter 100,000 times. You'd expect 200,000. You won't get it. Why? Because counter++ looks atomic but isn't — it's three operations:

counter++ // actually: 1. READ counter // load into a register 2. INC register 3. WRITE counter // store back

If two threads interleave these steps, an update gets lost:

StepThread-0Thread-1counter
1READ → reg=55
2READ → reg=5 ⚠5
3INC → reg=65
4WRITE → 66
5INC → reg=66

Two increments happened, but counter only went from 5 to 6 — it should be 7. Thread-0 overwrote Thread-1's update: a lost update.

Definition: race condition
A race condition is when the result of an operation depends on the timing/ordering of threads (a "race" between them) rather than on the program's logic. The shared-counter program gives indeterminate results — different every run (e.g. 125520, 137097, ...), never reliably 200000. The root cause is unsynchronised access to shared mutable state via non-atomic operations.
When is there NO race?
If each thread runs its own Runnable object, counter is a separate instance variable per object — not shared — so both reliably reach 100000. The race only appears when threads share the same object (and thus the same counter on the heap). Shared mutable state is the prerequisite for a race.

Java Synchronization

fixing races — and the deeper memory problems beneath them
The mission
Week 9 showed that sharing data between threads causes race conditions (because operations like counter++ aren't atomic). This week is the fix. But there are actually two distinct problems to solve — and most people only notice the first:

① Mutual exclusion (atomicity)

Stop two threads interleaving mid-operation. Fixed by synchronized / locks.

② Visibility

Make sure one thread's update is actually seen by others (CPU caches hide it!). Fixed by volatile (or synchronized's flush).

Critical sections & mutual exclusion

The shared-counter program from Week 9 contains a critical section: a sequence of instructions that only one thread at a time should execute, or you get incorrect/unpredictable behaviour. We protect critical sections with mutual exclusion — one thread at a time gets exclusive access — generally enforced with locks.

synchronized methods

The deceptively simple fix: declare the method that touches shared state as synchronized. The JVM then guarantees only one thread at a time can be inside it — making the whole method a critical section.

private synchronized void incCounter() { counter++; // now effectively atomic (within this method) }
A subtle but important detail
With synchronization, at least one thread is guaranteed to reach the correct total (200,000); the other might not. Why? The threads no longer interrupt each other mid-instruction, but they still interrupt each other in terms of progress — one thread may hit its loop limit before the shared counter reaches the final total. Think of it as the threads cooperating to reach the total, rather than each independently reaching it.

Locks & intrinsic locks

A lock lets you declare a critical section accessible by one thread at a time. Just before entering, a thread tries to acquire the lock; on exit it releases it. If thread A holds the lock and thread B tries to acquire it, B blocks until A releases — and if A never releases, B blocks forever.

🔓→🔒
Thread A acquires the lock, enters the critical section.
⛔
Thread B tries to acquire — lock is held → B is BLOCKED (waits).
🔒→🔓

Intrinsic locks (monitors)
Every Java object has a built-in lock called its intrinsic lock (or monitor). When you mark a method synchronized, you're locking on a specific object — implicitly this (the current object). You don't have to write it; it's implied.
Locking is per-object, not per-method
Because the lock is on the object (not the method), while one thread holds it, other threads can't enter any synchronized method on that same object. This is correct behaviour — if it only locked the single method, another synchronized method could run concurrently and still cause interference on the same shared state.

synchronized blocks — lock only what you need

A synchronized method locks the whole method — even parts that don't need it. If only part touches shared state, use a synchronized block to make just that part the critical section (and acquire the lock later / hold it for less time):

private void addToCounter(int amount) { if (amount >= 0) { // 'amount' is a local — not shared, no lock needed synchronized (this) { // lock acquired only here, only if needed counter += amount; // the actual critical section } } }

With a block you must specify which object to lock on (here this). The local parameter amount is per-thread, so it never needed protection — only the shared counter does.

Locking on another object

Sometimes you want to lock a different shared object — often one that isn't itself thread-safe. You can synchronize on any object:

public void run() { for (int i = 0; i < 100_000; i++) { synchronized (counter) { // lock on the shared Counter object counter.incCounter(); // Counter itself is NOT thread-safe } } }

Thread safety & immutability

The fragility of external locking
Locking on a shared object from outside relies on every class remembering to do the same. If one thread misuses the object (accesses it without the lock), all threads can suffer. You can't enforce it. Why might you be forced into this? Because you might not control the shared class's source code (you can't add synchronized to a class you didn't write).
The right way
Ideally, any class used to create shared mutable objects should be designed thread-safe from the start (synchronizing internally). And the strongest guarantee of all: an immutable object is inherently thread-safe — if its state can never change, no thread can ever observe an inconsistent value, so no locking is needed at all.

STALE ⚠

CPUs have mechanisms to flush caches/registers back to main RAM, but only after a flush can all threads be guaranteed to see the same value. Crucially: mutual exclusion alone doesn't fix this — it's not about interleaving, it's about stale cached copies.

volatile

Java's keyword for variables that might be cached locally and go stale. Marking a variable volatile signals that it must be flushed to main memory when changed, and read back from main memory when accessed — bypassing stale cached copies.

private volatile boolean newDataAvailable;
Java's visibility guarantee — you only need ONE volatile
Remarkably, if you just need the latest values flushed/read, you only need to mark one variable volatile. By Java's visibility guarantee: when a volatile variable is flushed to RAM, all variables visible to that thread are flushed too. (This is also why the boolean stop-flag from Week 9 should be volatile.)
synchronized gives visibility too
synchronized blocks have their own visibility guarantee: on entry, all variables visible to the thread are refreshed from main memory; on exit, all are flushed back. So synchronized fixes both problems — mutual exclusion and visibility. volatile fixes only visibility (no mutual exclusion / atomicity).

Instruction reordering & happens-before

One more twist. The JVM, the Java compiler, the HotSpot JIT compiler, and the CPU can all reorder instructions in your program — e.g. to exploit CPU pipelining by parallelising independent instructions for throughput. Statements that appear independent are candidates for reordering.

Why reordering breaks concurrency
Consider addToBuffer where these two lines get swapped:
newDataAvailable = true; // volatile flush — "data is ready!" buffer.addToBuffer(data, ...); // ...but data isn't actually added until HERE
Because newDataAvailable is volatile, setting it true flushes to RAM — so another thread thinks new data is available before it actually is. A consumer could read garbage.
The "happens-before" guarantee
Java's volatile happens-before guarantee fixes this: if a statement appears before a write to a volatile variable (in the program as written), it will stay before — it won't be reordered after it. This prevents the dangerous swap above.

The same applies to synchronized blocks: instructions won't be moved out of a synchronized block (a statement inside won't move to after it, and a statement before won't move to inside/after). The lock boundaries act as reordering barriers.

Deadlock & Semaphores

when locks turn against you — and finer-grained control
The final piece
Week 10 used synchronized to fix races. But locking itself can cause new problems — most notably deadlock. This week covers explicit locks (the Lock interface / ReentrantLock), the four conditions for deadlock, the famous Dining Philosophers problem, how to avoid deadlock, and semaphores for when you want to allow several threads through, not just one.

The Lock interface & ReentrantLock

synchronized is convenient but a blunt tool — it can only lock entire methods or blocks within a method, and the lock is released automatically. Java also offers explicit locks implementing the Lock interface, which you must create, lock, and unlock yourself. That's the price for more flexibility. The basic implementation is ReentrantLock:

private Lock lock = new ReentrantLock(); private void addToCounter(int amount) { if (amount >= 0) { try { lock.lock(); // acquire — open the critical section counter += amount; } finally { lock.unlock(); // ALWAYS release, even on exception } } }
Why try-finally?
Unlike synchronized (which releases automatically when the block exits, even via exception), an explicit lock will stay locked forever if you forget to unlock — e.g. if the critical section throws. Putting unlock() in a finally block guarantees release no matter what. The lock is now just an object, decoupled from any particular method or block.

Reentrancy

A lock is reentrant if a thread that already holds it can acquire it again without blocking. Java's synchronized blocks/methods are reentrant, and so is ReentrantLock (hence the name).

public synchronized void f() { g(); // calls another synchronized method on the SAME object } public synchronized void g() { }
Why reentrancy is essential
Consider a thread calling synchronized f() on object A, which calls synchronized g() also on A. The thread already holds A's lock from entering f(). Without reentrancy, it would block waiting for a lock it already holds — an instant self-deadlock. Reentrancy makes nested synchronized calls on the same object possible.

synchronized vs ReentrantLock

They behave similarly, so when would you choose the explicit lock? ReentrantLock offers several things synchronized can't:

Deadlock & the four conditions

If you only lock within one object you're usually fine. But realistic programs have multiple threads acquiring multiple locks, and if there are dependencies, you can get deadlock: thread A holds lock X and needs Y; thread B holds Y and needs X. Both are stuck forever, each waiting on a lock the other holds.

The four conditions for deadlock — ALL must hold

1Mutual Exclusion

Resources are held in a non-shareable way — i.e. critical sections exist.

2Hold and Wait

A thread holds one resource while waiting to acquire others.

3No Preemption

A resource is only released voluntarily by the thread holding it — it can't be forcibly taken.

4Circular Wait

A cycle of threads exists, each waiting on a resource the next one holds.

Break any ONE of these four and deadlock cannot occur. That's the key to every avoidance strategy.

A realistic example: bank transfers

Two threads transfer money between accounts, locking from then to:

// Thread 1: transfer(sid, doris, 200) → locks Sid, then Doris // Thread 2: transfer(doris, sid, 300) → locks Doris, then Sid public static void transfer(BankAccount from, BankAccount to, double amount) { synchronized (from) { synchronized (to) { from.withdraw(amount); to.deposit(amount); } } }

The threads call transfer with accounts in different orders. Thread 1 grabs Sid's lock; Thread 2 grabs Doris's lock — then each needs the lock the other holds. Deadlock. (All four conditions are present, including the fatal circular wait.)

The Dining Philosophers problem

The classic illustration. Five philosophers sit around a table, alternating between thinking and eating. There are five forks, one between each pair. To eat, a philosopher needs both adjacent forks. They're selfish and uncoordinated: each picks up its left fork, then its right fork, eats, then puts both down.

public void run() { while (true) { act("is thinking"); synchronized (fork1) { // pick up LEFT fork synchronized (fork2) { // pick up RIGHT fork act("is eating"); } } } }
Why it deadlocks
If all five philosophers get hungry at once and each grabs its left fork simultaneously, every philosopher now holds one fork and waits forever for the right one (held by their neighbour). That's a perfect circular wait — all five waiting on the philosopher to their right. Everyone starves. The program might run a while without deadlock, but it's never guaranteed.

Deadlock avoidance

The best approach is to design so deadlock can't occur — by breaking one of the four conditions. (You can also do deadlock detection: spot it after it happens and break it, but prevention is cleaner.) Since you usually can't eliminate mutual exclusion, the most practical target is the circular wait.

Lock ordering — the key technique
Impose a fixed global order in which locks are always acquired, based on some property of the objects. If everyone acquires in the same order, no cycle can form. For the bank example: sort by account id before locking.
BankAccount first = from, second = to; if (first.getId() > second.getId()) { // always lock lower id first first = to; second = from; } synchronized (first) { synchronized (second) { ... } }

For the philosophers, the equivalent fix is to make the last philosopher reach for the right fork first. This breaks the symmetry of the circular wait — the cycle can no longer close, so at least one philosopher can always get both forks and eat.

Or use ReentrantLock's tryLock()
A more flexible fix: with tryLock(), a philosopher attempts the right fork but doesn't block if it's unavailable — they just put the left fork back down and try again later. No thread ever holds-and-waits indefinitely, so deadlock is avoided (this breaks the hold and wait condition). Verified in Ian's program: all philosophers get to both think and eat.

Semaphores

So far, locks allow one thread at a time. But sometimes you want to allow N threads — e.g. a database that supports only 5 concurrent connections. A semaphore handles this.

What a semaphore is
Basically an integer with a fixed maximum, plus methods to increase/decrease it. It's initialised to its max — say 5 permits. acquire() takes a permit (5→4→3...); when permits hit 0, further acquirers block. release() returns a permit. The count never exceeds the maximum. This is a counting semaphore.

Binary semaphore = a lock
A binary semaphore holds only 0 or 1 — so it behaves exactly like a lock (one permit = one thread at a time). The general counting semaphore is the more powerful generalisation: it allows literal concurrent access by up to N threads to a resource that can safely handle N users at once.

  • Context switch = save/restore registers (pure overhead, ~1–2µs).
  • FCFS (convoy effect) · SJF/STCF (optimal turnaround, risks starvation) · RR (optimal response, fair).
  • Trade-off: turnaround vs response — can't optimise both.
  • Threads share code/data/heap, but each has its own stack → source of sync bugs.

W3 · Virtual Memory & Translation

  • Address-binding problem: programs embed fixed addresses but share physical RAM safely.
  • Evolution: relocation → base/limit → segmentation → paging → multi-level tables.
  • Internal frag (waste inside allocation) vs external (scattered free space).
  • Paging: equal frames kill external frag. Split address into page# p + offset o.
  • Translate: index page table by p → frame f → combine with o.
  • PT size = m × 2ⁿ (32-bit, 4kB, 4B PTE → 4MB). Multi-level tables skip unused chunks.
  • TLB caches translations; exploits locality (array example → 70% hits).

W4 · Demand Paging

  • Page fault = a hook, not just an error → OS can act & resume.
  • Lazy allocation · lazy zeroing (1 shared zero frame) · copy-on-write.
  • Virtual memory = illusion of more RAM than physical, via swapping to disk.
  • AMAT = T_M + P_miss × T_D. Tiny miss rate dominates (T_D huge).
  • Replacement: Optimal (baseline) · FIFO (Belady anomaly!) · LRU (impossible exactly; stack property) · Clock (second-chance, uses Used bit).

W5 · User-Space (malloc, stack, I/O)

  • malloc = library code in the process; parcels small pieces from OS pages. 2 layers of frag.
  • Free list threaded through free space; first-fit (fast) vs best-fit (less waste).
  • brk (move program break) vs mmap (flexible, no contended resource).
  • Stack frame = return address + saved frame pointer + locals. Walk it for backtrace.
  • Buffer overflow = unbounded input overwrites return address → hijack. C doesn't bounds-check; Java does.

W7 · Security

  • Security (adversarial) ≠ fault-tolerance (accidental).
  • Mechanism (OS) vs policy (users). Unix checks at open() only.

W8 · History & Microkernels ★

  • fork() — once called, twice returned: child PID in parent, 0 in child, <0 on fail. CoW memory.
  • exec() — replaces process with new program. fork-then-exec lets child set up fds/pipes/env.
  • Microkernel — drivers/FS/etc. as isolated server processes; kernel = interrupts + IPC only.
  • Benefit: fault isolation + least privilege. Cost: IPC overhead (L4 optimised it).
  • Monolithic (Linux) won via development model & quality control, not architecture.

W9 · Java Concurrency

  • 3 ways to thread: extend Thread, implement Runnable, lambda. Call start() not run().
  • Prefer Runnable — frees inheritance + lets threads share one behaviour object.
  • sleep() (TIMED_WAITING) · stop via boolean flag · daemon dies with Main · join() waits for another thread.
  • States: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
  • Memory: locals/refs on per-thread stack; objects+fields on shared heap.
  • counter++ = READ/INC/WRITE (not atomic) → interleaving → lost update.
  • Race condition: result depends on timing, not logic; needs shared mutable state.

W10 · Java Synchronization

  • Two problems: mutual exclusion (atomicity) + visibility.
  • Critical section = one-thread-at-a-time code; protect with mutual exclusion via locks.
  • synchronized method locks on this; blocks ALL synchronized methods on that object.
  • Intrinsic lock — every object has one; acquire on enter, release on exit, others BLOCK.
  • synchronized block — lock only what's needed; name the lock object.
  • Immutable objects are inherently thread-safe.
  • Visibility: per-core caches → stale copies. volatile = flush/read RAM (visibility, not atomicity). synchronized gives both.
  • Happens-before — volatile/synchronized prevent dangerous instruction reordering.

  • Reentrant = holder can re-acquire; needed for nested synchronized calls.
